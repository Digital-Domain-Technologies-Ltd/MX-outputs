Appendix C: Web Audit Suite

CogNovaMX's commercial service for measuring how well a website works for the machines reading it.

What it is

Web Audit Suite is a measurement service. It crawls a site the way the machines that matter actually crawl it (large language models, training pipelines, agents, Common Crawl, search indexers) and reports what those machines see, what they miss, and what changes most when fixed. The service is delivered by CogNovaMX as part of an engagement; it is not a self-serve tool.

The output is a client-facing report and a prioritised action plan. The report names the highest-leverage changes for the site under review, page by page, ranked by what is blocking machine readers from doing the work it exists to support.

What it measures

Web Audit Suite covers the dimensions that determine whether a machine reader can extract the same value from a page that a human visitor can:

  • Served HTML versus rendered HTML. What machines see at fetch time, before any JavaScript runs. The single highest-impact dimension; most machine readers never execute JavaScript.

  • Structured data presence and correctness. Schema.org markup, JSON-LD blocks, and type disambiguation: the standards that let machines know what a page is about without inferring it from prose.

  • Pricing, availability, and other commercial facts. Whether the numbers and states a buyer needs are present in the HTML or hidden behind a render step.

  • Document and page accessibility. WCAG conformance, semantic HTML, and ARIA usage, which assistive technologies and machine readers both need.

  • Discovery surface. Sitemap completeness, robots.txt correctness, llms.txt presence, in-page link discoverability, canonical declarations. The probe extends beyond the well-known trio: every entry in the IANA Well-Known URIs registry that a machine reader might check is probed, including agent-card.json (A2A protocol), did.json (W3C decentralised identity), oauth-authorization-server / oauth-protected-resource / jwks.json (authorisation and signing), caldav / carddav (calendar and contact discovery), mta-sts.txt (mail transport security), the IoT and device-provisioning family (brski / cmp / coap / core), and others. Where a JSON discovery file is present, the audit parses its body and reports the structured contents in the report tables rather than presenting a row that says only that it exists. Where a path is absent the report stays silent, surfacing only the IANA registry pointer so the reader knows where to look up the full catalogue.

  • Agent experience (AX). The site read the way a coding or research agent reads it, with plain HTTP and no JavaScript, against the public Agent-Friendly Documentation Spec: whether llms.txt exists and its links resolve, whether pages are available as markdown by address or by negotiation, whether a page is complete in one fetch with its content near the top, whether a wrong address answers 404, and how redirects, cache headers, sign-in walls and bot protection treat an automated visitor. The report carries two figures. The spec score is the site's standing on that specification's own public scale, which compares like for like with any other reading of it. The house score is the same scale extended to the full-content file, the agent skill file and the MCP server, and compares only with another audit from this series. Every check states pass, warn or fail, with its fix.

  • Provenance and trust signals. Whether the page declares who published it, when, under what licence, and how a reader can verify those claims.

  • Performance and pipeline survivability. Whether the page survives the truncation, byte caps, and timing constraints that real-world crawlers impose.

  • The accessibility tree. There is no single kind of machine visitor: an on-device model with a tight context window, a foundation LLM with browsing tools, a plain scraper, a converter that flattens HTML to text, a one-shot fetcher. Each reads a different projection of the page, none sees the visual layout, and meaning carried in only one channel fails every visitor that cannot read it. The suite reads each page the way an accessibility-tree consumer does and flags where behaviour, names, and structure fail to reach the tree: clickable containers with no role, links named "read more", form fields labelled only by placeholder text, data locked inside images, landmark wiring that resolves to nothing. Findings that repeat across pages with the same structure are reported as one template-level fix, not page-by-page copies. Because screen readers consume the same tree, every fix serves human visitors and machine visitors at once.

  • Machine Processing Speed. How long a machine takes to understand a page once the bytes have arrived, measured on cached pages with no network in the way. Network time describes the infrastructure. Analysis time describes the content. Two sites with identical browser performance scores can land in different bands: that score measures what is painted, and this one what a machine has to parse. The result is reported as a band rather than a raw number, so the site owner knows where they stand:

Band Name Time per page What it means
A Machine-Lean Under 100 ms Clean, structured markup that agents process without effort
B Machine-Ready 100 to 300 ms Standard complexity that agents handle without friction
C Machine-Workable 300 to 800 ms Moderate overhead; agents cope but may miss context
D Machine-Heavy 800 ms to 2 seconds Dense DOM or heavy script layers; agents slow down and risk missing information
E Machine-Dense Over 2 seconds Parsing cost exceeds a practical agent budget

A site in Band C, D or E is told which pages drive the overhead and which structural patterns cause it. The fixes are structural, not performance tuning: flatter DOM trees, semantic markup, and content written into the document instead of assembled by script (Cranstoun, 2026, https://mx.allabout.network/blog/machine-parsability-speed.html).

The dimensions are scored against thresholds CogNovaMX has calibrated against the behaviour of the major machine readers in production. The thresholds follow those readers as their behaviour shifts; the service tracks the drift.

Beyond the per-dimension scores, the suite applies a machine-readability adjustment. Some gaps are ones a machine cannot work around anywhere on the estate: an audience the audit had to infer rather than read, a sitemap that is ambiguous to a parser, content that appears only once JavaScript has run, markup so deeply nested that the meaning is buried, an automated visitor that is blocked outright, or an origin too slow to finish a fetch. Where a site carries such gaps, the overall machine-readability score is reduced to reflect that a real agent would struggle to use it. Every reduction is named in the report, so the reader sees exactly what drove the number down rather than facing an unexplained drop. The reduction is bounded, so these signals alone cannot score a site to nothing, and a gap that an individual dimension already accounts for is not counted twice.

Occasionally a site refuses the interrogation altogether: every page request from every automated visitor is turned away. The audit still delivers, because the refusal is itself the finding. The report sets out what a refused machine can still observe (which visitors are turned away and how, what the error handling looks like from outside, which discovery files the site publishes) and names the consequence: every AI search surface, recommendation engine, and buying agent meets the same closed door. For some organisations that refusal is deliberate and correct. Either way, the audit gives it a dated, evidenced record.

Running the audit inside your network

Some content cannot leave the customer's network. Regulated procurement teams at banks, hospitals, public-sector bodies, and pharmaceutical companies routinely ask, before agreeing to an engagement, whether any of the audit data (the pages crawled, the metadata extracted, the findings produced) leaves their network at any point in the pipeline.

The structural answer is yes by default. The pipeline runs as a deterministic core with one inference layer at the end. The deterministic core is scripted: every probe, every gate, every check is a small standard operating procedure the customer's security team can read, understand, and run in their own environment. The inference layer is small by design, a single judgement pass that turns a body of verified evidence into a readable report.

The inference layer can run against a hosted model or a locally served one. Ollama, LM Studio, and an on-premise Llama deployment look identical from the audit's point of view. When the customer specifies a local inference target at scoping, the audit runs end-to-end inside their network, no data leaves, and the resulting report matches the hosted-inference equivalent. The choice is theirs; the audit's output does not change.

Titles, descriptions and proposed rewrites

The title and description checks match those of a search-focused audit (missing, too long, too short, duplicated), with two more that ask what the text does. A title is flagged when it does not name the page's topic, meaning the words its own main heading and meta description agree on, so no keyword is guessed. A meta description is flagged when nothing in it asks the visitor to act (find, book, compare, download). Both checks rely on English word lists. They judge only English pages, and a page in another language is not marked down for them.

For each page that breaks a title or description rule, the technical appendix proposes a rewrite beside the current text and the rules it broke. A language model words the proposal and does nothing else. The audit then runs its own title and description rules on every proposal and drops any that still breaks one, rather than showing it. The pages, the current text and the rules broken come from the audit's own records, never from the model (Cranstoun, 2026, https://mx.allabout.network/blog/the-mx-audit-and-a-full-seo-audit.html).

The standard report makes no comparison with a named competitor. Nor does it list the topics a competitor covers that the audited site lacks. Each would need a second full audit of the other site, with every number drawn from that run's records.

The PDF inspector

The document checks behind the document-accessibility supplement are also available on their own. A free public inspector at https://mx.allabout.network/tools/pdf-inspector.html takes one PDF at a time and parses it in the reader's browser, so the file never leaves the machine. It reads the tagged structure tree, the XMP metadata packet and any embedded AI-governance provenance record, and places the file in one of three tiers:

Tier What the file carries
MX Compatible A tagged structure tree, MX metadata and the provenance record the MX badge claims
Tagged only A tagged structure tree without MX metadata
Plain Neither

Four things run on one detection core:

  • the public inspection page;
  • a hard gate in CogNovaMX's own publishing pipeline, which fails the build if a freshly rendered PDF would not qualify for the MX Compatible mark;
  • an automated check of the core against a reference file, repeated on every test run;
  • a command-line tool for accredited operators' own pipelines.

A regression in the core fails all four in the same way, so what CogNovaMX publishes and what it enforces cannot drift apart. The command-line tool runs locally, because the PDFs an operator checks are usually confidential, and it reports in a form a build system understands: exit code zero when every file meets the configured minimum tier, one when at least one falls below it, and two on a fatal error (Cranstoun, 2026, https://mx.allabout.network/blog/provenance/the-inspector-you-can-audit-yourself.html). A buyer can therefore re-check a supplier's PDF in the public inspector and reach the same conclusion as the supplier's pipeline.

A lighter page-level check exists in the same spirit. A browser extension reads the page in front of the reader for MX signals (the MX meta tags, AI disclosure, discovery links, files at the site's well-known addresses, structured data, Open Graph, accessibility quick wins and provenance markers) and scores each as pass, warn, fail or info. It then asks whichever on-device model the browser already has (Gemini Nano in Chrome, Phi-Silica in Edge on Copilot+ PCs, or a local Ollama server as the fallback) to write a short summary. Nothing leaves the device, and the model writes prose, not findings. The extension is a sideloaded developer tool for practitioners, a ten-second read of one page; the audit is the service when a written report and a record of how each finding was reached are needed (Cranstoun, 2026, https://mx.allabout.network/blog/watching-with-the-machines.html).

What you receive

Each engagement produces:

  1. The audit report, one document in two parts. Part one is an executive report the decision-maker reads: the verdict, the scorecard, what is working, the issues that matter in plain language, and the next steps. Part two is a technical appendix the implementing team works from: every finding in detail, page by page, with a recommended fix per blocker. The executive can stop at part one; the appendix holds the depth.
  2. Four covering letters, one per audience. Short letters addressed to the site owner, the development team, the agency, and the compliance function, each framing the findings so that audience can act on them.
  3. A prioritised action plan. What to fix in the first week, the first month, and the first quarter. Each action comes with an estimate of the score uplift it unlocks.
  4. A regression baseline. A snapshot of the site's current state so the next audit can measure the delta. Engagements that span multiple cycles produce a trend report alongside the per-cycle deliverables.
  5. Optional accessibility supplement. Detailed WCAG findings, severity-ranked, mapped to the relevant Web Content Accessibility Guidelines success criteria.
  6. Optional document-accessibility supplement. Coverage of every PDF, DOCX, and EPUB the site links to, ranked by an automated structural accessibility check (tagging, document language, PDF/UA declaration) that does not establish legal conformance.

Reports are delivered in PDF for the executive audience, plus structured data for technical teams who want to feed findings into their own tooling.

Who it is for

  • Publishers and marketers whose revenue depends on being found by AI search and recommendation surfaces.
  • E-commerce operations whose product information needs to reach the agents now placing transactions on behalf of buyers.
  • Government and public sector teams whose accessibility obligations are now enforced, not only set out in policy.
  • Developers and architects building new sites who want to measure machine readiness before launch, not after.
  • Investors and acquirers running due diligence on a site whose discoverability and trust posture is part of the asset valuation.

How an engagement works

A typical engagement runs in four stages: scoping, baseline audit, action plan, and re-audit. Scoping confirms the site, the audience priorities, and the supplements that apply. The baseline audit produces the deliverables described above. The action plan is reviewed with the client's team. The re-audit, six to twelve weeks later, measures the delta.

Engagements that need ongoing visibility move to a monthly cadence after the initial cycle. The dashboard surfaces score movement, regression detection, and progress against the action plan.

What changes after an audit

The findings point a site at three changes it can make and then measure at re-audit:

  • Pricing, availability, and product facts made reachable to AI search surfaces that returned "I don't have that information".
  • Structured data on every audited page instead of some of them, which is what rich-result and answer-surface eligibility depends on.
  • Accessibility findings quantified and triaged, moving the site from "we hope it's accessible" to "we know what is broken and what to fix first".

The MX framework documented in this book provides the conceptual basis. Web Audit Suite is the measurement layer that turns the framework into a per-site, per-page, per-cycle reality.

How the suite keeps improving

Each audit teaches the suite. We record what we find as anonymised, platform-level patterns: the type of finding, the platform it appeared on, and how often it recurs. We never store your domain in that shared record, nor your content, your URLs, or the specific text we corrected. When a class of problem keeps appearing on one platform, that signal prompts us to sharpen the deterministic check that catches it, so every future audit of sites built on it is more thorough. The audits run on local models by default, so your content stays inside your infrastructure. The result is a measurement layer that gets sharper for every site on your platform, without any site's data being exposed to another.
