Appendix W: Building the MX Operating System

How MX documentation evolves through human-machine partnership.

What is MX OS?

The MX documentation IS the MX Operating System (MX OS).

When we document patterns here, we define how Machine Experience works. This isn't documentation about a system; this IS the system.

MX OS is:

  • Documentation that specifies behaviour
  • Patterns that practitioners follow
  • Standards that machines implement
  • A living system that evolves through practice

Key principle: Documentation as specification. By documenting how MX should work, we create the operating system that defines machine experience.

The repository as a governed execution surface

MX OS is not only a thing agents read; it is a place agents act. Point Machine Experience at the repository and the repository stops being a passive store an agent writes to and becomes a governed execution surface: the place an AI agent acts on the work safely and on the record. The reference implementation states it in one line:

Maxine is where AI agents act on a repository safely and on the record: bounded by Human-in-Command, enforced by gates, and logged as provenance.

Three mechanisms carry three guarantees:

  • Authority (Human-in-Command). A human decides what the agent may do and where it must stop. The machine executes within that boundary and does not act outside it without direction.
  • Conformance (deterministic gates). A check decides whether a change is allowed to land, and refuses the non-conforming change at the boundary rather than trusting a reviewer to catch it later.
  • Provenance (the logged record). Every consequential action leaves an attributable, machine-readable record that travels with the work.

This completes the two pillars from the agent's side: MX makes the work readable, REGINALD makes it trustworthy, and the governed execution surface is where a machine then acts on it under control. It is an honest claim only with its shipped-versus-planned split kept in view. Shipped, and running on this estate: the governance layer, the gate suite, provenance written as changes land, and Human-in-Command boundaries on every automated system. Planned, and marked as such: packaging the surface as a turnkey product another team installs on its own repository, and the full attestation surface around it. We run on this ourselves, and we are building it into something others can run.

The Collaborative Process

The 4-Phase Pattern

Every significant MX documentation change follows this pattern:

  1. Investigate: Research existing standards, analyse codebase, gather context
  2. Interview: Clarify requirements, identify goals, surface constraints
  3. Iterate: Expand scope as discovery reveals deeper needs
  4. Document: Create clear, complete specifications

This pattern is documented in SOUL.md, the identity file that defines Maxine, and demonstrated in the case study below.

Case Study: Creating Appendix L Namespace Architecture

How It Started

The question: "Should we use ai- or mx- prefix for HTML meta tags?"

Simple answer expected: Rename tags, commit, done.

What actually happened: 7 plans, 7 commits, complete namespace architecture.

This case study demonstrates how MX OS evolves, from simple question to systematic documentation.

Phase 1: Investigate

What Maxine Did:

  1. Researched web standards (January 2026)
    • Searched W3C specifications
    • Searched WHATWG standards
    • Searched IETF RFCs
    • Searched vendor proposals (Google, Microsoft, Meta, Apple)
    • Searched community standards (Microformats, Schema.org)
  2. Finding: NO ai- prefix standard exists anywhere
    • Not in W3C specs
    • Not in WHATWG standards
    • Not in vendor proposals
    • Not in community conventions
  3. Pattern recognition: Framework-specific prefixes exist:
    • twitter: for Twitter Cards
    • og: for Open Graph
    • No generic ai- prefix

Conclusion: ai- was NOT following any established pattern. Need to evaluate alternatives.

Phase 2: Interview

Maxine used AskUserQuestion to understand true goals:

Questions asked:

  1. Goal clarity: "What's the primary goal - generic AI compatibility or MX brand identity?"
    • Answer: MX brand identity, not generic AI
  2. Scope understanding: "Should this be a simple rename or complete namespace documentation?"
    • Answer: Need complete namespace architecture
  3. Documentation level: "How much rationale and context should be included?"
    • Answer: Full documentation explaining the decision process
  4. Overlap analysis: "How does this relate to existing Registry and Appendix D?"
    • Answer: Should consolidate into Appendix L

Key insight from interview: This wasn't a simple rename; it was an opportunity to document complete MX namespace architecture.

Phase 3: Iterate (Scope Expansion)

As work progressed, scope expanded through discovery:

Initial scope: Rename ai- to mx- in a few files

After investigation: Document namespace architecture

After interview: Consolidate Registry and Appendix D

After first draft: Add SOUL.md explaining partnership

Pattern: Each phase of work revealed deeper architectural needs.

Key Principles Demonstrated

1. Investigation Before Action

Anti-pattern: Assume ai- is standard, rename, commit

MX pattern: Research web standards, find NO ai- standard exists, document evidence, then decide

Result: Evidence-based decision with clear rationale

2. Interview to Clarify Intent

Anti-pattern: Guess what user wants, implement, hope it's right

MX pattern: Use AskUserQuestion to understand true goals (MX brand vs generic AI)

Result: Solution aligned with actual requirements

3. Iterate as Scope Expands

Anti-pattern: Stick to original narrow scope, miss architectural opportunities

MX pattern: Allow scope to expand as investigation reveals deeper needs

Result: Complete namespace architecture instead of simple rename

4. Document Transparently

Anti-pattern: Make changes silently, don't explain reasoning

MX pattern: Document process (SOUL.md), rationale (Appendix L), and method (Appendix W)

Result: Replicable process, transparent decision-making

5. Plan Complex Work

Anti-pattern: Try to do everything at once, get overwhelmed

MX pattern: Break into 7 sequential plans, execute systematically

Result: Manageable execution, clear progress tracking

The MX Metadata System

.mx.yaml.md Files: Dual-Purpose Metadata

Every folder in MX repositories contains a .mx.yaml.md file combining:

  1. YAML frontmatter (machine-readable metadata)
  2. Markdown narrative (human-readable documentation)

Example:

---
title: "Build Tools and Automation Scripts"
description: "Build automation and repository management scripts"
audience: ["humans", "machines"]
inherits: "../.mx.yaml.md"
primaryLanguages: ["javascript", "bash"]
mx:
  version: "1.0"
  domain: "build-automation"
  ai:
    aiAssistance: welcome
    aiEditable: true
---

# Build Tools - Narrative

This folder contains scripts for building...

Why both formats?

  • For Humans: Read narrative to understand purpose
  • For Machines: Parse YAML for automation and navigation
  • MX Principle: Design for Both

Inheritance Resolution: .mx.effective.yaml

Problem: Inheritance chains can be deep (child → parent → grandparent → root)

Solution: .mx.effective.yaml files contain computed effective values: the final result after resolving complete inheritance chains.

Think of it like CSS computed styles:

  • .mx.yaml.md = authored styles (what you write)
  • .mx.effective.yaml = computed styles (what the browser sees)

How Inheritance Works

Parent (/.mx.yaml.md):

audience: ["both"]
primaryLanguages: ["javascript"]

Child (/scripts/.mx.yaml.md):

inherits: "../.mx.yaml.md"
audience: ["humans"]
primaryLanguages: ["bash"]

Effective (/scripts/.mx.effective.yaml):

# Generated automatically - DO NOT EDIT
audience:
  - both        # From parent
  - humans      # From child (merged)
primaryLanguages:
  - javascript  # From parent
  - bash        # From child (merged)

Inheritance Rules

  1. Scalars: Child overrides parent

    # Parent: title: "Parent Title"
# Child:  title: "Child Title"
# Result: "Child Title"

  2. Arrays: Merged and deduplicated

    # Parent: tags: ["api", "rest"]
# Child:  tags: ["graphql"]
# Result: ["api", "rest", "graphql"]

  3. mx: section: Child replaces parent entirely (no deep merge)

    # Parent: mx: { ai: { assistance: welcome } }
# Child:  mx: { domain: "build" }
# Result: { domain: "build" }  # Parent mx: section discarded

  4. Repository Boundaries: Inheritance stops at git submodule boundaries

The Onboarding Workflow

MX repositories use a 7-step onboarding process (npm run mx:onboard):

  1. Generate .mx.yaml.md files (folder classification)
  2. Install pre-commit hooks (validation)
  3. Add npm scripts (mx:generate, mx:validate, mx:enhance, mx:effective)
  4. Update documentation (README, CLAUDE.md)
  5. Enrich metadata from README (extract description, keywords)
  6. Compute effective values (generate .mx.effective.yaml files) ← NEW
  7. Validate setup (check all files are valid)

Step 6 Implementation:

File: mx-effective.cjs

Key algorithm:

function resolveInheritanceChain(dirPath) {
  const chain = [];
  let currentPath = dirPath;

  // Build chain from child to root
  while (true) {
    const metadataPath = path.join(currentPath, '.mx.yaml.md');
    if (fs.existsSync(metadataPath)) {
      chain.unshift({ path: metadataPath, data: extractYamlFrontmatter(metadataPath) });
    }

    const parentMetadata = findParentMetadata(currentPath);
    if (!parentMetadata) break;
    currentPath = path.dirname(parentMetadata);
  }

  // Merge chain (parent → child)
  return mergeMetadata(chain);
}

Features:

  • Respects git repository boundaries (stops at .git files)
  • Skips "output" and "outputs" folders (no-inherit policy)
  • Tracks missing .mx.yaml.md files (inheriting from parent)
  • Generates .mx-missing.log report

Why separate effective values?

  1. Performance: AI agents read one file instead of traversing inheritance
  2. Clarity: See final values without mental computation
  3. Debugging: Compare authored vs. computed values
  4. Automation: Build tools use resolved values directly

When to regenerate:

# After editing .mx.yaml.md files
npm run mx:effective

# Check what would change
npm run mx:effective:dry-run

  • Design for Both: Single system serves humans and machines
  • Size-Neutral: No file counts (descriptions don't break when files added/removed)
  • Context Preservation: Explicit relationships between folders
  • Machine-First: But humans benefit from documentation

This metadata system IS part of MX OS: it demonstrates how machine-readable structure improves human understanding.

The MX Graph: Making Metadata Navigable

Individual .mx.yaml.md files describe individual folders. Cog files, which carry the COG (Community Owned Governance Standard), describe individual documents. The MX graph connects them into a single queryable structure.

The graph builder scans every .mx.yaml.md and .cog.md file across the MX repositories, resolves inheritance chains, and outputs a JSON graph to ~/.mx/graph.json. Each folder becomes a node. Each cog becomes a node. Relationships between them become edges.

Five edge types capture the structure:

  • inherits: a folder inherits metadata from its parent .mx.yaml.md
  • contains: a parent folder contains a child folder
  • buildsOn: a cog depends on another cog (the builds-on graph from the cog specification)
  • derivedFrom: content originated from another source (upstream provenance)
  • publishedTo: content is published to a destination, which may be a path or a URL (downstream provenance)

Lineage fields make provenance explicit. Any .mx.yaml.md or .cog.md file can declare derivedFrom and publishedTo in its mx: block:

mx:
  derivedFrom: mx-canon/mx-maxine-lives/communications/blogs/md/
  publishedTo: https://allabout.network/blogs/mx/

The graph resolves these into edges, enabling full lineage tracing from authoring source to published destination. An AI agent can ask "what is the source of this blog?" and follow the derivation chain back to the original markdown in the brain. Or ask "where does this content end up?" and follow the publication chain forward to the live URL.

What the graph enables:

  • Querying: find all active cogs, all folders in a domain, all content tagged with a topic. Query by any metadata field: status:active, domain:mx-core, tags:manual, folderType:content.
  • Dependency tracking: for any cog, see what it builds on (upstream) and what depends on it (downstream). This is the builds-on graph from the cog specification, made queryable.
  • Lineage tracing: follow derivedFrom/publishedTo chains across repositories. Trace content from authoring directory through processing pipeline to published URL.
  • Validation: detect missing required fields, deprecated patterns, and broken references across every metadata file simultaneously.
  • Orphan detection: find directories without .mx.yaml.md files. These are gaps in the metadata layer.
  • Staleness detection: identify nodes not modified within a threshold, surfacing content that may need review.

The graph is exposed through three interfaces: a command-line tool (mx graph query "status:active"), npm scripts (npm run mx:graph), and an MCP server that makes the graph directly queryable from AI agent conversations. The MCP integration means an AI assistant working in a repository can query the graph without leaving the conversation, asking about dependencies, tracing lineage, or checking validation status in real time.

The graph does not add new information. Every fact it contains already exists in the .mx.yaml.md and .cog.md files. What the graph adds is navigability: the ability to traverse relationships that span the entire filesystem, resolve inheritance chains that cross directory boundaries, and answer questions that no single metadata file can settle alone.

This is the MX OS filesystem made queryable. The metadata was always there. The graph makes it a network.

What This Process Built: The Cog System

The process described above went on to produce something nobody planned.

The Problem the Process Revealed

The Investigate-Interview-Iterate-Document pattern, applied to the question "How do AI agents actually read content?", surfaced a gap: there was no simple, universal format for machine-readable documents. AI agents scrape web pages, guess at meaning, and get it wrong. A documented developer command goes denied. A patient's drug-interaction check returns "no interactions" because the contraindications are written in prose paragraphs the parser flattens. The information is there. It was never structured for machines to parse.

What Emerged: Cogs

A cog is the atomic unit of MX: any document that carries MX metadata. In its canonical form, it is a markdown file with YAML frontmatter (.cog.md). An HTML page with Schema.org JSON-LD and <meta name="mx:*"> tags is also a cog. Machine-readable metadata in the native carrier format, human-readable content alongside. Any AI agent can parse it.

---
name: river-cruise-pricing
version: "1.0"
description: Pricing for 2026 Rhine river cruises
category: commerce
tags: [pricing, cruise, rhine, 2026]
audience: ai-agents
---

# Rhine River Cruise Pricing

Standard cabin: £2,030 per person.

The metadata tells the machine what the document is before it starts guessing. The format is deliberately simple: markdown and YAML. Every developer knows it. Every AI agent reads it.

Cogs as Programs

This appendix stated: "The MX documentation IS the MX Operating System." The cog system made that literal.

  • Info-cogs are the data files of MX OS, documents that describe themselves
  • Action-cogs are the programs, cogs with an execute block that define actions
  • The runtime is any AI agent, because every machine can read markdown and parse YAML
  • The Gathering specification defines the system API
  • The cog registry is the package index

The runtime: field in an action-cog's execute block works like a shebang line in Unix; it tells the system how to run the program. Runtimes include bash, node, python, and runbook (where the action-cog IS the instruction set and the AI agent IS the executor).

The Companion Web

Cogs solve the document problem. The companion web solves the web problem.

Every web page has two readers: the human and the AI agent. The companion web adds structured metadata to HTML so both get what they need from the same URL:

<meta name="cog:name" content="river-cruise-pricing">
<meta name="cog:description" content="Pricing for 2026 Rhine river cruises">
<link rel="cog" href="/cogs/river-cruise-pricing.cog.md">

Metadata in the HTML head, like OpenGraph, but for AI agents. No new infrastructure. No API. Just HTML tags that any web server already supports.

QR codes on physical objects point to companion web pages. A machine scans a product and knows what it is: not from a database, not from computer vision, but because the object describes itself. This extends to robotics: warehouse robots, delivery systems, any physical machine.

Both Directions

The companion web is the world speaking to the machine. The personal cog is the person speaking to the machine.

A personal cog is a collection of cogs on the user's device: accessibility needs, interests, dietary requirements, health, skills. The user's AI agent controls what gets shared. A restaurant gets the dietary cog. A hospital gets the health cog. Nobody gets everything. It decides.

Each personal cog also declares how far it may travel. The personal profile, set out in section 22.AG of the Index of Metadata, gives every personal cog a disclosureTier (private, derived or guarded), names the identity that holds it, and records whether its earlier versions are kept or scraped. The agent honours the tier before any sharing rule.

The companion web is the world speaking cog. The personal cog is the person speaking cog. The machine reads both sides. That is the Machine Experience.

The Gathering

The cog specification is part of MX, which CogNovaMX stewards and publishes under the MIT licence. It is to be donated to The Gathering, an independent standards body on the W3C model, which will then govern it. Anyone may implement it now and build products on it.
