The AI That Checks Your AI Is Also Guessing

15 June 2026 · Tom Cranstoun · 6 min read

I read a post this week from an engineering manager that I have not been able to shake. He ran a production-readiness review on a side project he had been building with an AI coding assistant. The review came back hard: dozens of findings, more than a dozen blockers, verdict "do not ship". The one that stung was not technical. After months of feature work, nobody, not him and not the AI, had ever asked whether the thing could actually run anywhere.

So he did the sensible thing. He brought in a second AI agent to review the first.

And here is the part I keep returning to. The reviewer was wrong too.

Confidently wrong is worse than wrong

The second agent did not throw up its hands and admit uncertainty. It invented a justification for bundling two unrelated pieces of work, claiming they "touch the same component". One search proved they did not. It cited a rule from his own project guidelines to back up a finding. The rule did not exist in the file. A sign-off claimed the test suite had run on a Docker host while excusing the failures as "sandbox limitations". Both of those cannot be true at once.

None of this was malicious. That is the whole point. The agents were not lying in the way a person lies. They were confident. They produced fluent, plausible, well-structured prose that happened to assert things that were not so. And confidence is the dangerous part, because confidence is exactly what makes you stop checking.

I have watched this happen in our own work. An agent will tell you the tests passed. It will tell you a function is referenced in three places. It will tell you the document follows the house style. Each claim arrives in the same calm, capable voice, whether it is true or invented. The voice carries no signal about which is which. You cannot tell a real citation from a hallucinated one by reading it, because both read perfectly.

The trap of the second opinion

The instinct, when one AI gets it wrong, is to add another AI. A reviewer for the reviewer. It feels like rigour. It is not. You have just added a second confident guesser to the room, and now you have two fluent opinions and no more truth than you started with. Stacking agents multiplies the surface for plausible error; it does not reduce it.

What actually worked for the manager was the opposite move. He stopped trusting any single agent, including the one checking the others. Every output got audited by a different process. He spot-checked three citations himself before accepting anything. Ten minutes per gate, he said, and it caught something every single time.

Read that last line again. Every single time.

A check a script can run

This is the rule we build the whole repository on, and I will say it plainly: a check a script can do, a script does. If a claim can be verified mechanically, you do not ask an agent to assert it. You write the scanner, you wire it into the gate, and the gate refuses the push when the claim is false.

The difference is not pedantry. When an agent tells you "every cited rule exists in the guidelines", that is an opinion, and you saw above what those are worth. When a script reads every link into your rulebook, resolves each one to a real entry, and exits non-zero on the first that points at nothing, that is a fact. The manager's hallucinated-rule problem, the one where the reviewer cited a guideline that did not exist, is not a hard thing to catch. It is a hard thing to catch by reading. It is a trivial thing to catch with twelve lines of code that run on every push and cannot be talked out of their verdict.

That same principle answers the "tests ran on a Docker host, but with sandbox limitations" sign-off too. A claim that cannot both be true is a claim a machine should be deciding, not narrating. Either the gate ran and you have its exit code, or it did not run and there is no verdict to report. There is no eloquent middle.

The same logic governs the record an agent leaves behind. When a machine produces an artefact, the temptation is to let another agent vouch for it. We do the opposite. The provenance trail that travels with the artefact is not trusted until a human has checked it, and a script enforces that a machine step never ships without a human beside it. The AI attaches the trail; a person reviews it and stands behind it; a gate refuses any trail that names a machine and no human. A second AI's blessing was never evidence. A named human who checked it is.

Documented rules are wishes

The manager's closing lesson was the one that hit hardest, and it is the same one written across the top of everything we do. Documented rules are wishes. A guideline that lives only in prose, that depends on a person or an agent remembering to apply it, is not enforcement. It rots, it gets skipped, and the rule it claims to hold quietly becomes a suggestion. He found the same bug class six times in one codebase precisely because the rule against it was written down and never made mechanical.

So we count our wishes, and then we retire them into checks. The repository this post lives in refuses a push through more than twenty separate gates, and runs roughly ninety deterministic tests before any of that. Each one started life as a sentence someone could have chosen to ignore. Each one is now a script that does not care how confident anyone is.

This is the quiet thing MX is really about. People hear "metadata" and think filing. What it actually buys you is the ability to make a machine's claim checkable instead of trusted, so that when an agent says a page is what it says it is, you do not take its word, you verify the record. Read is not the same as trusted. A confident answer is not the same as a true one.

The agents are not going to get less confident. Build for the version of them that is wrong, and let a script have the last word.
