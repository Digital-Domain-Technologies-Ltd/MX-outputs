Skills Don't Travel

18 June 2026 · Tom Cranstoun · 7 min read

There is an old story type -- the monkey's paw, the genie's three wishes -- where a request is granted exactly as worded and catastrophically against intent. You wish for a million pounds and it arrives as a life-insurance payout. You ask for eternal life and get it without eternal youth. The instruction was followed precisely. The outcome was not what you wanted.

AI agents do this too. Not maliciously. They follow the instruction they were given, in the context they were given it, as literally as they can. The problem is almost never the agent. It is the instruction.

But there is a second problem that gets less attention. Even when you write a good instruction -- clear, bounded, safe -- it only works for the tool you wrote it for.

I hit both problems in the same afternoon. That afternoon is the reason this standard exists.

Seven formats in one repository

I was setting up operating rules for AI agents working in this repository. Rules like: always compute link depth correctly before writing a markdown file. Never hardcode credentials. Never edit outside your declared output boundary. The rules themselves are simple. Enforcing them across tools is not.

Here is what the tool landscape looks like in a single repository in 2026:

Tool Boot file
Claude Code CLAUDE.md
Cursor .cursor/rules
GitHub Copilot .github/copilot-instructions.md
Windsurf .windsurfrules
Continue .continue/config.md
Gemini CLI GEMINI.md
OpenAI Agents AGENTS.md

Seven formats. None compatible. A rule written for Claude Code does nothing in Cursor. A .windsurfrules file is invisible to Gemini CLI. If I want the same link-depth rule enforced across all seven tools, the naive approach is: write it seven times. Then remember to update it in seven places every time it changes.

That is not a workflow. That is a maintenance burden that will quietly become seven drifting versions of the same rule, and the agent that happens to be running the day a rule has drifted will do the wrong thing -- precisely, faithfully, as instructed.

What you are actually trying to do

When you write a rule for an AI agent in a repository, you are doing one of two things.

Describing a process -- "here is how to check link depth, fix wrong links, and stage the result." That is information. It should be readable by any agent, not just the one that happened to be running today.

Constraining behaviour -- "do not write files outside datalake/. Do not run this on a partial checkout. Always confirm before committing." That is policy. It should be enforceable by any capable agent, because policy that only applies to one tool is not really policy -- it is a suggestion to your current vendor.

Both are documentation problems, not tool problems. The information and the constraints belong in the repository, in a format any capable reader can understand.

The solution is not to write seven files

The solution I built is a single COG -- scripts/cogs/mx-agent-rules.cog.md -- that contains every invariant operating rule for any agent working in this repository. The seven tool-specific files each contain exactly one instruction: read the COG first, and apply what it says.

CLAUDE.md  ──────────────────────────────┐
GEMINI.md  ──────────────────────────────┤
AGENTS.md  ──────────────────────────────┤
.windsurfrules  ─────────────────────────├──► scripts/cogs/mx-agent-rules.cog.md
.cursor/rules  ──────────────────────────┤        (the only place rules live)
.github/copilot-instructions.md  ────────┤
.continue/config.md  ────────────────────┘

Each adapter is ten to fifteen lines: what the repository is, where the rules live, which document wins on conflict. No rules are duplicated. When the link-depth formula changes, I update the COG once. Every tool that boots into this repository next picks up the change.

The document does not need to know which tool will read it

There is one more problem to solve. If the rule document names Claude Code or Cursor specifically, it is no longer runtime-agnostic -- it has just hidden the coupling in a different place.

The solution is a x-mx-runtimeProbe block in the COG's frontmatter. It lists the environment signals that identify each known runtime, in priority order:

x-mx-runtimeProbe:
  instruction: "Work through these signals in order. First match is your identity."
  signals:
    - env: CLAUDE_CODE_VERSION
      identity: claude-code
    - env: CURSOR_SESSION_ID
      identity: cursor
    - env: COPILOT_AGENT
      identity: github-copilot
    - env: WINDSURF_SESSION
      identity: windsurf
    - env: CONTINUE_SESSION_ID
      identity: continue
    - env: GEMINI_CLI_VERSION
      identity: gemini-cli
    - fallback:
      identity: unknown-agent
      action: flag-and-continue

The COG never names a tool in its rules. Instead, it says: probe your environment, identify yourself, then look up the notes column of the rules table for anything that applies to your identity specifically. The universal rules apply regardless.

This is runtime-agnostic in the strongest sense. The document does not assume which tool will read it. The tool identifies itself by reading the document.

Why the pre-web analogy is exact

Before HTML, your Word document could not be opened in WordPerfect. Your Lotus 1-2-3 spreadsheet was stranded when you moved to Excel. Content and tool were fused. HTML broke that coupling. The document declared what it was. Any browser could render it.

AI tooling is at exactly the pre-HTML moment. Every tool has invented its own skill file format. None are compatible. The content -- your hard-won instructions, the constraints you refined over months, the process knowledge encoded in a good skill -- is stranded on the tool you happened to be using when you wrote it.

COGs are the HTML moment for agent instructions. A COG declares what it is and what an agent should do with it. Any capable agent can act on it. The format wins when it is portable, not when any one tool is better.

The cost is hidden until it isn't

With one AI tool and one workflow, runtime-specific skills look fine. The cost is invisible.

The cost appears when:

  • You switch tools. Migration cost: rewrite all your skills from scratch.
  • You use multiple tools in the same repository. Coordination cost: keep N formats in sync indefinitely.
  • A tool is acquired or deprecated. Stranded cost: all your skills are worthless.
  • You need an audit trail of what an agent was authorised to do. Compliance cost: the authorisation lived in a vendor config, not in the repository. It is not version-controlled, not reviewable, not verifiable.
  • A colleague uses a different tool. Collaboration cost: you cannot share the skill set.

None of these are edge cases. They are the normal trajectory of any team that uses AI tooling over a multi-year horizon.

The instruction should outlast the tool

A good rule file is valuable. It encodes judgment -- when to run a check, what to verify first, where the boundaries are, what constitutes done. That judgment is hard-won. It should not be stranded when your tooling changes.

The seven-format problem in this repository took one afternoon to solve. The adapter files took minutes to write. The COG -- the actual rules -- took longer, because writing rules that are correct takes time and thought. That is as it should be. The thinking belongs in the document. The document belongs in the repository. The repository belongs to no vendor.

Write your rules as COGs. Let the document travel with the repository, not with the tool.

This is also why we need MX as a machine understanding standard, not just as a practice. A standard gives the x-mx-runtimeProbe block a stable meaning that every tool can implement without central coordination. Without the standard, every tool has to agree bilaterally on every convention. With the standard, the document declares itself and any conformant reader knows what to do.

That is the lesson seven boot files taught in one afternoon.

MX COGs are documented at tg.community. The action-doc specification is part of the MX Cogs draft note. The mx-agent-rules.cog.md and adapter files described in this post are in the MX-hub repository.
