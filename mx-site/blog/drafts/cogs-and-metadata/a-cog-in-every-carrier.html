A Cog in Every Carrier: Your Scripts, PDFs, and Images Carry MX Too

19 June 2026 · Tom Cranstoun · 6 min read

When people hear "metadata" they picture a block of YAML at the top of a markdown file. That picture is too small, and it quietly excludes most of what an agent actually meets. The file in front of a machine is just as likely to be a PDF, a PNG, or a shell script as it is to be markdown. If metadata only lives at the top of .md files, every other file an agent opens is a stranger.

So here is the rule I keep coming back to: a cog is defined by the metadata it carries, not by its file extension. A markdown file with frontmatter is a cog. A plain text file with frontmatter is a cog. And a file that is not text at all can be a cog too, because every carrier has somewhere native to put the declarations.

Every format already has a place for it

Think about where the metadata goes, carrier by carrier.

An HTML page carries it in the <head> - either <meta name="mx:..."> tags or a comment that holds the source declarations verbatim. The page body is the content; the head says what the page is.

A shell script carries it in a comment header at the top, a small fenced block of # key: value lines before the code starts. The script body is what it does; the header says what it is and who may run it.

A PDF carries it in its XMP packet, the same metadata channel Adobe defined years ago and that sits inside the file itself (see the XMP specifications). The pages are the content; the packet says what the document is, who is accountable for it, and what conformance it claims.

An image carries it the same way - XMP for raster formats, an SVG <metadata> element for vector, or a small sidecar file alongside it when the format cannot hold the fields. The pixels are the content; the metadata says what the asset is and how it may be reused.

In each of these, the non-prose part is the equivalent of a markdown body. The HTML body, the script, the PDF pages, the image itself - that is the content. The metadata is the briefing that travels with it.

Why this matters the moment the file travels

A file rarely stays where it was made. It gets fetched, attached, downloaded, passed to an agent, dropped into a folder far from the page or pipeline that produced it. When it lands somewhere new, the surrounding context is gone. All that is left is the file.

If the file carries its own declarations, the machine that meets it is not guessing. It reads what the file is, who it is for, where it lives, and what it is safe to do with it - and it reads that the same way whether it opened a markdown file, a PDF, or a script. The declarations do not depend on the format. They depend on the file having brought them along.

That is the whole point of putting metadata in the native carrier rather than in a separate database or a companion web page. The database is somewhere else. The web page is somewhere else. The file is here, in the machine's hands, and the answer travels inside it.

The objection: borrowed vocabulary, awkward carrier

There's a fair objection buried in all this, and it's worth answering rather than stepping around.

Good metadata practice says borrow rather than invent. If an established vocabulary already names the author of a thing, use it, don't coin your own. But the best-known of those vocabularies is usually met as a block of JSON-LD inside a web page, and a shell script has no head section to put it in. A log line has nowhere for a script block. So the advice appears to hold only for the carrier the vocabulary grew up in, and to abandon you everywhere else.

The objection dissolves once you separate what's easy to conflate. A vocabulary is a set of terms and their meanings. A syntax is one way of writing them down. JSON-LD is a way of writing; it isn't the meaning. Nothing about the term for authorship requires angle brackets.

A shared context moves the meaning across formats: one published mapping from the names a file uses to the addresses those names mean. Declare the mapping once, and every carrier only has to hold plain key-and-value text.

That turns out to be something every format can already do. YAML front matter has a linked-data form on the standards track, so the block at the top of a markdown file can be both a human-readable header and a machine-readable island of meaning. A web page keeps its familiar script block. Strip the comment marks from a shell header and the same YAML sits underneath. And the metadata packet inside a PDF or an image was linked data from the beginning: an address drops straight in, with no adapter and no translation.

Where a format has room for structure, it holds meaning. Where only a line of text fits, an address goes in instead and resolves to the rest. That floor never fails, because a link is only a short string of characters, and no format struggles with one of those.

The trade is honest and worth naming. Borrowing someone else's vocabulary means inheriting their release schedule: when they change a definition, you absorb it. Keeping your own names avoids that and costs you the shared meaning. It's a real decision, not a free lunch, and it isn't one to make casually.

The principle underneath

This is Metadata Everywhere, applied without an exception for binaries. The visible artefact is for eyes - the rendered page, the printed PDF, the picture. The metadata behind it is for the machine - the agent, the validator, the screen reader, the parser. Both say the same thing about the file; they just speak to different readers.

Once you hold that, a useful property falls out. A system that keeps its metadata in every carrier can see every file it owns, whatever the format, and it can check and repair those declarations file by file. Nothing is invisible to it just because it is a PDF instead of a paragraph. The markdown cog is the richest form and the easiest to teach, but it was never the only one. The same identity, provenance, and usage belong on whatever file you are about to publish - in the language that file already speaks.
