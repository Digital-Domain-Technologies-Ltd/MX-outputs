The First COG: When a Registry Gets Its First Document

8 February 2026 · Tom Cranstoun and Maxine · 7 min read

The moment REGINALD went from "a registry" to "a registry with something in it."

Date: 8 February 2026 Author: Tom Cranstoun Co-Authored-By: Claude Opus 4.6 (Maxine)

Why this matters

Building a registry is easy. Populating it is the hard part.

For two years, REGINALD existed as specifications, architecture, pilot proposals, and grant applications. It had a URL. It had a signing engine. It had a name that made people smile. What it didn't have was a document.

Today it got one.

The first COG — Certificate of Genuineness / Contract of Governance — was created, given a home, and placed in the registry at allabout.network/cogs/mx-reginald/cog-system.cog.md.

That's a URL you can type. A document an AI system can fetch. A real thing in a real location with real metadata. The registry is no longer empty.

What is a COG?

I'd been calling REGINALD documents "COGs" for a while. Originally it stood for Contract of Governance — the accountability layer. Who maintains this document? How often? What triggers an update? Good questions. Important questions. But only half the story.

Maxine pointed out the gap. A governance contract tells you who's responsible, but it doesn't tell you whether the document is genuine. You need a trust layer too. Who published this? When? Can you verify it cryptographically?

So COG became a dual-meaning term:

Layer Full name What it proves
Certificate Certificate of Genuineness "This is real"
Contract Contract of Governance "This is maintained"

Every COG carries both. A COG without the Certificate is unverified. A COG without the Contract is ungoverned. Both layers are required for REGINALD registration.

The metaphor writes itself. A cog is a tooth on a gear. Remove one and the machine fails. AI systems need COGs — without them, they guess.

Where COGs live

This was the decision that made today significant. Not the format — we'd already defined that. The location.

COGs live at:

allabout.network/cogs/{client-id}/{subject}.cog.md

No dot-prefix. COGs are designed for both humans and machines — hiding them defeats the purpose. The MX motto is "Design for machines. Benefit humans. Advance both." Both audiences need to find these documents.

The directory structure:

cogs/
  .mx.yaml.md                         # Registry root metadata (MX metadata keeps its dot)
  mx-reginald/                         # Client: MX Reginald Ltd
    .mx.yaml.md                        # Client folder metadata
    cog-system.cog.md                  # The first COG
    cog-system.cog.mx.yaml.md          # COG document metadata

Four files. Three metadata files and one COG. The COG and the cogs/ directory are visible to everyone. The .mx.yaml.md metadata files keep their dot-prefix — they're MX system metadata, not documents for general consumption. Every level documented. If any file is lost, the metadata at the level above describes what should be there.

The first COG describes the COG system

Of course it does.

The first document registered in a verification registry is a document that explains how the verification registry works. What else would it be?

It covers:

  • What a COG is — the dual-layer format, the gear metaphor, the trust and accountability questions
  • How COGs work — three sections (Certificate Header, Governance Body, Content)
  • The lifecycle — Draft, Signed, Registered, Active, Review, Updated, Re-signed
  • Compliance levels — five tiers, from "YAML frontmatter present" to "independently audited"
  • The MX ecosystem — links to MX Holdings, MX Books (The Handbook, The Protocols), and MX Reginald

It's a draft. Status: unsigned, Level 2 compliance. The Certificate Header has signature: "unsigned" and verified: false. Honest about its own state. When the Signing Engine processes its first production document, this COG will be that document. It will sign itself.

A self-describing, self-signing, self-verifying document. If that's not MX in practice, nothing is.

The five compliance levels

This crystallised during the COG specification work. Not every document needs the same level of verification:

Level Certificate Governance Who needs it
1 YAML present Publisher identified Internal docs
2 MX-compliant structure Maintainer + contact Public docs
3 Cryptographically signed Review cycle + triggers REGINALD minimum
4 Signed + registered Full contract with SLA Commercial docs
5 Signed + registered + audited Third-party governance audit Regulated industries

Level 3 is the minimum for REGINALD registration. Level 5 is for healthcare, finance, legal — industries where a wrong answer doesn't just waste tokens, it harms people.

The first COG sits at Level 2. It's honest about that. It will be Level 3 when signed, Level 4 when registered, and it documents the path to Level 5 for others.

Full MX metadata

Tom teaches MX. I implement. That's the deal.

So when Tom said "full MX metadata", every level got an .mx.yaml.md file:

Registry root (cogs/.mx.yaml.md) — describes the directory structure, access rules, the API pattern for fetching COGs, links to the specification.

Client folder (mx-reginald/.mx.yaml.md) — identifies the publisher, lists founders, indexes all COGs in this client's folder, links to the company overview and grant application.

COG document (cog-system.cog.mx.yaml.md) — summarises the COG's content, records the author and co-author, defines update triggers, and includes a regeneration prompt. If the COG is deleted, Maxine can recreate it from this metadata file alone.

That last point matters. The .mx.yaml.md system was designed so that if a document is lost, the metadata contains enough information to regenerate it. The first COG in REGINALD follows this principle. The registry protects its own documents.

The recursive stack

Let's count the layers of self-reference in today's work:

  1. MX is the discipline of making documentation machine-readable
  2. REGINALD is a registry of machine-readable documentation, built using MX principles
  3. COG is the document format for REGINALD, defined in an MX-compliant specification
  4. The first COG describes the COG system, registered in REGINALD, following MX conventions
  5. The metadata for the first COG contains a regeneration prompt so an AI (Maxine) can recreate the COG that describes the system Maxine helped build
  6. This blog documents the creation of the first COG, and will itself eventually become a COG in the registry

Six layers deep. Each one genuine. Each one necessary. None of them contrived.

When your documentation system documents itself and the documentation about the documentation system is itself documented — you've either gone too far or you've got it exactly right.

I think we got it exactly right.

What this means for the grant application

Yesterday we built a 14-document grant application package targeting £250k+ from the Scottish Government. Today we created the first real artefact in the registry that the grant application describes.

Grant assessors can now visit allabout.network/cogs/mx-reginald/cog-system.cog.md and see an actual document in the actual registry. Not a mockup. Not a screenshot. A real COG at a real URL with real metadata.

The grant application says "the registry is live." Now there's a document in it to prove it.
