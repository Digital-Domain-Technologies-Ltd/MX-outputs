The Layer Beneath the System Prompt

14 June 2026 · Tom Cranstoun · 7 min read

I took the leaked Fable 5 system prompt and decomposed it into MX COGs. That post is about how well the structure fits.

This post is about what the structure misses.

Fable 5 is Anthropic's answer to one question: how should Claude behave in general? It's a good answer. 1,585 lines covering tone, refusal rules, tool definitions, knowledge cutoff, copyright compliance, memory state, and filesystem configuration. Comprehensive, well-structured, and leaked the day after the model launched.

My .claude/ folder is my answer to a different question: how should an agent behave in this specific codebase, on this specific quality standard, with these specific pipelines, under this specific governance regime?

That question can't be answered with a system prompt. It needs a different layer. And that layer is what MX does.

The difference between instructions and enforcement

Its tone section tells Claude: avoid over-formatting with bold emphasis, headers, and lists.

My pre-write-forbidden-vocab.sh hook runs a banned-word scanner against the proposed file content and blocks the write before it happens. The code comment explains the design decision:

This hook removes the reading-and-judging step from the path: it runs the scanner itself and fails closed, so a hard-banned word cannot reach disk no matter what the author did or did not read.

The difference is not subtle. One is a request. The other is a gate. A request reaches the model, which decides whether to honour it. A gate runs before the write; if it fails, the action doesn't complete.

Fifteen hooks in my .claude/ folder are blocking. pre-write-frontmatter.sh blocks any markdown write with invalid MX frontmatter. pre-write-html-hygiene.sh blocks HTML writes with hygiene failures. pre-bash-readonly.sh blocks writes to read-only submodule repos entirely. pre-bash-deterministic-tooling.sh blocks throwaway in-place mutations and directs the agent to save a script instead.

A system prompt, no matter how detailed, can't do this. It can ask. It can't block.

The difference between memory and state

Its memory section reads: "Claude has no memories of the user because they haven't enabled it in Settings."

That's accurate. It's also the only option available when memory is on the model provider's platform.

My session-memory-hydrate.sh hook runs at every session start. It merges the repo-tracked memory store from .claude/memory/ with the device-local cache, newest-wins, tombstones honoured. session-uber-plan.sh loads the active project plan into context. session-index-trust.sh sets the index trust state. After every write, post-write-memory-sync.sh writes new memory back to the repository.

The capture is deliberate, not incidental. Write a memory in one session - a fact established about this codebase, a correction I made - and it is folded into the repo-tracked store at the write boundary and hydrated back at the next session start. Each machine keeps its own working copy, and the two reconcile by a deterministic merge: union by file, newest stamp wins, deletions carried as tombstones, so two operators on two machines converge instead of clobbering each other. Memories meant to be shared are typed to travel; private ones stay on the device. And it is gated - a pre-push check refuses to let the repository and the device drift apart - so the shared memory is trustworthy, not best-effort.

The agent starts from where the project actually is, not from a blank slate. That state is in version control. It travels with the repository. A new team member gets the accumulated project memory on their first clone.

No system prompt can do this. Memory on the model provider's platform belongs to the provider. Memory in your repository is yours.

The difference between a tool list and a routing system

Fable 5 lists fifteen available tools. There's no routing logic. No way to find the right document for a task.

My proactive-cog-beacon.sh hook scores every incoming prompt against the full COG registry using trigger, tag, name, and description matching. If a relevant action-doc scores strongly, it injects a soft advisory before the model responds. run-cog-enforcer.sh handles hard intent detection and resolves the exact COG file from the registry. cog-authoring-gate.sh intercepts authoring intent and injects the how-to-write-a-cog.cog.md authority before the model guesses at the structure from training data.

The system finds the right document before the first token of response. A system prompt can't do this because it doesn't know what documents exist in your specific codebase.

The difference between documentation and provenance

Fable 5 has no concept of provenance. The word does not appear in 1,585 lines.

My pre-commit-provenance-sidecar.sh hook scans every staged artefact under mx-outputs/ at commit time. For any file without a sidecar, it auto-generates a .provenance.ai.json and stages it alongside. The evidence chain lands in version control as part of the commit. post-write-metadata-transfer.sh verifies that artefacts carry their source MX metadata through the pipeline as they are transformed from markdown to HTML to PDF.

This is evidence that travels with what was produced, not a record of what happened. Auditors can verify it. Regulators can query it. The model provider does not hold it.

Anthropic's controversial 30-day data retention policy on all Fable 5 and Mythos 5 traffic exists because they have no equivalent mechanism. The evidence that their system is making good decisions has to live somewhere. They chose the API log. The right answer is the artefact.

The difference between a fixed prompt and a learning loop

Fable 5 is the same 1,585 lines for every session. It does not learn that this codebase keeps tripping over the same mistake, because it has no memory of the codebase and no mechanism to mine one.

My dream skill does exactly that. It reads the project's own Claude Code session transcripts, finds the mistakes that recur (a cd to a relative path after the Bash working directory has drifted, an Edit with no preceding Read), and classifies them with a local Ollama model. Nothing leaves the machine. The output is a findings catalogue and a human-readable report.

Here is the part that matters: Dream recommends, it does not act. It writes only inside datalake/dream-files/. It never edits LEARNINGS.md, never touches a cog, never changes the rulebook on its own. I read the report and decide what graduates into a permanent rule. The machine mines; the human commands. That is Human-in-Command, and it is the line a self-improving system has to hold: the loop that proposes is never the loop that promotes.

A system prompt cannot mine its own history, and a model platform that could would hold the evidence on its side, not yours. The learning loop belongs in your repository, on a local model, writing to a bounded area you control.

The question system prompts cannot answer

Fable 5 is a general-purpose instruction document. It governs how Claude behaves when talking to anyone, about anything, on any platform. That's a hard problem and Anthropic has put serious thought into it.

But "how should an agent behave on your codebase, with your quality standards, in your governance regime" is a different problem. It's per-operator. It's per-context. It's per-domain. No model provider can answer it for you, because they don't know what your codebase contains, what your quality standards require, what your pipelines do, or what governance obligations you operate under.

The answer to that question needs to be:

  • Written by the operator, not the model provider
  • Enforced mechanically, not aspirationally
  • Versioned alongside the work it governs
  • Portable across model providers, not locked to Claude or any other vendor
  • Governed by an open standard, not a commercial API contract

That is what MX OS does. The .claude/ folder is MX running live, in a real codebase, governing a real agent's behaviour in a real production context. Every blocking hook, every session-start hydration, every provenance sidecar, every post-write sync is the architecture operating as designed.

The system prompt tells the agent what to do.

MX is the layer that makes sure it does it.
