The Repo Now Knows Who Is In The Room

15 June 2026 · Tom Cranstoun · 4 min read

I run multiple Claude Code sessions at the same time. A primary session working on content, a background session running a web audit, sometimes a forked agent finishing off a documentation task while I get on with something else. It is a natural way to work when the agent is capable enough to own a task end to end.

The problem is that all of those sessions were writing to the same repository directory. Same main branch. Same working tree. Git is brilliant at resolving divergence at commit time, but at write time it just saves the file. If two sessions both open the same markdown file and write to it within the same minute, the last one wins. Silently. No warning, no conflict marker, just the first session's work gone.

I hit this in practice. The fix is obvious once you say it out loud: give each session its own working directory.

What a git worktree is

Git's worktree feature lets you check out multiple branches from the same repository simultaneously, each in its own directory. They share the git history and object store, but each has its own working files and its own branch. You can have five sessions open against five different branches, all in separate folders, all committing independently, and git will merge them correctly when you bring the branches back together.

It is not a new feature - it has been in git for years. I just had not wired it into the repo's workflow.

Session start, session close

I added two scripts to the repo.

npm run session:start creates a worktree for you. It picks today's date and an auto-incrementing letter suffix (A, B, C...), creates a branch called feature/session-20260615-A, and puts the worktree at .claude/worktrees/session-20260615-A. It prints the path and the close command. Open that folder in Claude Code. Everything you do in that session stays in that directory and on that branch.

npm run session:close -- session-20260615-A does the reverse. It checks for uncommitted changes (blocks if there are any - commit first), merges the session branch back to main with --no-ff so the session history stays readable, then removes the worktree and the branch. It also offers to regenerate the estate indexes if the environment qualifies for that.

npm run session:list tells you what is currently open.

Two things to know before you close

Gate 22. The repo has a gate that checks whether any published blog post source in datalake/draft-site/blog/ was edited since the corresponding HTML was last generated. If you edit a published post in your session, you need to republish it (npm run promote) and commit the result before closing. Otherwise the gate fires when you push.

Index regeneration stays on main. The generated indexes - the routing registry, the documentation map, the cog registry - can only be regenerated on a fat clone of main with all submodules present. A session branch refuses to run the regenerators, which is correct: a partial or off-branch index is worse than a stale one. After session:close merges your work to main, run npm run index:regen there if you edited sources the indexes read from.

Why this matters beyond just not losing work

The worktree pattern makes the repo's concurrency explicit. Before this, the repo had no model of "more than one operator at a time" - it assumed a single writer and the Gates were designed accordingly. Now there is an actual mechanism: each session declares itself at start, commits to an isolated branch, and declares itself done at close. Merge conflicts become visible at the merge step, where git can describe them, rather than silent at the write step, where the last file save wins.

The repo knows who is in the room. That is how it should work.
