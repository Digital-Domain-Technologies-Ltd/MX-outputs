Agent Harness: Witnesses

5 July 2026 · Tom Cranstoun · 4 min read

This is the fourth post in the series. Previous posts covered parsing, annotations, and fingerprints. This one covers witnesses - the most structurally distinct handler in the MX harness.

Every other handler calls one function and checks the result. The witness handler runs a sequence: sign a cog, optionally modify it, then verify. The verification outcome depends on what happened between signing and checking. That makes witnesses the only handler where order matters and where the case drives conditional behaviour mid-sequence.

What witness cases test

A witness is a signed record that a cog's contract satisfied a set of validators at a point in time. Signing produces a witness document. Verification reads that document and re-runs the validators against the current cog to confirm the contract has not changed.

The harness tests two outcomes: a cog that has not been modified since signing should verify successfully; a cog where the contract has changed should not.

An unmodified case:

case-id: witnesses-001
case-name: A signed cog verifies successfully when unmodified
spec-references:
  - "section 6.1"
input:
  type: cog
  content: |
    ---
    title: Witness test
    description: Will be signed and verified.
    schema: urn:mx:schema:basic
    ---
    Body text.
  tamper: false
expect:
  outcome: success
  verify-outcome: valid

A tampered case:

case-id: witnesses-002
case-name: A cog with a modified contract does not verify
spec-references:
  - "section 6.3"
input:
  type: cog
  content: |
    ---
    title: Witness test
    description: Will be signed and then modified.
    schema: urn:mx:schema:basic
    ---
    Body text.
  tamper: true
  tamper-field: schema
  tamper-value: urn:mx:schema:altered
expect:
  outcome: success
  verify-outcome: invalid

The tamper flag tells the handler to modify the cog between signing and verifying. tamper-field and tamper-value specify what to change. Changing the body text, by contrast, should not invalidate the witness - that is the asymmetry the system is designed around.

The handler

async function runWitnessesCase(testCase) {
  const { input, expect } = testCase;
  if (input.type !== 'cog') return skip(`input type ${input.type} not handled`);

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    return fail(`cog did not parse: ${err.message}`);
  }

  let witness;
  try {
    witness = await signContractSatisfaction(parsed);
  } catch (err) {
    return fail(`signing failed: ${err.message}`);
  }

  let subject = parsed;
  if (input.tamper && input['tamper-field']) {
    subject = {
      ...parsed,
      frontmatter: {
        ...parsed.frontmatter,
        [input['tamper-field']]: input['tamper-value']
      }
    };
  }

  let verifyOutcome;
  try {
    await verifyWitness(subject, witness);
    verifyOutcome = 'valid';
  } catch (err) {
    verifyOutcome = 'invalid';
  }

  const expected = expect['verify-outcome'];
  if (verifyOutcome === expected) return pass();
  return fail(`expected verify-outcome "${expected}", got "${verifyOutcome}"`);
}

Each step is wrapped separately. A signing failure is a different kind of problem from a verification failure, and the error message should say which step broke.

The tamper step modifies the parsed cog in memory - it does not rewrite the source text. That is sufficient because verifyWitness takes the parsed object, not the raw content. If your implementation verifies from raw text, the tamper step would need to reconstruct the content string instead.

The asymmetry the cases encode

The MX system distinguishes contract changes from body changes. A contract change - modifying a schema reference, adding or removing a validator - invalidates the witness. A body change - editing the prose - is recorded as drift but does not invalidate.

The conformance cases encode both sides of that distinction. A case with tamper-field: schema and verify-outcome: invalid checks that contract changes are caught. A case with tamper-field: body and verify-outcome: valid checks that body changes are not treated as invalidating.

Without both cases, an implementation that rejected everything after any change would pass the first case and fail the second. Both poles of the test space need to be present.

Why this handler is async

signContractSatisfaction and verifyWitness are both async because signing in the reference implementation involves cryptographic operations (Ed25519 over RFC 8785 canonical JSON). The harness dispatcher marks the witnesses case as await runWitnessesCase(testCase) to handle this. Parsing, annotations, fingerprints, and validators are all synchronous in the reference implementation; only witnesses requires async.

If your implementation signs synchronously - because you are using a different key type or a mock signing function in tests - you can remove the async/await from the handler. The case format does not change.
