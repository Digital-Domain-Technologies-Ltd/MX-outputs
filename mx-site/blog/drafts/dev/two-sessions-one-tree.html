Two Sessions, One Tree

2 July 2026 · Tom Cranstoun · 7 min read

This week, two of my Claude Code sessions met in the middle of the same file.

One of them was repairing a metadata field across ninety-one blog sources, a careful batch fix with its own verification step. The other was renaming a path inside the frontmatter of the same files. Both sessions were doing exactly what I'd asked. Neither knew the other existed. The batch fix applied cleanly, then the verification step reported edits in more than two hundred files, and I spent the rest of the afternoon doing line-level surgery: keeping the second session's changes while backing the first session's out of the files they'd both touched.

Nobody misbehaved. Both sessions shared one working tree, and that was the whole problem.

Why Sharing a Working Tree Fails

Every Claude Code session you open the ordinary way works in the same checkout. Two tabs in the editor share it. A session in the terminal shares it too. Git copes fine with many writers once work is committed; what it cannot referee is two sets of uncommitted changes landing in the same files at the same moment. One session stages, another edits, and by the time either of them looks, the diff underneath has moved.

I had rules for this. Stage by explicit path. Push before switching sessions. Never git add -A. Good rules, and I'd have quoted them to you five minutes before the collision. Rules held in memory fail exactly when you're deep in something else, which is the only time you run several sessions in the first place.

That's the same lesson we apply to content in MX work: a check a person has to remember is a check that will be skipped. If a machine can verify something, the machine should be the one verifying it. It took a wrecked afternoon to make me apply my own rule to my own working practice.

Worktrees Give Each Session Its Own Copy

The isolation mechanism already exists in git, and Claude Code has it built in:

claude -w              # new session in its own worktree, auto-named
claude -w audit-fixes  # same, with a name you chose

A worktree is a second working copy of the same repository: shared history, separate files. Each session started with -w gets its own copy under .claude/worktrees/ and its own branch, named worktree-<name>. Two sessions in two worktrees cannot collide, no matter what either of them does, because there is no shared file for them to fight over. When the session ends, an untouched worktree removes itself; one with real work asks whether to keep it.

The whole fix costs one flag. That's the part that stung most in hindsight.

One Primary Session, Everything Else Isolated

The pattern I've settled on has a single rule at its centre: one session owns the real checkout, and it's the only one that does.

The primary session handles anything that touches shared state: publishing, pushing, coordinating work that spans repositories. It's the session I'd point at the messy jobs. Every other session, the quick question, the parallel draft, the background refactor, starts with claude -w and works in its own copy. Their commits land on their own branches, and they merge back the way any branch does, reviewed and deliberate.

When a throwaway session unexpectedly grows teeth, halfway through a "quick look" it starts editing files, you don't have to restart it. Ask it to move into a worktree; recent builds carry a tool for exactly that, and the session relocates itself mid-conversation.

When You Forget, the Machine Should Say So

The flag only works when you remember to type it, and the whole premise here is that memory is the weak layer. The last piece is detection: make the tree itself announce that it's shared.

Each session now registers a heartbeat when it starts, a small file recording its identity, keyed by the working tree it sits in and stored outside the repository where it can't pollute anything. At session start, a hook scans for other live heartbeats on the same tree. When it finds one, it prints a banner naming the other session, how long it's been running, and when it last did anything, along with the reminder that matters: uncommitted edits will collide, prefer claude -w.

The banner goes two places at once: to my terminal, and into the model's context. That second delivery is the half people skip, and it's the half that changes behaviour. The model starts the session already knowing it's a co-tenant, so it stages by explicit path, expects the diff underneath it to move, and offers to relocate itself before starting anything broad.

A second hook handles the case the banner can't: the co-tenant who arrives after you did. The first time a session writes a file while another live session shares its tree, a one-time warning lands in the model's context, naming the other session and the safe behaviours. Once per session, so it stays a signal instead of becoming noise.

The hooks are advisory: they warn and never block. Liveness comes from a process check with a freshness fallback, and dead heartbeats get swept on the next scan, so there's no bookkeeping to rot. If the detection ever misfires, the cost is one spurious banner, not a blocked write.

Half a Warning

Within the hour, the system got its first live test, and it half-failed.

I opened a fresh window while my main session was still running. The new session's start-scan ran exactly as designed, found nothing, and stayed silent. The problem: my long-running session predated the hooks, so it had never announced itself. A detector can only see sessions that register, and the one session that mattered was invisible. Meanwhile, over in the older session, the write-boundary hook fired the moment it saved a file, and the file it fired on was the draft of this post. It named two other live sessions sharing the tree. The machine half of the warning system worked on its first outing.

The human half never reached me. The banner had gone to hook output and to the model's context, and I was looking at an editor panel that shows neither with any prominence, so the warning might as well not have fired.

The fixes followed the same evening. A once-per-session check now runs at each prompt, catching any co-tenant that became visible after the session started, which closes the invisible-session gap on its own schedule: the next thing you type, you find out. Every warning also raises an operating-system notification, the one channel that reaches me whichever interface the session runs in, terminal or panel or app.

In MX work we keep saying the audience includes the machine, because everyone builds for human readers and forgets the agents. I'd made the same mistake in reverse: a warning built for the machine, with the human forgotten. Two audiences, and each needs its own carrier: context injection for the model, a notification for the person.

What Isolation Doesn't Fix

Isolation and warnings don't retire the habits; they make the habits survivable when they slip.

Stage by explicit path, always, and read git diff --cached before committing, because what's staged is what ships. Finish and push in one session before starting the same work in another. When a diff appears that you don't recognise, treat it as information rather than corruption: someone else is working, and the right response is to look, not to revert.

The afternoon I lost to the collision ended with every change accounted for and both sessions' work intact, but it was archaeology: hours spent working out whose edit was whose.

What It Costs

One flag when you open a second session. A few small hooks that warn on a channel each audience actually receives. A habit of letting one session own the checkout.

Against that: parallel sessions that genuinely run in parallel, instead of taking turns wrecking each other's staging area. If you only ever run one session, none of this applies to you. The day you open the second one, type the flag.
