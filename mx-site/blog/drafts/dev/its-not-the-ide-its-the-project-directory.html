It's Not the IDE - It's the Project Directory

22 June 2026 · Salva · 4 min read

Two developers, the same repository, the same model. One opens a new folder and a metadata file appears in it automatically. The other does the same thing and gets nothing. The obvious explanation - "you're in the terminal, he's in the IDE" - is wrong. Here's what's actually going on, because the real answer is more useful than the wrong one.

The setup

A colleague - call him Tom - runs Claude Code inside the IDE. I run it from a macOS terminal by typing claude. We both work in the same MX repo. When Tom creates an empty directory, an .mx.yaml.md "folder-metadata" file shows up in it on its own. When I create the same empty directory, nothing happens.

It looks like a difference between the IDE and the terminal. It isn't. The IDE extension and the terminal CLI are the same Claude Code engine - same model, same agentic loop, same tools. A behavioral difference like this never comes from the frontend. It comes from which directory the session treats as its project.

The thing that actually creates the file

The MX repo isn't a plain codebase. Every directory is supposed to carry an .mx.yaml.md file describing it, and the repo ships tooling to generate one for any directory that lacks it ("orphans"). More importantly, its .claude/settings.json registers a wall of SessionStart hooks - shell scripts the harness runs the moment a session begins.

The file isn't written by "the model deciding to." It's written by a hook: deterministic project machinery that fires automatically. And every one of those hooks is declared like this:

{
  "type": "command",
  "command": "bash \"$CLAUDE_PROJECT_DIR/.claude/hooks/session-...sh\""
}

Notice $CLAUDE_PROJECT_DIR. That variable points at the directory you launched claude from - your project - not at any directory you attach afterwards.

Where the two sessions diverge

  • Tom launches Claude Code inside the MX repo. So CLAUDE_PROJECT_DIR is the MX repo. Every SessionStart hook fires, the orphan/boot machinery runs, and a new directory gets its .mx.yaml.md scaffolded automatically.

  • I launched claude in a different repo and then ran /add-dir /path/to/MX-repo to pull the MX folder into my session. So CLAUDE_PROJECT_DIR is still my original repo. The MX repo's settings.json, its hooks, and its skills are never loaded in my session.

That's the whole difference. Not terminal versus IDE. Project-rooted versus attached-after-the-fact.

The trap inside /add-dir

This is the part worth internalizing, because /add-dir looks like it should be equivalent to opening the folder, and it isn't:

/add-dir grants file access and permission scope to another directory. It does not adopt that directory's .claude/settings.json, its hooks, or its CLAUDE_PROJECT_DIR.

Project configuration is bound to the launch directory plus your user-level ~/.claude. Adding a directory widens what the session can read and edit; it does not make that directory's project machinery active.

There's a quiet safety implication. The MX repo's hooks aren't just cosmetic - some are guard rails: read-only protections, frontmatter validation, content gates. In my attached-directory session, none of those fire. If I edit MX files from there, I'm editing them with the repo's own safety rails switched off. The missing .mx.yaml.md is the visible symptom; the disabled guard rails are the part that can actually bite.

The fix

If you want the project's full behavior - hooks, scaffolding, guard rails - root your session in it instead of attaching it:

cd /path/to/MX-repo
claude

Now CLAUDE_PROJECT_DIR is the MX repo, the SessionStart hooks run, and you get the same automatic .mx.yaml.md scaffolding your teammate has.

Use /add-dir when you genuinely want a second directory in scope - a backend plus its frontend, say - and you accept that only your launch directory's project config is in force.

The takeaway

A good diagnostic question whenever Claude Code "behaves differently" for two people on the same repo: where did each of you launch it? Frontends are interchangeable. Project directories are not. Hooks, settings, skills, and the guard rails that come with them all hang off the directory you started in - and /add-dir deliberately does not change that.

When the harness does something the model didn't choose, look for a hook. And when a hook doesn't run, check whose project directory you're actually in.
