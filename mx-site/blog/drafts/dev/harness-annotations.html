Agent Harness: Annotations

5 July 2026 · Tom Cranstoun · 4 min read

This is the second in a series covering each handler in the MX conformance harness. The first post covered the parsing handler. This one covers annotations.

Annotations are markers embedded in a cog's body text. They flag sections for review, note concerns, or attach structured comments to specific passages. The annotations handler checks that the extractor finds the right annotations in the right places.

What annotations cases test

An annotation case provides a cog with annotations in the body and asserts what the extractor should find. The expected result is a list of annotation objects, each with a type and a location.

case-id: annotations-001
case-name: A single inline annotation is extracted
spec-references:
  - "section 3.1"
input:
  type: cog
  content: |
    ---
    title: Annotated cog
    description: Contains one inline annotation.
    ---
    This paragraph has a [REVIEW: check this claim]() marker in it.
expect:
  outcome: success
  annotations:
    - type: REVIEW
      text: check this claim

The expect.annotations list names the annotations that should be present. The handler checks that every expected annotation appears in the extractor's output. It does not require the output to contain only those annotations - additional annotations do not cause a failure, because some test inputs may contain structural markers the extractor also picks up.

A case that checks a block annotation:

case-id: annotations-004
case-name: A block annotation spanning multiple lines is extracted
spec-references:
  - "section 3.2"
input:
  type: cog
  content: |
    ---
    title: Block annotation test
    description: Contains a block annotation.
    ---
    Normal paragraph.

    <!-- CONCERN: this section needs a source -->

    Another paragraph.
expect:
  outcome: success
  annotations:
    - type: CONCERN
      text: this section needs a source

The handler

function runAnnotationsCase(testCase) {
  const { input, expect } = testCase;
  if (input.type !== 'cog') return skip(`input type ${input.type} not handled`);

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    return fail(`cog did not parse: ${err.message}`);
  }

  const extracted = extractAnnotations(parsed);

  if (expect.outcome === 'failure') {
    return extracted.length === 0
      ? pass()
      : fail(`expected no annotations, found ${extracted.length}`);
  }

  if (!expect.annotations || expect.annotations.length === 0) {
    return pass();
  }

  for (const expected of expect.annotations) {
    const found = extracted.find(a =>
      a.type === expected.type &&
      a.text.toLowerCase().includes(expected.text.toLowerCase())
    );
    if (!found) {
      return fail(
        `annotation not found — type: ${expected.type}, text: "${expected.text}"`
      );
    }
  }

  return pass();
}

The handler parses the cog first, then passes the parsed result to extractAnnotations. If parsing fails, the case fails - a cog that does not parse cannot have its annotations tested.

For each expected annotation, it searches the extracted list for a match on type and text. The text comparison is a substring match, case-insensitive, for the same reason as in the parsing handler: annotation text may contain punctuation or surrounding words that vary between implementations.

What extractAnnotations returns

The function returns an array of objects. Each object has at minimum:

{ type: 'REVIEW', text: 'check this claim', location: { line: 7 } }

The location field is not checked by the handler - only type and text are compared against the case. That is a deliberate choice: line numbers are fragile if the case content changes. If you need location testing, add a location field to the case format and extend the comparison.

Adapting this for your own extractor

Replace extractAnnotations with your own extraction function. The case format is independent of the implementation - any function that returns a list of objects with type and text fields will work with this handler.

If your annotation format uses different syntax (JSON comments, custom delimiters, front-matter lists), the case input.content just needs to use that syntax. The handler does not inspect the content directly - it hands it to parseCog and then to your extractor.
