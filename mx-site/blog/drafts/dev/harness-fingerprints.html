Agent Harness: Fingerprints

5 July 2026 · Tom Cranstoun · 4 min read

This is the third post in the series. The first two covered parsing and annotations. This one covers fingerprints.

A fingerprint is a hash of part of a cog. The MX system uses two: a contract fingerprint, computed over the cog's structured metadata, and a body fingerprint, computed over its narrative content. They serve different purposes. The contract fingerprint is what gets signed when a witness is created. The body fingerprint records the state of the prose at signing time, without being included in the signed claim.

The fingerprints handler checks that the hashing functions produce stable, correct output.

What fingerprint cases test

Fingerprint cases are different from parsing or annotation cases in one important respect: they include the expected hash value in the case itself. This means the hash must be computed once - by hand or by a reference run - and recorded. Any implementation that produces a different hash for the same input has a bug.

case-id: fingerprints-001
case-name: Contract fingerprint is stable across runs
spec-references:
  - "section 4.1"
input:
  type: cog
  content: |
    ---
    title: Stable fingerprint test
    description: Used to verify hash stability.
    schema: urn:mx:schema:basic
    ---
    Body text that should not affect the contract fingerprint.
expect:
  outcome: success
  contract-fingerprint: "a3f8c2e1d4b7..."

The contract-fingerprint value in expect is the canonical output. The handler computes the fingerprint from the input and compares it character-for-character.

A body fingerprint case:

case-id: fingerprints-003
case-name: Body fingerprint changes when body content changes
spec-references:
  - "section 4.2"
input:
  type: cog
  content: |
    ---
    title: Body fingerprint test
    description: Body fingerprint test.
    ---
    Original body content.
  altered-content: |
    ---
    title: Body fingerprint test
    description: Body fingerprint test.
    ---
    Altered body content.
expect:
  outcome: success
  fingerprints-differ: true

This case does not assert a specific hash value. It asserts that two different inputs produce different hashes. That is a weaker assertion but a useful one - it checks that body changes are detected without requiring a pre-computed value.

The handler

function runFingerprintsCase(testCase) {
  const { input, expect } = testCase;
  if (input.type !== 'cog') return skip(`input type ${input.type} not handled`);

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    return fail(`cog did not parse: ${err.message}`);
  }

  if (expect['contract-fingerprint']) {
    const actual = computeContractFingerprint(parsed);
    if (actual !== expect['contract-fingerprint']) {
      return fail(
        `contract fingerprint mismatch\n  expected: ${expect['contract-fingerprint']}\n  actual:   ${actual}`
      );
    }
  }

  if (expect['body-fingerprint']) {
    const actual = computeBodyFingerprint(parsed);
    if (actual !== expect['body-fingerprint']) {
      return fail(
        `body fingerprint mismatch\n  expected: ${expect['body-fingerprint']}\n  actual:   ${actual}`
      );
    }
  }

  if (expect['fingerprints-differ'] && input['altered-content']) {
    let altered;
    try {
      altered = parseCog(input['altered-content']);
    } catch (err) {
      return fail(`altered cog did not parse: ${err.message}`);
    }

    const original = computeBodyFingerprint(parsed);
    const alteredFp = computeBodyFingerprint(altered);

    if (original === alteredFp) {
      return fail(`fingerprints did not differ after body change`);
    }
  }

  return pass();
}

The handler checks whichever fields are present in expect. A case may check a contract fingerprint, a body fingerprint, both, or neither - instead asserting that two fingerprints differ. All three checks are independent.

Why pre-computed hashes in cases

Recording the expected hash in the case file means the case is a contract. If someone changes the hashing algorithm, the case fails. If the case fails for any reason other than an intentional algorithm change, that is a regression.

The downside is that adding a new case requires running the reference implementation first to get the hash. This is a small cost for a meaningful guarantee. The alternative - testing only that a hash is produced, without checking its value - does not catch the class of bug where the hash function changes silently.

The canonical form requirement

Both fingerprint functions - computeContractFingerprint and computeBodyFingerprint - operate on a canonical form of their input, not the raw text. For the contract fingerprint, this means sorting object keys alphabetically and removing whitespace variation before hashing. This is the RFC 8785 JSON Canonicalisation Scheme (JCS) approach.

Canonical form matters because two cogs that are semantically identical but differ in whitespace or key order must produce the same fingerprint. A case that passes on one machine and fails on another - because key order varies between JavaScript engines - is not a useful conformance case.

If you are adapting this for your own agent, make sure your fingerprint function specifies and tests its canonical form. The fingerprint cases are where implementation drift becomes visible.
