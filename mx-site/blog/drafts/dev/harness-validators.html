Agent Harness: Validators

5 July 2026 · Tom Cranstoun · 4 min read

This is the fifth and final post in the series. Previous posts covered parsing, annotations, fingerprints, and witnesses. This one covers validators.

Validators are named functions that inspect a cog and return a pass or fail result. They are declared in the cog's frontmatter by name. At review time, the system resolves each name from a registry, runs the function against the cog, and collects the outcomes. The validators handler checks that this resolution and execution works correctly.

What validator cases test

A validator case names a cog with specific properties and declares which validator should run against it. The expected outcome is whether that validator should pass or fail given those properties.

case-id: validators-001
case-name: Schema field present — schema-field-present validator passes
spec-references:
  - "section 4.3"
input:
  type: cog
  content: |
    ---
    title: Validator test
    description: Has a schema field.
    schema: urn:mx:schema:basic
    ---
    Body text.
  run-validator: cogs.review.schema-field-present
expect:
  outcome: success
  validator-result: pass

The run-validator field names the validator to run. The validator-result field says whether it should pass or fail.

A failing case:

case-id: validators-002
case-name: Schema field absent — schema-field-present validator fails
spec-references:
  - "section 4.3"
input:
  type: cog
  content: |
    ---
    title: No schema
    description: Missing schema field.
    ---
    Body text.
  run-validator: cogs.review.schema-field-present
expect:
  outcome: success
  validator-result: fail

Note that expect.outcome is success in both cases. That field describes whether the harness itself ran without error, not whether the validator passed. A validator that correctly identifies a failing cog is a successful harness execution.

The handler

async function runValidatorsCase(testCase) {
  const { input, expect } = testCase;
  if (input.type !== 'cog') return skip(`input type ${input.type} not handled`);

  if (input['validate-procedure']) {
    return runProcedureValidationCase(testCase);
  }

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    return fail(`cog did not parse: ${err.message}`);
  }

  const validatorName = input['run-validator'];
  if (!validatorName) return skip('no run-validator specified');

  let validator;
  try {
    validator = resolve(validatorName);
  } catch (err) {
    return fail(`validator not found in registry: ${validatorName}`);
  }

  let result;
  try {
    result = await validator(parsed);
  } catch (err) {
    return fail(`validator threw: ${err.message}`);
  }

  const expected = expect['validator-result'];
  const actual = result.passed ? 'pass' : 'fail';

  if (actual === expected) return pass();
  return fail(`expected "${expected}", got "${actual}"`);
}

The handler separates two failure modes. If resolve(validatorName) throws, the registry does not contain the named validator - a configuration or registration problem. If the validator itself throws during execution, that is a bug in the validator function. Both are harness failures, but with distinct messages.

The procedure validation sub-case

The validator cases also include a sub-case type: validate-procedure. Instead of running a named validator against a cog, these cases check that a review procedure declaration in the frontmatter is well-formed.

case-id: validators-006
case-name: Ill-formed procedure phase id is rejected
spec-references:
  - "section 4.4"
input:
  type: cog
  content: |
    ---
    title: Test
    description: Bad phase id.
    review-procedure:
      runner: cogs.review.runner
      phases:
        - id: BAD PHASE ID
          function: cogs.review.inventory
          success-criteria:
            - sections-extracted
    ---
    Body.
  validate-procedure: true
expect:
  outcome: success
  procedure-validation:
    ok: false
    reason-mentions: phase id

function runProcedureValidationCase(testCase) {
  const { input, expect } = testCase;

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    return fail(`cog did not parse: ${err.message}`);
  }

  const result = validateProcedure(parsed);
  const expectedOk = expect['procedure-validation'].ok;

  if (result.ok !== expectedOk) {
    return fail(`expected ok=${expectedOk}, got ok=${result.ok}: ${result.reason}`);
  }

  if (expect['procedure-validation']['reason-mentions']) {
    const mention = expect['procedure-validation']['reason-mentions'].toLowerCase();
    if (!result.reason || !result.reason.toLowerCase().includes(mention)) {
      return fail(`reason did not mention "${mention}": ${result.reason}`);
    }
  }

  return pass();
}

The sub-handler is kept separate from the main validator handler. Both types of case live in the validators/ directory and are dispatched from runValidatorsCase, with the validate-procedure flag routing to the right path.

Why registry resolution is tested explicitly

The validator handler does not import validator functions directly. It calls resolve(validatorName) to fetch them from the registry. Testing that step separately - before running the validator - means a missing registration produces a clear error rather than a confusing crash.

This matters for interoperability. A second implementation must register validators under the same names. If a case fails at the resolution step, the problem is registration; if it fails at the execution step, the problem is the validator logic. Keeping those two failure modes distinct makes debugging across implementations faster.
