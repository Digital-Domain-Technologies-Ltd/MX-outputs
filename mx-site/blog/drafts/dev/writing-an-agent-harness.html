Writing an Agent Harness

5 July 2026 · Tom Cranstoun · 8 min read

An agent harness is a thin piece of code that sits between your test cases and your agent. It loads a case, hands it to the agent, and checks the result. That is all it does.

The term sounds more involved than it is. If you have written any kind of test runner, you have written something in the same family. The difference is that the thing being tested is an agent - a function, a pipeline, or a model call - rather than a pure function with deterministic output.

This post works through a real harness: the one built for the MX cog-review conformance suite. The code is plain JavaScript with one dependency (js-yaml). The pattern it follows is the same pattern you would use for any agent you want to test systematically.

What a Harness Does

A harness has three responsibilities.

Load. Read each test case from a file. The case describes an input and an expected outcome. It does not contain any code - it is data.

Dispatch. Work out which part of your agent handles this type of case, and call it with the input.

Report. Compare the agent's output against the expected outcome, and record pass, fail, or skip.

That is the whole shape. Everything else is detail.

Why Keep Cases as Data Files

The cases in the MX suite are YAML files. Each one describes a single behaviour:

case-id: parsing-001
case-name: A well-formed cog parses without error
spec-references:
  - "section 2"
input:
  type: cog
  content: |
    ---
    title: Test cog
    description: A minimal valid cog.
    ---
    Body text.
expect:
  outcome: success

Keeping cases as data rather than code has two practical benefits. First, anyone can read them - a developer working on the spec, a reviewer checking coverage, an implementer in a different language. Second, a second implementation can use the same case files with its own harness. The cases define what the agent must do; the harness defines how to call it.

In the MX suite, the case files live under conformance/cases/, organised into sub-directories by category: parsing/, annotations/, fingerprints/, witnesses/, validators/. The harness discovers them by reading the directory.

The Harness Structure

Here is the top-level shape of run-js.js, the MX reference harness:

import { readdirSync, readFileSync } from 'node:fs';
import { join, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';
import yaml from 'js-yaml';

// Import the agent under test
import { parseCog } from '../../../../../../src/cog.js';
import { runReview } from '../../../../../../src/runners/review.js';
import { signContractSatisfaction, verifyWitness } from '../../../../../../src/runners/reginald.js';

const __dirname = dirname(fileURLToPath(import.meta.url));
const CASES_DIR = join(__dirname, '..', 'cases');

const results = { passed: [], failed: [], skipped: [] };

const categories = readdirSync(CASES_DIR)
  .filter(name => !name.startsWith('.') && !name.startsWith('_'));

for (const category of categories.sort()) {
  const categoryDir = join(CASES_DIR, category);
  const caseFiles = readdirSync(categoryDir)
    .filter(f => f.endsWith('.yaml'))
    .sort();

  for (const caseFile of caseFiles) {
    const casePath = join(categoryDir, caseFile);
    const testCase = yaml.load(readFileSync(casePath, 'utf8'));
    const result = await runCase(category, testCase);
    // record result
  }
}

Two things to note. The harness imports the agent - the actual functions being tested. The case files know nothing about those imports; they just describe inputs and expected outputs. And the harness iterates by category, which is how it knows which dispatcher to call.

The Dispatch Function

Each category of case maps to a handler function. The dispatch looks like this:

async function runCase(category, testCase) {
  switch (category) {
    case 'parsing':    return runParsingCase(testCase);
    case 'annotations': return runAnnotationsCase(testCase);
    case 'fingerprints': return runFingerprintsCase(testCase);
    case 'witnesses':  return runWitnessesCase(testCase);
    case 'validators': return runValidatorsCase(testCase);
    default:
      return { outcome: 'skip', reason: `no handler for category: ${category}` };
  }
}

A new category of case means a new handler and a new line in the switch. Nothing else changes.

Each handler follows the same shape: extract the input from the case, call the agent, compare the result to testCase.expect, and return { outcome: 'pass' } or { outcome: 'fail', reason: '...' }.

Here is the parsing handler:

async function runParsingCase(testCase) {
  const input = testCase.input.content;
  const expected = testCase.expect.outcome;

  let actual;
  try {
    parseCog(input);
    actual = 'success';
  } catch (err) {
    actual = 'error';
  }

  if (actual === expected) {
    return { outcome: 'pass' };
  }
  return {
    outcome: 'fail',
    reason: `expected ${expected}, got ${actual}`
  };
}

The agent here is parseCog. The case says whether it should succeed or throw. The handler calls it, catches any error, and compares.

Handling More Complex Cases

Not every case is a single function call. The witness cases in the MX suite test a multi-step workflow: sign a document, edit it, then verify the signature should fail. The handler runs each step in sequence:

async function runWitnessesCase(testCase) {
  const { document } = testCase.input;

  // Step 1: sign
  const signed = await signContractSatisfaction(document);

  // Step 2: tamper if the case asks for it
  const subject = testCase.input.tamper
    ? signed.replace('Body text.', 'Altered text.')
    : signed;

  // Step 3: verify
  let verifyOutcome;
  try {
    await verifyWitness(subject);
    verifyOutcome = 'valid';
  } catch (err) {
    verifyOutcome = 'invalid';
  }

  const expected = testCase.expect['verify-outcome'];
  if (verifyOutcome === expected) return { outcome: 'pass' };
  return { outcome: 'fail', reason: `expected ${expected}, got ${verifyOutcome}` };
}

The case data drives the behaviour. testCase.input.tamper is a flag set in the YAML; the handler reads it and decides what to do. The handler is still thin - it is translating between the case format and the agent's API.

Reporting

After all cases have run, the harness prints a summary:

const total = results.passed.length + results.failed.length + results.skipped.length;
console.log(`\n${results.passed.length}/${total} passed`);

if (results.failed.length > 0) {
  console.log('\nFailed:');
  for (const f of results.failed) {
    console.log(`  ${f.caseId}: ${f.reason}`);
  }
}

process.exit(results.failed.length > 0 ? 1 : 0);

Exit code 1 on any failure means a CI pipeline will catch regressions without extra configuration.

Adapting This for Your Agent

The harness above is coupled to the MX reference implementation - it imports parseCog, runReview, and the other functions by name. That is intentional. The harness is the translation layer between the language-agnostic case files and the language-specific agent. A Python implementation of the same agent would write a Python harness importing its own functions, pointing at the same case files.

If you are writing a harness for a different agent, the steps are:

Define your case format. Decide what fields a case needs: an input, an expected output, and enough metadata to identify it in a report. YAML works well. Keep it flat - nested structures make cases harder to write and harder to read.

Write one handler per case category. Start with one category and one case. Get the load-dispatch-report loop working end to end before adding more. The loop is the same regardless of how many categories you have.

Keep handlers thin. A handler that calls the agent and compares the result should be short. If a handler is doing significant work itself, that work probably belongs in the agent, not the test.

Make skips explicit. If a case cannot run in this environment - because a dependency is missing, or a feature is not yet implemented - return { outcome: 'skip', reason: '...' } rather than letting it fail silently. Silent skips hide coverage gaps.

Exit non-zero on failure. One line. Makes CI integration free.

What This Does Not Cover

A harness of this kind tests deterministic agent behaviour: given this input, expect this output. It does not handle probabilistic outputs from a language model, where the same input can produce different outputs on different runs.

Testing model behaviour is a different problem. You need either a scoring function (does the output satisfy these criteria?) or a fixed seed and a snapshot test. Those are valid approaches, but they add complexity. Start with the deterministic cases. They will find most of the bugs.

How this connects to MX, REGINALD, MaXinE, and Palimpsest

The harness described in this post is the structural layer inside MaXinE that wraps every agent workflow. MaXinE is the engine that runs the harness, routes inference, records configuration, and catches adverse events. REGINALD attests the content the harness processes - every document the agent reads or produces passes through a signing step that makes its origin verifiable.

The signed content that comes out of a harness run reaches a reader through Palimpsest, shaped to their declared context. A regulator asking about a specific agent decision gets the git log, the harness event record, and the REGINALD attestation chain. MX is the discipline that determines what each of those records should contain.
