Agent Harness: Parsing

5 July 2026 · Tom Cranstoun · 3 min read

This is the first in a series of posts working through the MX conformance harness category by category. Each post covers one handler: what it tests, what the case format looks like, and how the handler code works.

The parsing handler tests one thing: given a block of text, does the cog parser accept or reject it?

What parsing cases test

A cog is a markdown file with a YAML frontmatter block. The parser's job is to read that block and either return a structured object or throw an error. Parsing cases exercise both sides of that behaviour - inputs that should succeed and inputs that should fail.

Each case in the parsing/ directory is a YAML file describing one input and one expected outcome.

A passing case:

case-id: parsing-001
case-name: A well-formed cog parses without error
spec-references:
  - "section 2"
input:
  type: cog
  content: |
    ---
    title: Test cog
    description: A minimal valid cog.
    ---
    Body text.
expect:
  outcome: success

A failing case:

case-id: parsing-003
case-name: Missing description field produces a parse error
spec-references:
  - "section 2.1"
input:
  type: cog
  content: |
    ---
    title: No description here
    ---
    Body text.
expect:
  outcome: failure
  failure-mentions: description

The failure-mentions field is optional. When present, it asserts that the error message contains a specific word or phrase - in this case, description. That lets the case check not just that the parser rejected the input, but that it identified the right problem.

The handler

function runParsingCase(testCase) {
  const { input, expect } = testCase;
  if (input.type !== 'cog') return skip(`input type ${input.type} not handled`);

  let parsed;
  try {
    parsed = parseCog(input.content);
  } catch (err) {
    if (expect.outcome === 'failure') {
      if (expect['failure-mentions']) {
        const ok = err.message.toLowerCase()
          .includes(expect['failure-mentions'].toLowerCase());
        return ok
          ? pass()
          : fail(`error did not mention "${expect['failure-mentions']}": ${err.message}`);
      }
      return pass();
    }
    return fail(`unexpected parse error: ${err.message}`);
  }

  if (expect.outcome === 'success') return pass();
  return fail(`expected failure but parsing succeeded`);
}

Walk through the logic:

  1. If the input type is not cog, return skip. The harness may eventually handle other input types; this makes the gap explicit rather than silent.
  2. Call parseCog. If it throws, we are in the failure path.
  3. In the failure path: if the case expected failure, check whether failure-mentions is set. If it is, verify the error message contains the expected string. If not, pass unconditionally.
  4. If parseCog did not throw: if the case expected success, pass. If the case expected failure, fail.

Adapting this for your own parser

Replace parseCog with whatever your parser is called. The case format stays the same - input.content, expect.outcome, and the optional expect['failure-mentions']. The handler shape stays the same.

If your parser returns structured errors rather than throwing, adjust the try/catch to read the error from the return value. The comparison logic is identical.

The failure-mentions check is a substring match, case-insensitive. That is intentionally loose - error message text changes; what matters is that the right field or concept appears in the message. If your error model is more structured (error codes, field names as structured data), you can add a failure-code field to the case format and check it directly.
