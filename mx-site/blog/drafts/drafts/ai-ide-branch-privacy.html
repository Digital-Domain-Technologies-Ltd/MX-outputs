Your AI IDE Is Not Reading Your Repo the Way You Think

1 July 2026 · Tom Cranstoun · 12 min read

Something happened in my repository that still bothers me.

I was using Claude Code, with several branches under active development: features, drafts, experiments. None of it was finished. They're the kind of branches that exist so main stays clean while ideas get tested and thrown away.

Claude Code read those branches and found things it liked. Then, without being asked, it made changes on main built from ideas and patterns in the drafts.

The tool's reasoning holds together: it had access, it found relevant material, and it applied it. Efficient, even. I saw it as a violation.

The drafts weren't ready, and nothing in them had been decided. What went to main, and when, and how, was my call. The tool swapped in its own judgment on a question that wasn't its to answer.

The failure wasn't one of intelligence but of scope. The tool had no policy telling it the difference between "I can read this" and "I am permitted to act on this".

How a human reads a repository

A human developer doesn't read a repository the way a search engine crawls a website. They navigate it with intent.

When I open a repository I haven't worked in before, I start with the README. I want to know what the project is before I look at what it does. I build a mental model from the description, the folder structure, and the contributing guide. The commit history tells me the pace and the culture, and the open issues and pull requests show me what's unresolved.

Only then do I start on the code, and I read it with context: who wrote this, why, what problem they were solving, when, and what else they were working on at the same time.

This is well-documented. Research consistently finds that developers spend 58-70% of their time on code comprehension and only around 5% actually editing it, which gives Robert Martin's "10:1 reading-to-writing ratio" empirical support. Letovsky's foundational 1987 work frames comprehension not as reading but as hypothesis formation: you form conjectures about why the code exists, how it works, and what it means. You also use "beacons", recognisable patterns that let someone with experience skip familiar structures and focus on the unfamiliar. Eye-tracking studies confirm that visual attention decays roughly 40% per repeated pattern occurrence. The navigation sequence is remarkably consistent across developers: README - CONTRIBUTING.md - config files - file tree - entry point search - tests - Issues and PRs for context - git blame for history.

I also pick up signals from outside the code. A branch named wip/rethinking-auth is a warning rather than an invitation: this work is in progress, the author is thinking, don't treat it as a decision. Put the same idea on main and it's a commitment. The bytes can be identical, and the naming convention is what tells you the intent.

Human developers pick up these conventions early and apply them without thinking: drafts and experiments get treated as unfinished, and a branch is a workspace rather than a publication.

How an AI IDE reads a repository

An AI IDE retrieves rather than navigates.

The technical picture varies by tool but the pattern is consistent. Cursor uses a Merkle tree file-hashing approach with AST chunking via tree-sitter and vector embeddings stored in Turbopuffer. GitHub Copilot announced a custom-trained embedding model in September 2025 with a 37.6% retrieval quality improvement. Windsurf uses multi-dimensional retrieval (AST embeddings, ripgrep, and a knowledge graph) with LLM-based reranking. All three find what's relevant to the current query, and none of them builds the kind of global-to-local mental model a human builds over days of working in a codebase.

Claude Code uses no pre-built index at all. It works through repositories with iterative bash grep commands in real time, on the stated grounds that a pre-built index goes stale during active development. That observation is correct. It also explains what happened in my repository: working from the live filesystem rather than a static copy, Claude Code picks up whatever branches it can see, including ones I considered private workspaces.

Most AI IDEs build a semantic search index of the repository up front by parsing file trees and embedding code chunks. When you ask a question or start a task, the tool pulls the chunks that best match your query, assembles a context window, and generates a response.

The index doesn't know what a branch is for, only what it contains. It can't tell whether that content is a draft, an experiment, an abandoned idea, or a considered decision, so it treats everything indexed as equally valid material.

Context overflow is the number-one autonomous agent failure mode, accounting for 63.4% of unresolved tasks in Claude Sonnet 4 on SWE-Bench Pro. The "lost in the middle" effect shows up clearly: roughly 50% of correctly identified bugs appear in the first 25% of a file, and only 18% in the last 25%. One million token context windows are, in a researcher's characterisation, "lossy semantic meaning pattern matchers with big holes". Reading branches that were never meant to be in scope makes this worse, because unneeded material crowds out what matters.

None of this comes from a flaw in the indexing approach so much as from how the job is framed. The tools optimise for relevance, meaning the code likeliest to help with the current task. Respecting the intent a developer encoded in the branching strategy isn't something they're built to weigh.

The gap: accessibility is not authorisation

The difference between how humans and AI IDEs read a repository produces one specific failure mode.

An AI IDE treats accessibility as authorisation.

If it can read a branch, it assumes it's permitted to act on what it finds there. Nobody states that assumption and nobody questions it, because it's baked into the tool's behaviour below the level of the prompt.

A human developer doesn't assume that. When I see a colleague's WIP branch, I recognise it as a draft and act accordingly: I keep its ideas out of my own work on main, I leave it out of technical discussions as evidence, and I don't treat it as a settled decision.

I can see the social contract behind the branching strategy, and the tool can't.

The evidence that something is going wrong

The productivity data is sobering. A 2025 randomised controlled trial by METR found that experienced developers using AI tools were 19% slower on real-world repositories, while believing they were 20% faster. They felt quicker than they were.

GitClear's longitudinal analysis of quality in AI-assisted development shows a 4x increase in code cloning and refactoring dropping from 25% to under 10% of changes. That fits what I saw: the AI finds something it likes and copies it, where a human developer with full context would build a considered abstraction.

Neither finding is surprising once you see the mechanism. An AI tool that reads branches indiscriminately, treating drafts as material and copying patterns with no regard for where they came from, produces exactly this output. It finds and copies without building understanding. Whoever reviews the result may not realise the source was a draft branch, so they get code that looks finished, resting on an idea nobody ever decided.

What needs to change

Read access to branches is useful, and I'm not arguing against it. What's missing is a machine-readable policy telling the tool what it's permitted to do with what it reads.

That gap can be closed, and a machine-readable standard exists to close exactly this kind of gap.

The fix is a branch access policy. It declares that every non-canonical branch is private by default and that reading one doesn't authorise acting on its contents. Before the tool may extract, derive, or cite from a branch, someone has to grant it explicit access.

MX has developed this standard as a draft for The Gathering, draft-cranstoun-branch-access-policy.

The MX branch access policy

All branches are private by default

The canonical branch (main, trunk, or master) is the published, accepted state of the work. Every other branch is a private workspace, which the tool may read subject to three prohibitions.

The three prohibitions

When an AI agent reads one of these branches without having been granted access:

  1. No extraction. The agent must not take ideas, designs, patterns, naming conventions, or code from the branch to use elsewhere.
  2. No derivation. The agent must not create, propose, or suggest anything on the canonical branch that derives from a private branch without explicit human authorisation.
  3. No citation. The agent must not reference a private branch as authoritative. A draft isn't a decision.

The five discoverable-access modes

There are five legitimate ways for an AI agent to gain extended access to a non-canonical branch:

Mode What it means
Session assignment The human explicitly names the branch for work in this session
PR review A pull request is open and the agent is asked to review it
Branch declaration The branch contains a machine-readable access declaration
Repo policy The repository policy file grants access to this branch
Checkout context The branch is the currently checked-out working branch

The audit requirement

Access only counts as discoverable if it's declared. When an AI agent accesses a non-canonical branch, two things must happen:

  1. An entry is written to the session audit log.
  2. The agent states at the start of any response drawing on that branch's content which branches it read and under which access mode.

Both steps earn their keep, because together they're the evidence that the access was legitimate.

The deeper principle

Underneath the git policy is a principle that reaches well past git: accessibility is not authorisation. It covers files that are visible but unpublished, emails in a shared inbox that aren't addressed to the agent, readable documents still in draft, and API endpoints that respond but aren't in the public contract.

AI tools work surrounded by accessible content that nobody has authorised them to use, and they can't tell the two apart unless someone declares the difference. MX's job is making that declaration machine-readable.

GitHub has moved in this direction. Copilot Workspace was sunset in May 2025 and replaced by a Cloud Agent model. GitHub now supports .github/copilot-instructions.md for repo-level instructions and .prompt.yml files versioned in the codebase, and both are attempts at machine-readable governance. The AGENTS.md standard, backed by the AI Agent Infrastructure Forum and the Linux Foundation from December 2025, has shown that human-curated context files cut agent runtime by 29% and token consumption by 17%. Even so, as of mid-2026 only around 5% of repositories have adopted any form of context manifest, and none of the existing standards address branch privacy specifically.

What this means for AI IDE designers

If you're building an AI IDE, this is a feature request as much as a critique.

Build a branch access policy layer. Before indexing or acting on any branch other than the canonical one, check for a machine-readable declaration. If there isn't one, apply private-by-default, log the access, and declare it in responses.

Technically, this is easy. What it needs is a policy choice about how the tool should behave when it finds accessible content. The current default is "use it", and it should be "ask first".

As of mid-2026, no mainstream AI IDE implements branch-level access policy. The closest existing mechanisms are repo-level instruction files (CLAUDE.md, .github/copilot-instructions.md, .cursorrules), which can include text instructions about branches. They rely on the model reading and following prose, though, rather than on a machine-readable policy enforced at the indexing or retrieval layer. A text instruction in a governance file beats nothing, but it's no substitute for a policy the tool enforces before it reads.

What this means for repository owners

If you work in a repository with AI IDEs, add a branch access policy now. At minimum, add a section to your CLAUDE.md, AGENTS.md, or equivalent governance file stating:

All branches other than main are private by default. Do not extract ideas, patterns, or code from non-canonical branches. Do not create work on main that derives from a private branch without explicit instruction. Extended access requires one of the five discoverable-access modes defined in branch-access-policy.cog.md.

Until tools implement the policy natively, the governance file is what you have. It's imperfect, since a sufficiently inattentive tool will ignore it, but it's the declaration that makes your intent explicit, and MX depends on that.

A Gathering proposal

The branch access policy developed for MX-hub is being submitted to The Gathering (tg.community) as a draft open standard.

The gap it addresses shows up in every repository AI agents work in, and every AI IDE that can read branches faces the same choice about what to do with what it finds. With a shared standard, every COG-aware agent works under the same branch-privacy contract, whichever codebase it's in.

Draft identifier: draft-cranstoun-branch-access-policy v0.1. The standard Gathering process applies: Propose - Review - Consensus - Ratify.

Summary

A human reads a GitHub repository with context, intent, and a social understanding of what its different parts mean. An AI IDE reads whatever it can reach and treats it as usable material.

That difference matters most with branches, because they carry intent. An AI that treats a draft branch as a decision has been oblivious rather than intelligent.

The fix is a machine-readable branch access policy: all branches private by default, five modes of discoverable access, two audit requirements, and the principle that accessibility is not authorisation. The standard is simple and honest.
