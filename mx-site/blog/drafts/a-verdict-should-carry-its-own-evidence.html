A Verdict Should Carry Its Own Evidence

1 November 2026 · Tom Cranstoun · 4 min read

Every commit that reaches our main line is tested again after it lands. One afternoon that check came back red. The message named the stage that had failed and the place its log was kept. That was all it said. The log was on the computer that ran it, which wasn't answering.

The next commit went the same way, and the one after that. Three failures in a row look like three bad commits, so each sent someone off to read its code. Each time the code was fine.

What a Bare Red Costs

A message that only says "failed" hands its reader a job. To act on it, they need the name of the test and the error it printed. If those are in a log on one computer, every reader has to get there first. When they can't, they guess.

Guessing goes like this. You open the newest commit, find nothing wrong with it, and move on to the one after. A cause that stays put while the commits come and go never shows up in any one of them.

We had one piece of luck. The suite that ran on the unreachable computer works anywhere, so I ran it myself on my laptop. Nearly everything passed. One didn't, and it broke the same way every time: a request to a small local web server got no answer within five seconds.

The Test Was Judging the Machine

That test starts a little web server and fetches a file from it over loopback, the address a computer uses to talk to itself. The server listens on every network interface, because in real use other devices need to reach it. The fetch goes over loopback because that address is meant to answer whatever else is going on.

On my laptop it didn't. A VPN client was running, and it filters local traffic. With the tunnel up, a request over loopback to anything listening on every interface was dropped without a word. Bind the same server to loopback alone and it answered at once. It wasn't the programming language, either: the web server built into a different runtime did exactly the same.

The test, in other words, told us nothing about the code. It reported on the network setup of whichever computer ran it. On a build server with no VPN it passed. On a laptop with one, it failed every time, whatever the commit.

I still can't say whether that was the whole story on the computer nobody could reach, because its message didn't say.

Fixing the Test, Then the Verdict

A test should depend only on what it controls. This one controls the address it fetches from, so it now starts its server there too. A separate check makes sure that, left to its defaults, the server still listens on every interface. It does that without sending a request, so nothing on the network can change its answer.

The second fix matters more. A red result now carries its own evidence: each failing test by name, and the line it failed with, wherever it's published. Anyone who sees the verdict, anywhere, can see why it's red. The full log is still there for the detail, but nobody needs it to make a start.

A Pass or a Fail Is an Artefact

This is the MX principle turned on our own tools. MX is metadata that records where a file came from, what it's for, and how it should be used, written so the next reader, human or machine, can check it instead of taking it on trust. A test result is a file too. Somebody reads it and acts on it, so it owes them the same things: what was checked, what was found, and where to look next.

A machine has no stake in its own errors. It won't go hunting for the cause of a failure it reported; it'll just report the same thing again, as ours did. If you want the cause found, the verdict has to carry what its next reader needs to find it.

Try It on Your Own Checks

Pick one of your own failure messages and read it as if you'd never seen the system before. Does it name what failed and say what it printed? Could you act on it without opening the log? If not, the evidence is somewhere else, and someone pays for that the next time it goes red.

When a check passes in one place and fails in another, ask what it depends on that it doesn't control. Ours depended on the network. Yours might depend on the clock, the disk, the locale, or a service somebody left running.
