A Verdict Should Carry Its Own Evidence

1 November 2026 · Tom Cranstoun · 5 min read

If you're paying for AI agents, you're also paying for the scores that tell you whether they work. On 11 November AWS open-sourced an evaluation framework for agents, UAEF, and the most useful thing in it isn't a metric. It's a rule: when an AI judge scores an agent's answer, it has to quote the exact words it used as evidence for that score. UAEF checks that the quote really is in the answer. If it isn't, the score is thrown out rather than recorded.

That rule exists because agents read the web. An agent that reads a page can pick up instructions someone planted there and pass them along. A judge that then reads the agent's answer can be talked into a number. Tech Times reports a Cloud Security Alliance paper citing Google's finding of a 32% rise in malicious prompt-injection payloads in web content between November 2025 and February 2026. A score that has to point at its evidence is much harder to fake.

We learned the same lesson the dull way, from a check that said only "failed".

What a Bare Red Costs

Every commit that reaches our main line is tested again after it lands. One afternoon that check came back red. The message named the stage that had failed and the place its log was kept. That was all it said. The log was on the computer that ran it, which wasn't answering.

The next commit went the same way, and the one after that. A run of failures looks like a run of bad commits, so each sent someone off to read its code. Each time the code was fine.

A message that only says "failed" hands its reader a job. To act on it, they need the name of the test and the error it printed. If the only copy is a log on one computer, every reader has to get there first. When they can't, they guess, and a cause that stays put while the commits come and go never shows up in any one of them.

The Test Was Judging the Machine

The suite that ran on the unreachable computer works anywhere, so I ran it on my laptop. Nearly everything passed. One test didn't, and it broke the same way every time: a request to a small local web server got no answer within five seconds.

That test starts a web server and fetches a file from it over loopback, the address a computer uses to talk to itself. The server listens on every network interface, because in real use other devices need to reach it. On my laptop a VPN client was running, and it filters local traffic. With the tunnel up, a loopback request to anything listening on every interface was dropped without a word. Bind the same server to loopback alone and it answered at once.

The test told us nothing about the code. It reported on the network setup of whichever computer ran it. I still can't say whether that was the whole story on the computer nobody could reach, because its message didn't say.

Fixing the Test, Then the Verdict

A test should depend only on what it controls. This one controls the address it fetches from, so it now starts its server there too. A separate check makes sure the server still listens on every interface by default, without sending a request, so nothing on the network can change its answer.

The second fix matters more. A red result now carries its own evidence: each failing test by name, and the line it failed with, wherever it's published. Anyone who sees the verdict can see why it's red without opening the log.

That's the same move AWS made for its judge, pointed the other way. Our verdict names the error it saw; theirs names the words it scored. Either way the reader can check the claim instead of trusting it.

Where the Rule Stops

AWS is careful about the limits, and so should you be. Its security notes say no delimiter is safe against every model on every input, and the quote check isn't applied when you supply your own judge template. They also say judge scores are evaluation signal, not a safety decision, and shouldn't gate a security control. A quote proves the judge looked at real words. It doesn't prove the judge read them well.

A Pass or a Fail Is a Record Too

This is the MX principle turned on the tools that judge the work. MX is metadata that records where a file came from, what it's for, and how it should be used, written so the next reader, human or machine, can check it instead of taking it on trust. A test result or an agent score is a file too. Somebody reads it and acts on it, so it owes them what was checked, what was found, and where to look next.

A machine has no stake in its own errors. It won't hunt for the cause of a failure it reported, and a judge won't notice it was steered. If you want the cause found, the verdict has to carry what its next reader needs.

Try It on Your Own Checks

Pick one failure message from your build and one score from whatever evaluates your agents. For each, ask whether it names what it judged and quotes what it found. If you use an AI judge with your own template, confirm it asks for an evidence quote, and that something then checks those words are really in the answer, because UAEF won't do it for you there. Where the answer is no, add the quote and the check before you trust the next number.
