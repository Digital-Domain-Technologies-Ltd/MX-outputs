The Flag That Rewrote My Search

4 July 2026 · Tom Cranstoun · 6 min read

I was searching my own repository the other day, and the tool lied to me. It did not crash, which is the part worth sitting with. A crash is honest. This was quiet.

I ran a search for a field called stability in a config file, using ripgrep, the fast search tool a lot of us reach for without thinking. The results came back looking almost right, and then I noticed one line read mx.n where I knew the file said mx.stability. For a moment I thought the file was broken. I nearly opened it to fix a corruption that did not exist.

The file was fine. The search had rewritten its own output.

One letter, the wrong meaning

Here is what happened, and it is the kind of thing that catches everyone once. In grep, the old workhorse, -r means recursive: search down through folders. My fingers typed rg -rn, the way they have typed grep -rn a thousand times. But ripgrep is not grep. It recurses by default, so it never needed a recursive flag, and it gave -r a completely different job: -r is --replace. My -rn did not mean "recursive, with line numbers". It meant "replace every match with the letter n".

So ripgrep did exactly what I told it. It found every stability, and in the output it printed, it swapped each one for n. The file on disk was never touched. Only the answer it handed back was quietly wrong.

That is a benign version. I caught it because mx.n looked odd to a human who knew what the file should say. Change the search term to something I did not already know the answer to, and I would have had no tell at all. I would have read the rewritten output as the truth, because there was nothing to say it was not.

The machine has no squint

A person gets lucky here sometimes. You know roughly what you expect to see, so a mangled line snags your eye. You squint, you re-run it, you notice.

A machine does not squint. Feed that same rewritten output to an agent, a script, a model deciding what to do next, and it takes the confident wrong answer and acts on it. There is no red mark, no exception, no "are you sure". The tool reported success. The bytes were plausible. The next step inherits the lie as fact.

If you have read the piece on fat clones, thin clones, and the strawberry problem, this will feel familiar. There, the danger was never the loud failure; it was the quiet, confident damage that looks freshly generated and is silently gutted. This is the same shape, one layer down, in the tools themselves. The environment a machine reads through can misrepresent the thing it is reading, and the machine cannot tell.

The fix everyone reaches for is the wrong one

The obvious lesson is "be careful with your flags". Learn the difference, slow down, check twice.

That is a rule that lives in a human head, and it fails the way all such rules fail. It works until you are tired, or moving fast, or it is a different person, or a different agent, or the same agent on a different day. A rule you have to remember is a rule that will eventually not be remembered. Worse, it does nothing at all for the machine, which was never going to read your careful mental note.

So we did not write a reminder. We wrote a check.

A check a script does

Two small things now stand between that mistake and any harm.

The first is a guard that refuses the dangerous shape before it runs. If a command tries to hand ripgrep a replace flag in a spot where a search was plainly meant, the guard stops it and says why, in plain words: this flag rewrites your output, here is the safe form, and here is how to override me if you truly mean it. It is not advice. It is a gate, and it fires every time, for every person and every agent, without anyone having to be careful.

The second is a safe search tool that simply cannot produce the corrupted answer. It wraps the same fast engine, but it fixes the risky settings shut, passes your query where a query belongs and never where a flag could be mistaken for one, and always prints results the same honest way. You get the speed without the sharp edge.

Neither of these is clever. That is the point. The whole idea is to take a rule that was floating in prose and human memory, where it rots, and turn it into something the environment enforces on its own.

Determinism over inference

This is the operating principle underneath, and it is the one I would keep if I had to throw the rest away. If a rule can be checked by a machine, a machine should check it. A rule that only lives in a document, or a habit, or a hope that everyone stays sharp, is not really enforced. It is just described, and description is what you have right up until the moment it quietly fails.

It is the same instinct as writing metadata for the machine in the first place: do not make the reader guess, and do not make them trust. Give them something they can check. We write the frontmatter so an agent never has to infer what a file is. We write the guard so a tool can never misreport what a search found. In both cases the machine is handed a fact, not asked for faith.

The tool did not have to lie to me. It lied because nothing stopped it, and nothing told me. Now something does. The next person to type -rn out of habit will get a clear refusal instead of a quiet corruption, and the machine reading along will get the truth, because we stopped hoping and wrote the check.
