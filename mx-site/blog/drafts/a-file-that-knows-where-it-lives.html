A File That Knows Where It Lives

14 June 2026 · Tom Cranstoun · 4 min read
  • Mx
  • Machine Readability
  • Metadata
  • Paths
  • Grounding
  • Agents

There are two kinds of link in a markdown file. The kind a human needs, and the kind a machine needs. They are not the same.

The human kind is a relative path: [how-to-write-a-cog](../../cogs/how-to-write-a-cog.cog.md). Open the file in GitHub or VSCode and the link works. The previewer knows where you are; it resolves the path from there. Correct, helpful, and zero maintenance if you never move the file.

The machine kind needs something different. A machine reading a cog copied to a Gitea repo, embedded in a PDF, or fetched via an API has none of that context. It does not know which repo the file came from. It cannot resolve a relative path. It cannot follow ../../ to anything. The file is a document with no address, and the agent has to guess or give up.

The gap relative links leave

This is not a hypothetical failure. It is the normal state when metadata travels.

MX is designed for exactly this: metadata that travels with the file. A cog pushed to a per-domain Gitea audit repo, an attestation record stored in REGINALD, a PDF embedding its provenance XMP - in every case the file has left its origin context. The relative links in the body remain, pointing at paths that no longer resolve from where the machine is standing.

The usual answer is the canonicalUri field: a full raw-content URL for this specific file.

canonicalUri: https://raw.githubusercontent.com/Digital-Domain-Technologies-Ltd/MX-hub/main/scripts/cogs/how-to-write-a-cog.cog.md

That solves location for this file. It does not tell a machine which repo this file belongs to, or where to look for sibling files. A machine that wants to follow a relative link ../../../../datalake/knowledge/system/gitea.cog.md still has no anchor.

Two fields, one address

The fix is two x-mx- fields that together give every file a repo address it carries wherever it goes.

x-mx-hostRepo declares the raw-content base URL of the owning repository:

x-mx-hostRepo: https://raw.githubusercontent.com/Digital-Domain-Technologies-Ltd/MX-hub/main

x-mx-repoPath declares the file's path from the repo root, no leading slash:

x-mx-repoPath: scripts/cogs/how-to-write-a-cog.cog.md

Together they let a machine construct a direct fetch URL for any file in the same repo: x-mx-hostRepo + "/" + x-mx-repoPath. For this file: https://raw.githubusercontent.com/Digital-Domain-Technologies-Ltd/MX-hub/main/scripts/cogs/how-to-write-a-cog.cog.md - which is exactly what canonicalUri already declares.

That is the point. x-mx-hostRepo and x-mx-repoPath are not a replacement for canonicalUri; they are its components, separated so a machine can use them independently. The three fields together give three complementary anchors:

Field What it answers
x-mx-hostRepo Which repo owns this file?
x-mx-repoPath Where in that repo?
canonicalUri What is the direct fetch URL?

Relative links stay relative

The human surface is not touched. Markdown body links remain relative. A previewer resolves them from the file's location, as always. The two new fields are metadata - they live in the frontmatter, invisible to a renderer, and they do not change what a human sees or what a link checker verifies.

The grounding is a parallel channel for machines, not a replacement for the human channel. Both exist at the same time.

The backfill

For files that already carry canonicalUri, x-mx-repoPath is derivable by stripping the x-mx-hostRepo prefix. scripts/backfill-repo-path.cjs does this in one pass across the hub:

npm run repo-path:backfill          # dry run
npm run repo-path:backfill:apply    # write

The script is non-clobbering: an existing x-mx-repoPath is never overwritten.

Why this matters for agents

An agent reading a cog should be able to answer: where does this file live? Who owns it? Can I fetch the file it refers to?

Without repo grounding, the answer to all three is "I cannot determine this from the file alone." With x-mx-hostRepo and x-mx-repoPath, the file carries its own address. The agent has the same information a human gets from looking at a browser URL bar.

MX exists so that a file remains useful when it travels outside the environment that produced it. Repo grounding is what keeps a file useful when it travels outside the repo.
