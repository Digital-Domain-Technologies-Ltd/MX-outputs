The Flight Deck Bridge: Planning a Discord MCP Server

4 July 2026 · Tom Cranstoun · 5 min read

In the previous post, "From Solo Pilot to Flight Deck", we described the Flight Deck: a shared Discord server where Tom's wingman and Scott's agent work from one verifiable channel history. Step 4 of that recipe - wire the agent runtime to the bot - glossed over an inconvenient fact we have since confirmed: Anthropic's connector registry has no Discord connector. Slack, yes. Discord, no.

So we build the bridge ourselves. This is the plan, written before the code, so that the code has something to be checked against.

What we are building

A small MCP (Model Context Protocol) server - working name flight-deck-bridge - that a Claude agent loads as a custom connector. It authenticates as one Discord bot (one bot per partner, per the Flight Deck rules) and exposes the narrow set of operations an agent needs to participate in the shared channel: read the history, read the pinned conventions, post with provenance, open a thread. Nothing else.

MCP is the right shape for this because it is the same protocol every other connector in the session already speaks. To the agent, Discord becomes another tool surface, no different in kind from Drive or Gmail - which is precisely the MX argument: agents should meet new systems through declared, inspectable interfaces, not bespoke glue.

Design constraints

Four constraints, all deliberate:

Plain JavaScript, minimal dependencies. The implementation is Node with exactly one dependency: the official @modelcontextprotocol/sdk. Discord's REST API is spoken through Node's built-in fetch - no discord.js, no gateway library. Fewer dependencies means less to audit, and this bridge handles a credential.

stdio transport, local first. The server runs on the owner's machine alongside their agent, connected over stdio - the MCP norm for local servers. No hosting, no public endpoint, no session state. Each partner runs their own copy with their own token.

Token from the environment, never from the conversation. The bot token arrives as an environment variable in the server's launch configuration. It never appears in a tool argument, a channel message, or a log line. Scott never holds Maxine's token; the code enforces what the previous post promised.

Append-only by construction. The server exposes no edit and no delete. The Flight Deck's ledger property is not a convention the agent must remember to honour; it is a capability the agent simply does not have. Governance as code, not as goodwill.

The v1 tool surface

Five tools, named for discoverability, most of them read-only:

Tool What it does Writes?
discord_whoami Confirms the bot identity and lists the channels it can see. The state handshake's opening move. No
discord_read_channel Paginated read of a channel's message history, newest first, with author, timestamp, and message ID on every item. No
discord_get_pins Fetches a channel's pinned messages - the Flight Deck's index.md, read before anything else. No
discord_post_message Posts to a channel. Enforces the provenance header: the tool requires onBehalfOf, sources, and an optional artefact URN, and formats them into the message. Yes
discord_create_thread Opens a thread on a message, for isolating one job's working. Yes

Every tool returns message IDs, and the read tools accept them as cursors. Identity, never position - the channel equivalent of the folder index's rule.

Build phases

Following the mcp-builder methodology already installed in this workspace:

Phase 1 - research. Confirm current MCP spec details (streamable transports, tool annotations) from the protocol documentation, and the exact Discord REST endpoints and permission bits for the five tools. Output: a one-page API map appended to this cog.

Phase 2 - implement. One file if it stays readable, two if not: an API client wrapping fetch with the auth header, rate-limit handling (Discord returns 429 with a retry_after - the client waits and retries once), and actionable error messages; then the five tool registrations with input schemas, descriptions, and readOnlyHint/destructiveHint annotations set truthfully.

Phase 3 - test. Compile-free by design; test against a scratch Discord server with the MCP Inspector, then live from a Cowork session. The button-was-below rule applies to testing too: verify by fetching, never by assuming.

Phase 4 - evaluate. Ten read-only evaluation questions against seeded channel history ("what did the other agent report as the root cause on the delivery autopsy thread?"), each with one verifiable answer, per the mcp-builder evaluation format.

Acceptance

One test decides success, and it is the scenario from the original post. Seed the channel with a discussion between the two humans and one agent. Then ask the second agent - cold, no briefing - a question whose answer lives only in that history. If it answers correctly, citing message IDs, the state handshake works: context carried by the shared channel, not by a human re-explaining. That is the saving on context, measured.

Risks, named now

Discord could tighten bot rules or rate limits - the bridge's single-client design keeps the blast radius to one file. The Message Content intent must be enabled per bot or reads come back empty - the whoami tool will check and say so rather than fail quietly. And custom local connectors depend on the agent platform's support for adding them - verified before Phase 2 starts, not after Phase 3 finishes.

The plan is the cog; the code comes next. When the bridge posts its first provenance-headed message into #flight-deck, this file's x-mx-contentState flips, and the Flight Deck stops being an essay.
