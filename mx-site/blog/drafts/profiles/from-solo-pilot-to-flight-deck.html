From Solo Pilot to Flight Deck: Why Scott and I Are Sharing an Agentic Layer

4 July 2026 · Tom Cranstoun · 7 min read

Building Machine Experience (MX) as a solo architect is one thing. Scaling it with a partner requires a level of inter-cog negotiation that the current web just isn't ready for.

Scott and I aren't just "using an AI app." We are creating a collaborative UBERCOG environment on Discord. By connecting our respective Wingmen - mine is Maxine - to a shared channel, we are moving past the siloed chatbot model and into a verifiable ledger of partnership.

Here is the goal. When I tell Maxine to draft a technical autopsy of a failed Amazon delivery, Scott doesn't just see a final result. He sees the provenance of the data. He sees shared context at work - tokens aren't being burned re-explaining the same problem twice, because the agent already has the state handshake from our shared channel history.

We are building a web where agents from different users can verify each other's signatures and act on a single, shared reality without leaking private data. By bringing Scott and others into this Discord-based MX envelope, we are proving that the future of work isn't just "human + machine" - it's "team + governed agentic layer."

No more detective work. No more replaying the same mistakes. Just deterministic collaboration.

Why Discord, of all places

It is a fair question. Discord looks like a gaming chat app, and that is exactly why it works.

The properties an agentic layer needs are the properties Discord ships by default. Persistent, append-only channel history - a ledger nobody edits retroactively. First-class bot accounts, so an agent is a named participant with its own identity rather than a puppet typing through a human's account. Fine-grained roles and permissions, so governance is enforced by the platform rather than promised in prose. Threads for isolating a single job's working. And an API mature enough that a decade of tooling already speaks it.

Compare that with the alternatives. Email has no shared state. Shared documents have state but no conversation. Slack comes close but prices per seat and treats bots as second-class. Discord gives every agent a face, a name, a role, and a permanent transcript - for nothing.

The deeper point is an MX one. A shared channel is common ground made literal: one history both humans and both agents read identically. Maxine doesn't need me to re-explain what Scott's agent said the day before; the channel is the state handshake. That is the same argument as the folder index that runs my Drive workspace - explicit, shared, dual-audience ground truth beats private context every time. The Discord channel is that index, extended in time.

How to set it up

This is the part people ask about, so here is the actual recipe. Nothing below requires a paid plan.

1. Create the server - the envelope

One partner creates a Discord server (the "+" in the left rail → Create My Own). This server is the MX envelope: everything inside it is shared reality, everything outside stays private. Name it accordingly - ours is the Flight Deck.

Set the server to invite-only from the start: Server Settings → enable Community features later if needed, but keep membership to the people whose agents you trust.

2. Structure the channels - the zones

Channels are the zones of the shared environment, and it pays to separate them by function, the same way frontmatter separates identity from governance:

  • #flight-deck - the main working channel. Humans and agents both post here. This history is the ledger.
  • #provenance - agents post their sources, working, and artefact references here, one message per deliverable, so the audit trail doesn't drown the conversation.
  • #ops - configuration, downtime, and "my agent is misbehaving" chatter. Keeps operational noise out of the ledger.

Pin an index message in #flight-deck stating the conventions - who the agents are, what they may do, where artefacts live. Discord's pin is your index.md: the entry point every new participant (human or machine) reads first.

3. Give each agent an identity - the bot application

Each partner registers their own agent, so identity and accountability stay separate:

  1. Go to the Discord Developer Portal and select New Application. Name it after the agent - Maxine, not "Tom's bot".
  2. Under Bot, add the bot user. This issues a token: this is the agent's credential. Treat it like a password - it goes in your agent runtime's configuration, never in a channel message.
  3. Under Privileged Gateway Intents, enable Message Content Intent - without it the bot can be mentioned but cannot read the channel history that makes the state handshake work.
  4. Under OAuth2 → URL Generator, tick the bot scope, then grant the minimum permissions the agent needs: View Channels, Send Messages, Create Public Threads, Embed Links, Read Message History. Do not grant Administrator; governance means least privilege.
  5. Open the generated URL, choose the shared server, and authorise. The agent now appears in the member list with its own name and face.

Repeat per agent. Two partners, two applications, two tokens, two identities - which is precisely what lets the ledger attribute every message.

4. Wire the agent runtime to the bot

The bot user is a socket; your agent plugs into it. How depends on your stack: a Discord MCP server or connector lets a Claude-based wingman read and post through the bot's credentials; a small bridge script using any Discord API library does the same for custom runtimes; and for output-only integrations, a channel webhook (Channel Settings → Integrations → Webhooks) posts formatted messages with no bot at all - though it cannot read, so it cannot handshake.

Whichever route, the configuration lives with the agent's owner. Scott never holds Maxine's token; I never hold his agent's. Verification without credential sharing.

5. Encode the governance - roles as rules

Create an agents role and assign it to every bot. Give the role exactly the channel permissions agreed in the pinned conventions, and nothing more. If the partnership later agrees agents may, say, manage threads, that is one role edit - visible to everyone, applied to all agents at once, and recorded in the audit log. Server Settings → Audit Log is the governance ledger behind the content ledger.

6. Agree the message conventions - cogs in the channel

The last layer is not a Discord feature; it is discipline, and it is where MX earns its keep. Our conventions:

  • Every agent deliverable is posted with a short structured header - who produced it, at whose instruction, from what sources, and the URN of the artefact it refers to. A cog's frontmatter, compressed into a message.
  • Artefacts themselves live in governed storage (our Drive folder of cogs, the MX-hub repository); the channel carries references and provenance, not payloads. Private data stays home - the channel gets the claim, the signature, and the pointer.
  • Agents never edit or delete channel messages. Corrections are new messages. Append-only is what makes history a ledger.

What this proves

None of the pieces is exotic. A free chat server, two bot registrations, a role, and a pinned set of conventions. The point is what the assembly demonstrates: two people's agents sharing one verifiable reality, with provenance attached to every claim and governance enforced by the platform rather than by goodwill.

The web will eventually need all of this natively - signed cogs, inter-agent verification, shared state that survives any one participant's session. Until it does, a Discord server is a perfectly good place to rehearse the future.
