MX Gathering Notes: A Guide for the Internal Team

29 April 2026 · Tom Cranstoun · 5 min read

This post is for the internal team only. It is not public and will not be indexed. It exists to give you the context you need before I submit these notes to The Gathering for community review.

I want you to read the notes, ask questions, and tell me if anything is unclear or wrong before they go out. That is the whole point of this document.

What The Gathering is

The Gathering is an open community formed around the idea that the web needs agreed vocabulary for machine-readable metadata. Think of it as a lightweight RFC process, similar in spirit to how IETF works, but focused on the gap between what established standards (Schema.org, Dublin Core, WCAG, OpenAPI) cover and what is left unspecified for AI agents and automated workflows.

The community review process works like this: a note author publishes a draft, the community reads it, leaves comments or raises issues on GitHub, and the note is revised until it reaches rough consensus. Once ratified, a note becomes part of the shared vocabulary anyone can implement.

None of my notes are ratified yet. They are drafts. That is the point: I am seeking review, not announcing a finished standard.

All ten notes are in the public GitHub repository at github.com/ddttom/mx-shared-gathering under the MIT licence. Anyone can read them, fork them, or comment.

Reading order

The notes are not independent. They build on each other. Read them in this order:

  1. Start with Field Definition Pattern - it sets the structural rules that every other note follows when defining a field. If you skip this one, the others will feel arbitrary.
  2. Read Core Metadata next - this is the vocabulary floor. Everything else is optional layering on top of it.
  3. After those two, read the remaining notes in any order that interests you. If you work with code, Carrier Formats and Cogs are probably most relevant. If you work with content governance, Provenance and Workflow Contracts. If you deal with accessibility or compliance, Document Accessibility.

The notes

Each entry below links directly to the note on GitHub. Click the link to read the full draft.

1. Field Definition Pattern

The structural template that every field definition in the MX framework must follow. It specifies exactly what a field entry needs: a heading, a property table (name, type, cardinality, conformance level), definition prose, and an example. Read this first.

Read draft-field-pattern.md on GitHub

2. Core Metadata

Defines the vocabulary floor for any text-bearing document - markdown, HTML, YAML sidecar, or similar. Zone 1 covers identity fields at the top level (title, author, date, language). Zone 2 covers operational fields in the mx: namespace (status, content type, audience, tags). Three conformance levels: MX Core, MX Standard, MX Complete.

Read draft-core-metadata.md on GitHub

3. Cogs

An optional layer on top of Core Metadata. A cog is a .cog.md file with structured YAML frontmatter that makes a document navigable, composable, and runnable by agents. Defines relationship fields (partOf, buildsOn, requires, refersTo) and the magic-header HTML comment format. Documents do not need to be cogs to carry MX metadata - cogs are for the subset of documents that need to be agent-executable.

Read draft-cogs.md on GitHub

4. Extensions

Defines the namespace policy for the framework. Three tiers: standard fields (no prefix, owned by The Gathering community); public extensions (x-mx-, owned by CogNovaMX); private extensions (x-mx-p-, for organisation-internal use). The prefix tells you who governs the field.

Read draft-extensions.md on GitHub

5. Provenance

Attribution, trust, and verification vocabulary. Five groups: attribution fields (who created it, where it came from), quality and trust fields, maintenance fields, decision record references, and migration fields. If you need to track where a document came from and whether it can be trusted, this note covers it.

Read draft-provenance.md on GitHub

6. Carrier Formats

How MX metadata travels across file formats. Each format has a different mechanism: YAML frontmatter for markdown, <meta> tags for HTML, JSDoc comments for JavaScript, block comments for CSS, shell script header comments, XMP sidecar files, and so on. The note also defines code-specific provenance vocabulary. Deliberately out of scope: function signatures, API surfaces, and test metadata - those belong to JSDoc, docstrings, and OpenAPI.

Read draft-carrier-formats.md on GitHub

7. Workflow Contracts

Optional fields for cogs that declare an executable workflow - an approval process, a review chain, or a procedural sequence. Defines fields for thresholds, approvers, target environment, and procedures. All fields are conformance level MAY; this note only applies to documents that explicitly declare themselves as workflow contracts.

Read draft-workflow-contracts.md on GitHub

8. Contract Fingerprinting and Signing

Specifies how a cog can be signed to attest provenance and integrity. Defines two fields: contractFields (the top-level keys covered by the signature) and metadataFields (excluded keys). The fingerprint is a deterministic canonical JSON projection hashed with SHA-256. Signing is optional - it attests that a document has not been altered, not that its contents are true.

Read draft-contract-fingerprinting.md on GitHub

9. Agent Directory Discovery

How hosts should expose agent-directory files (such as llms.txt) so AI training pipelines, search indexers, and agent crawlers can find them reliably. Three-layer conformance: Level 1 is HTML transport (the file is served as text/html or linked as a resource), Level 2 is sitemap inclusion (the file appears in sitemap.xml), Level 3 is resilience (fallback mechanisms if the primary URL fails). This note is directly relevant to our current llms.txt implementation.

Read draft-agent-directory-discovery.md on GitHub

10. Document Accessibility

How publishers declare and demonstrate accessibility of non-HTML document carriers - primarily PDF, with DOCX and EPUB informative - so AI systems, search engines, and assistive technology can reach them on equal terms. Motivated by the EU Accessibility Act and regulatory gaps not covered by existing HTML-focused standards. References ISO 14289 (PDF/UA), ISO 32000, WCAG 2.1, and EN 301 549.

Read draft-document-accessibility.md on GitHub

What to do

Read the notes in the order above. As you read, note anything that:

  • Does not make sense or needs a clearer explanation
  • Contradicts something we already do in practice
  • Is missing - a use case or field that should be there but is not
  • You think will be questioned by the community when it goes for review

Send your feedback directly to Tom before the community submission. You can also raise issues on the GitHub issues tab if you prefer to work that way.

The goal is to submit these as a coherent set, not one at a time. So the sooner you have read them and flagged questions, the sooner I can revise and submit.
