Self-Healing Code: How Dreams, Inspirations, and Memory Turn a Repository Into a Learning System

27 June 2026 · Tom Cranstoun · 9 min read

Most repositories are static. You clone them, build them, run them, commit to them. They don't improve. They don't learn. They accumulate debt.

MX-Hub is different. It has three mechanisms that make a repository self-aware, self-checking, and self-healing: Dreams that mine for improvements in the background, Inspirations that repair drift on demand, and Memory that travels with the repository so new operators inherit what everyone has learned.

Together, these make a repository that gets smarter every session.

The Problem: Repository Drift

Repositories grow entropy. You establish a pattern - "always validate links before commit". A month later, a link breaks silently. You establish a standard - "field names must be consistent". Months later, you find three variants in use. You establish a linting rule - "no em-dashes in markdown". Six months later, someone bypasses it in an emergency and forgets to clean up.

Rules live in prose. Prose is not machine-readable. Prose doesn't enforce anything. Prose is where rules go to rot.

Most teams accept this. They accept that repositories drift toward inconsistency. They do quarterly "tech debt sprints" to clean it up. They document standards in a README that nobody reads.

MX-Hub doesn't accept it. The architecture rule is:

Determinism over inference: a check a script can do, a script does.

If a pattern repeats, it belongs in a script with a test. If a rule can be verified mechanically, it is verified mechanically - not by memory, not by goodwill, not by cross-team Slack messages. The script is the source of truth. The prose documents what the script does, never the reverse.

But scripts only prevent new drift. What about the drift that already exists? What about inconsistencies that crept in before the rule was written? That's where Dreams and Inspirations come in.

Dream: The Silent Background Miner

A Dream is a silent, background LLM process that mines a repository for improvements.

Think of it as a 3am operation. You're asleep. A model wakes up, reads the whole repository, identifies patterns that don't match the established rules, generates fixes, and writes them to a temp folder. Then it goes to sleep again.

In MX-Hub, Dreams are configured in datalake/dream-files/. They run in the background on a schedule (or on-demand). Each one scans for a specific class of problem:

  • Missing MX frontmatter: finds markdown files that should carry metadata but don't
  • Broken links: identifies references to files that no longer exist
  • Inconsistent field definitions: discovers where terminology drifted
  • Stale descriptions: spots where a doc's summary no longer matches its content

The Dream produces a report: "Found 47 instances of em-dashes in blog markdown. Found 12 broken internal links. Found 3 field definitions that conflict with the canon."

The Dream doesn't commit anything. It doesn't make decisions. It surfaces findings.

That's where Inspirations come in.

Inspiration: The Deterministic Repair Actor

An Inspiration is the operator-facing counterpart to a Dream. It's a foreground, deterministic actor that the operator runs explicitly to repair a specific class of drift.

Unlike a Dream (which is silent background work), an Inspiration is:

  1. Explicit - the operator runs npm run inspire -- em-dash-remediation to trigger it
  2. Deterministic - it follows a clear algorithm, not inference
  3. Reviewable - it commits one change per bounded unit, narrates as it goes
  4. Scope-enforced - it refuses to touch anything outside its declared write boundary
  5. Operator-controlled - it never pushes. The operator reviews, then decides to push

The runner harness (scripts/lib/inspire-runner.cjs) enforces this at two layers. First, it limits what the inspiration can write (a filesystem boundary). Second, after the inspiration runs, it snapshots the tree - if the inspiration tried to write outside its scope, the snapshots fail to match, and the commit is refused.

This is Human-in-Command: the machine fixes the problem, the human signs off.

From Temporary to Permanent: Promotion

Here's where it gets smart. Inspirations can be temporary or permanent.

A temporary inspiration is created on-the-fly when you run npm run inspire -- fix-new-issue. The system generates a script that fixes that one issue, runs it once, commits it, then forgets about it. The script lives in datalake/dream-files/inspirations/temp/ and is git-ignored.

But the system is watching. A decorator called Wittgenstein (named after Ludwig Wittgenstein's "whereof one cannot speak, thereof one must be silent" - it only counts what it can see in the graph) inspects temporary inspirations for reuse. Every time an inspiration is used more than four times, Wittgenstein flags it for promotion to full class.

Promotion means: this pattern is real enough to codify. Move it from the temp folder to scripts/inspirations/, give it tests, document it, make it a first-class repair actor.

This is the repository learning. What started as a one-off fix, used four times, becomes part of the permanent infrastructure.

Memory: Practice That Travels With the Repository

Here's the third mechanism: Memory.

When you clone a repository for the first time, you don't just clone code. You clone accumulated practice. You inherit lessons everyone before you has learned.

Memory lives in .claude/memory/ and is checked into the repository. It's portable. The four types of memory that travel are:

  1. Feedback - decisions made and why. "We don't use em-dashes. Here's why and what broke when someone tried."
  2. Project - operational knowledge specific to this repo. "Build the indexes on a fat clone on main, never on branches - here's what happens if you try."
  3. User - individual operator profiles and preferences. "Claude prefers terse responses. Claude uses the Sonnet model for reviews."
  4. Reference - pointers to external resources. "The Gathering standard spec lives here. The MX Manifesto lives there."

When you first clone the repository, a deterministic merge happens (the contract is scripts/lib/memory-sync.cjs). Your local device memory (the working copy on your machine) converges with the repo-tracked memory (what everyone has committed). The rule is: union by file, newest modified: timestamp wins.

Deletions are handled deliberately, not silently. You don't delete a memory file; you add an entry to RETIRED.md saying why it's gone. That way, if someone clones an old branch, they see what was retired and why - not a mysterious absence.

This is what onboarding should be. You don't read a fifty-page operations manual. You clone the repo. The memory syncs. The next time you run a command, hooks remind you of the patterns you need to know. By session three, you've internalized the practice.

How They Work Together

Here's the full loop:

  1. Day 1: You establish a rule in prose: "all blog posts should have a canonicalUri field".

  2. Day 2: You write a script that enforces it: a validator that scans every blog post on push and refuses to land one without canonicalUri.

  3. Day 3: The validator catches a violation. An operator comes to you - "why is this post rejected?" You explain. The fix goes into a temporary inspiration (auto-generated, run once).

  4. Day 10: Someone clones the repo on branch with an old blog post, no canonicalUri. They encounter the same issue. The system detects the temporary inspiration running again. Use count: 2.

  5. Day 17: Another operator, another branch, same issue. Use count: 4. Wittgenstein flags it for promotion.

  6. Day 20: You review the temporary inspiration, confirm it's a real pattern, move it to scripts/inspirations/canonicaluri-backfill. You add tests. You document it.

  7. Day 21: The next time someone clones and encounters the issue, they run npm run inspire -- canonicaluri-backfill, it fixes all instances in one deterministic run, commits per-file, and the problem never emerges again.

  8. Day 22: The first session operator adds a memory entry to project type: "canonicalUri on every doc - here's why and how the backfill works". New operators who clone the repo sync that memory on day one.

The repository has just healed itself and learned the lesson so everyone else can skip the pain.

What This Enables

The architecture enables three outcomes:

Self-aware: The repository knows what it is. It keeps machine-readable models of itself (the cog registry, the routing registry, the documentation graph, the MX graph). It can answer "what changed?" and "what's inconsistent?" because it asks itself, not because humans remember.

Self-checking: The repository verifies its own rules. Every commit, every push, every session runs a suite of deterministic gates. The gates aren't opinions - they're scripts. If a gate fails, there's a specific, fixable problem, not a gray-area judgment call.

Self-healing: When drift is detected, repair is deterministic. Inspirations don't guess - they follow an algorithm. They're narrowly scoped so nothing gets clobbered. They commit reviewably so humans stay in command.

And critically - knowledge travels. Every operator who figures something out commits it as a memory entry. The next operator inherits it. The system doesn't regress.

The Rules That Make It Work

Three rules hold this together:

  1. Determinism over inference. If a check can be scripted, it is scripted. If a pattern repeats, it's codified. Prose describes what the script does, never the reverse.

  2. Machine-readable self-description. The repository models itself. Every COG carries metadata. Every generated index is byte-identical on re-runs. The system can ask itself questions without human mediation.

  3. Human-in-Command. No repair commits without explicit human approval. Machines mine, machines suggest, machines draft - but humans decide. The push is always the operator's, never automatic.

The Outcome

What this produces is unusual: a repository that gets better with use. Not by accident or cleanup sprints, but by design. Every time someone encounters a problem, they can fix it once and promote it to permanent. Every time they learn something, they can record it in memory so the next person doesn't re-learn it.

You clone MX-Hub. The memory syncs. You read the Reminders (key decisions that need to be in your head). You run a command. Hooks remind you of the patterns. By session three, you're operating at the level of operators who've been here for months.

That's what Dreams, Inspirations, and Memory do. They make repositories that heal themselves and teach.
