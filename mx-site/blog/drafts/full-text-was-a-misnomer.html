Full-Text Was a Misnomer

4 July 2026 · Tom Cranstoun · 5 min read

I asked my repository's own search for a phrase I knew was in one of its documents. I had written the phrase. I could see it on the screen in the file. The search came back empty.

The search was called full-text. It was not full-text. And the gap between the name and the truth is exactly the kind of thing a machine cannot see through.

What the search was actually reading

My repository keeps a graph of itself: a map of every file, what kind it is, how it relates to the others, what it is for. An agent can query that graph, and one of the queries is fulltext. The name promises what it sounds like: search the full text.

When I looked at how it worked, it was reading the labels, not the contents. For each file it pulled the title, the description, the tags, the one-line purpose, the handful of fields at the top that describe the file. Then it read the body once, counted the words for a statistic, and threw the body away. Every word of actual prose, the thing I was searching for, was never in the index at all.

So fulltext only ever matched the writing on the box. My phrase was inside the box, in the body of the document, where the search had never looked. Empty was not "this phrase is not here". Empty was "this phrase is not on the label", and the search had no way to tell me which of those it meant.

The gap is invisible, which is the problem

Indexing the labels is not a scandal on its own. Metadata is small, structured, and cheap to hold; bodies are large and messy. Starting with the frontmatter is a reasonable first cut, and for finding a file by what it is about, it works well.

The fault was the name. Calling it full-text told every reader, human and machine, that a miss meant absence. A person might eventually feel the wrongness, the way you do when a search for a word you can see returns nothing, and go and check by hand. A machine has no such itch. It reads "full-text search: no results" and concludes the text is not there. It moves on, confident and wrong, and the mistake is invisible because nothing in the answer admits the search only skimmed the surface.

This is the same quiet dishonesty I wrote about in the flag that rewrote my search: a tool reporting more certainty than it earned, in a way the reader cannot detect from the answer alone. Name a thing full-text and it had better read the full text, or the name itself becomes a small lie the machine will believe.

Reading the body, honestly, and where it lives

The fix is the obvious one: index the bodies for real, so a search for a phrase looks where the phrase actually is. We have written down how we will do it.

The interesting part is not the indexing; it is where the index lives. A real full-text index over an entire estate of documents is large, and it changes every time any document changes. Commit a thing that big and that restless into the shared repository, and you spend the rest of your life fighting the churn. So it will not go there. The body index will be a local artefact: it lives on the machine that builds it, rebuilt from whatever files are present, and it never travels with the repository.

If you have read fat clones, thin clones, and the strawberry problem, you already know why that is not a compromise but the correct design. The shared truth is the documents. The search index is a derived view an environment builds for its own convenience, and a derived view is allowed to describe exactly the slice its machine can see, precisely because it never claims to speak for everyone. A partial checkout gets an honest index of its own files. It does not, and must not, pretend to index the parts it never fetched.

There is a bonus once a machine can read the bodies. It starts to notice when one document names another, a reference the frontmatter never declared, and the map of the estate gets richer without anyone hand-drawing the new lines. But that is a story for when it is built.

Say what it does

The lesson is small and it is the same one MX keeps arriving at from every direction. What a machine can find in your content is a promise you make, whether you meant to or not. If you label a search full-text, you have promised the full text; deliver it, or name the thing honestly so a miss means what the reader thinks it means.

The search did not have to mislead me. It misled me because its name claimed more than it did, and a machine has no way to check a name against a behaviour. So we are making the behaviour match the name. The cheapest honesty in the whole system is to call things what they are, because the machine is going to take you at your word.
