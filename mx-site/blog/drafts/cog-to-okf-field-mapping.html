A COG Is an OKF Concept Document, With the Trust Added

13 June 2026 · Tom Cranstoun · 6 min read

In the last post I said a cog can be expressed as a concept in Google's Open Knowledge Format, so MX rides on top of OKF rather than competing with it. A claim about formats is worth nothing until you show the fields line up, so here they are.

I've checked every correspondence below against OKF SPEC.md and against real production OKF documents, including Google's own GA4 BigQuery bundle and community implementations. Treat this as the settled mapping.

The reserved fields

OKF reserves a small set of frontmatter fields and leaves everything below them to the producer. Here's each one against its MX equivalent.

OKF reserved field MX / COG field Note
type type (and cogType for the cog kind) Same field, at the top level. It answers the same question in both: what is this. A cog also declares whether it merely describes (info-cog) or acts (action-cog).
title title Direct. Same field, same job.
description description Direct.
resource resource Same field, at the top level. It's a single optional URI: the canonical external URL of the one asset the concept describes, such as a BigQuery table API URL or a web page URL. It's absent for abstract concepts such as playbooks. Don't read it as MX's refersToExternal, which lists the external sources a document cites as evidence. resource says what the document is about and refersToExternal says what it draws on, so the two never share a value. The servedAt field (where this document is published) has no OKF equivalent. It's a valid MX addition, since OKF identifies documents in a bundle by file path rather than by a published URL.
tags tags Direct, at the top level. Plain array, no leading hash.
timestamp created and modified OKF carries one timestamp; MX separates first-authored from last-modified, both ISO 8601. An OKF consumer reading one timestamp can take modified.

Nothing here makes you choose. A cog already carries type, title, description, tags and, where it describes an asset, resource, all at the top level under OKF's own names. The same file is a valid OKF concept, with no change to the cog itself.

The graph, two ways

OKF turns a directory into a graph with ordinary markdown links between concepts in the body. MX keeps those links, so the two stay compatible, and also records each edge as a typed field in the frontmatter: refersTo, buildsOn, relatedTo. Any OKF consumer walking the markdown can still follow them. A machine reading the frontmatter can traverse the same edges and know the kind of each one without parsing prose. OKF gets its graph for free, MX adds a typed, machine-traversable layer over it, and carrying both costs a producer nothing.

The fields OKF has no equivalent for

Map every reserved OKF field to a cog and some cog fields are left over. They have no OKF counterpart under any name, because OKF doesn't reach into the trust question.

MX / COG field What it answers Aligns with
canonicalUri Where does this live, as a stable identity, regardless of where the copy was found -
author Who wrote it -
proofOfAuthorship I made this, and I can prove it W3C Verifiable Credentials, Signed Exchanges
integritySignature What you read is what was written RFC 9421 HTTP Message Signatures, Subresource Integrity
provenancePedigree Where did this come from, and through whom -

author and canonicalUri are mild gaps. They're identity and a stable address, and an OKF producer can always add them outside the reserved set. The real gap is the genuineness family, proofOfAuthorship, integritySignature, and provenancePedigree, and it's deliberate. OKF tells an agent what to read, while these fields tell it whether to believe it. That's what MX adds and what REGINALD records as a dated, verifiable entry. Leaving them out isn't a deficiency in OKF, which chose its scope, and this half of the stack is where the work has always been.

A worked shape

Here's a real OKF concept document from Google's own GA4 BigQuery bundle, as published in the knowledge-catalog repository:

---
type: BigQuery Dataset
resource: https://bigquery.googleapis.com/v2/projects/bigquery-public-data/datasets/ga4_obfuscated_sample_ecommerce
title: BigQuery sample dataset for Google Analytics ecommerce web implementation
description: A sample of obfuscated Google Analytics BigQuery event export data...
tags:
- ecommerce
- web analytics
- Google Analytics
- BigQuery
- public dataset
timestamp: '2026-05-28T22:49:59+00:00'
---

resource holds a canonical API URL for the underlying asset, and there are no provenance, authorship, or integrity fields. It's a well-formed OKF concept.

Here's the same thing as a cog. OKF readers still get the fields they expect, and MX-aware ones find the rest:

---
type: BigQuery Dataset
resource: https://bigquery.googleapis.com/v2/projects/bigquery-public-data/datasets/ga4_obfuscated_sample_ecommerce
title: BigQuery sample dataset for GA4 ecommerce
description: A sample of obfuscated GA4 BigQuery event export data from the public dataset.
tags: [ecommerce, analytics, bigquery, public-dataset]
author: Tom Cranstoun
created: 2026-05-28
modified: 2026-05-28
mx:
  servedAt: https://example.com/cogs/ga4-ecommerce-dataset
  canonicalUri: https://example.com/cogs/ga4-ecommerce-dataset.cog.md
  proofOfAuthorship: { ... }
  integritySignature: { ... }
---

The top block is a valid OKF concept. The bottom block is the same one, still OKF-readable, now with identity, a published URL, and the trust signals OKF leaves to you. In practice, OKF-compatible means you don't pick one format: you emit the reserved fields and add the rest.

For abstract concepts, such as a playbook, a runbook, or a business process, OKF's own spec says resource should be absent. A cog follows the same rule and leaves resource out. It can still list the sources it cites in refersToExternal, and either way the governance block holds the full trust layer.

Who decides what the added fields mean

The mapping also shows who's in charge of what. OKF defines the reserved fields, which means Google does. Whoever the producer answers to defines the fields added on top. For MX that's The Gathering, the community body that governs what each field means and how it's encoded, independent of any single vendor. One vendor can hold the interoperability side, but none should own the meaning of the trust layer. That split is deliberate, and it's the subject of the post that started this.
