Anthropic, Publish the COG

11 July 2026 · Tom Cranstoun · 5 min read

The previous posts in this series documented a vocabulary gap between Claude Code and Claude Web, and a capability contradiction within a single Claude Web response. Both failures are preventable. Neither requires a new model, a new product, or a significant engineering investment.

They require one thing: a published, machine-readable capability declaration for each Claude surface.

This post is a direct ask to Anthropic to produce and maintain those declarations.

What the problem costs

Right now, every user who moves between Claude surfaces discovers the vocabulary gaps through friction. They learn that "question tool" works in Claude Code but not in Claude Web. They learn that "open Drive" produces a link rather than a navigation. They learn these things by being confused, sometimes more than once.

Multiply that across Anthropic's user base and the cost is significant - not in any single incident, but in aggregate trust. Every time a surface says it can't do something and then does it, a user learns to treat the surface's self-description as unreliable. That erosion compounds. It's the kind of problem that doesn't show up in any single support ticket but shapes how people feel about using the tools.

For developers building on the Claude API, the cost is more concrete. A pipeline that routes tasks between surfaces needs to know what each surface calls its capabilities. Without declared vocabulary, the developer has to probe each surface empirically, document the results privately, and update that documentation every time Anthropic ships a change. That's engineering overhead that a published capability declaration would eliminate entirely.

For agents operating in pipelines - one Claude surface calling another, an orchestrator routing tasks - the cost is silent failure. An agent that hits a naming boundary has no way to distinguish "this surface doesn't have this capability" from "this surface has this capability but calls it something else." It stops. Or it continues on a false assumption. Neither outcome is good.

What the ask is

The ask has three parts.

Publish a capability COG for each Claude surface. Claude Web, Claude Code (VS Code), Claude Desktop, Claude for iOS, Claude for Android, the API - each is a distinct surface with distinct capabilities. Each should have a machine-readable declaration covering the three layers: what it knows, what it can do, and what it will do. The declaration should include tool names with cross-surface aliases where they exist.

Version and date the declarations. Capabilities change. The declaration for Claude Web on one date is not the declaration for Claude Web six months later. Each version should carry a date and a version number. Each change should be documented. Users and agents need to know whether the declaration they're reading is current.

Publish the declarations at a stable, predictable URL. The obvious home is alongside the existing llms.txt infrastructure. A declaration at claude.ai/capabilities.cog is a declaration every agent can find without being told where to look. Stability matters: a URL that changes breaks every agent that has cached it.

None of this requires a new standard. The COG format is published under the MIT licence, so anyone may implement it, and it will be donated to The Gathering as an open standard. Anthropic can adopt it, extend it, or use it as a reference for whatever format they prefer. The format matters less than the act of publishing.

Why now

Anthropic has already done most of the work. Model cards exist. System prompt documentation exists. The Claude usage policy exists. The capability information is known - it just isn't published in a form that agents and users can query before a session starts.

The gap between what exists and what's needed is narrower than it looks. A capability COG for Claude Web is a structured summary of information Anthropic already holds. The engineering task is format conversion and maintenance, not original research.

The reason to do it now is that the agent pipeline problem is already here. Claude surfaces are already being called from other Claude surfaces. Orchestrators are already routing tasks between them. The vocabulary gaps that cause human friction will cause agent failures. The window to fix this before it becomes a significant reliability problem is open, but it won't stay open.

What good looks like

A user starts a session in Claude Web and the session reads a capability COG before the first prompt. It knows what tools are available, what they're called, and what the surface won't do. When the user says "use the question tool," the session maps it to ask_user_input_v0 and proceeds without confusion.

An agent in a pipeline queries the capability COG for the target surface before routing a task. It knows whether the surface has web search enabled. It knows whether it can render clickable UI. It knows the precise vocabulary to use. It routes correctly, the first time, every time.

A developer building on the API finds the capability COG in the documentation alongside the model card. They know what changed in the last version. They know what to expect from each surface. They write their integration once and it stays correct.

That's the outcome. The path there is one engineering task: publish the declarations, version them, and put them somewhere stable.

Anthropic, publish the COG.
