Same Question, Five Answers

9 October 2026 · Tom Cranstoun · 8 min read

Part of Watching the Machines, a record of how the companies shipping AI treat the people who own the devices and write the content.

macOS 27 ships with a command called fm. It's Apple's Foundation Models CLI, installed at /usr/bin/fm, and it talks to the language model Apple now puts on every supported Mac. No account, no API key, no network call. I typed the example from its own help screen, fm respond 'what is swift?', pressed the up arrow, and ran it again. Then three more times.

~ fm respond 'what is swift?'
Swift is a programming language developed by Apple.

~ fm respond 'what is swift?'
Swift is a programming language developed by Apple for building software. It is designed to be fast, safe, and easy to use, especially for developing apps on iOS, macOS, and other Apple platforms.

~ fm respond 'what is swift?'
Swift is a programming language developed by Apple, designed for safety and performance. It is used for developing applications, particularly for macOS, iOS, watchOS, and tvOS.

~ fm respond 'what is swift?'
Swift is a programming language developed by Apple for building software, particularly for macOS, iOS, watchOS, and tvOS. It is designed to be fast, safe, and easy to use, with a focus on performance and simplicity.

~ fm respond 'what is swift?'
Swift is a programming language developed by Apple, designed for writing fast, safe, and efficient software. It is particularly well-suited for iOS, macOS, watchOS, and tvOS development.

They're all right. They just don't agree with each other.

What Stayed and What Moved

Read them side by side and you can see which parts hold. Some facts turn up every time: Swift is a programming language, and Apple made it. Everything else moves. The first answer is a single sentence and names no platform at all. The second names iOS and macOS and waves at the rest. The third, fourth and fifth list four platforms, though not always in the same order. Swift is "fast, safe, and easy to use" twice, "designed for safety and performance" once, and "fast, safe, and efficient" at the end. The model repeats what every source says and improvises the rest.

None of this is a fault. A language model picks each word from a ranked list of likely next words, and by default it doesn't always take the top one. That small dose of chance is deliberate, because it stops the writing from sounding mechanical. In a chat about Swift that's harmless. It turns into a problem the moment someone needs to check what was said.

You Can't Optimise a Dice Roll

That same chance is why generative engine optimisation is so hard to pin down. GEO sets out to get a page cited, and a citation is part of what moves. When one prompt on one machine gets five different replies inside a minute, a tactic that earned a mention in one reply can lose it in the next with nothing on the page changed. Nobody broke anything. The dice came up differently.

I've made the wider case in GEO Is a Tactic. MX Is the Specification., the post on why chasing citations needs a foundation underneath it. Those five replies show what that foundation does. All of them agreed on what every source states plainly, and the drift came where the model was left to fill gaps. MX works on those gaps by adding context the model would otherwise have to guess: what the page is, who wrote it, when it last changed, which version this is, and its intended use. No publisher can make a model deterministic. A page that declares more leaves the dice less to decide.

You Can't Ask Again

Here's the case that worries me. An assistant built on a model like this one tells a customer something about your product, and they act on it. A month later there's a dispute about what they were told. The obvious move is to put the same question to the same assistant and see what comes back.

It won't work, and the transcript shows why: the same question, on the same machine, within the same minute, produced five different answers. Re-asking doesn't recover what the customer saw. You get a new one, which shows the model can say something like the original. What's in dispute is whether it actually did.

If nobody saved the original reply when it was given, there's no getting it back.

The Switch Exists, and It Isn't Yours

Apple does provide a way out. fm respond takes a --greedy flag, which tells the model to always take its most likely word. Apple's developer documentation on sampling says greedy "always chooses the most likely token". I reran the question with it and hashed each result. The hashes all matched, byte for byte.

That text is also identical to my fourth default run. That one just happened to pick the top word at every step, and the flag locks that path in.

Repeatability, then, is a switch, and two things limit it. The first is who holds it. The developer of the app sets the sampling mode. The person asking never sees that setting, and neither does the publisher whose page supplied the facts. The second is that greedy repeats only against the same model build. Apple updates the on-device model with the operating system, so the same prompt after an update can return a different answer, just as fixed as the old one. The command doesn't help you pin it down either: fm respond -v reports that it's "Creating session with default instructions" and never names the model version that answered.

Greedy gets you the same reply on one machine and one model version. Months later, after an update, it may not.

What a Record Has to Carry

If you can't ask again, the answer has to carry its own evidence from the moment it's produced. For a machine-generated answer, that means writing down, at the time:

  • the prompt and any added instructions
  • the exact answer
  • the model and its build
  • the date
  • the sampling mode
  • the pages the model read, and their versions

Whoever runs the model owns everything on that list except the pages. The pages are where publishers come in, and they're the part most often missing. An assistant that read your page can only record what your content declared about itself. If the page declares who wrote it, when it last changed, and which version this is, the record can point at a specific state of your content. If it declares none of that, the record can only say that something was read at a URL, and the content behind that URL has probably changed since.

Machine Experience is built for this. MX writes provenance and dates into the file itself, along with its intended use, so the machine reading it can check them, and so can whoever audits that reader afterwards. I hold my own tooling to the same rule: every model call writes to a log, and every generated output keeps a provenance record beside it. Rerunning a model can't show me what it did the first time, so the log has to.

A declared interest. I wrote the books on MX and consult on it, so I have a stake in the practice this column recommends. The runs above are reproducible on any Mac with macOS 27; the method is below.

Method

All runs were made on 9 October 2026 on macOS 27.0.1 (build 26A434), using /usr/bin/fm with its default on-device model, which its help text lists as "On-device Apple Foundation Model".

  • Default sampling. fm respond 'what is swift?', run in succession; the transcripts above are those runs. A second set of the same size, run with --no-stream and hashed with shasum, also produced a distinct output every time.
  • Greedy sampling. fm respond --no-stream --greedy 'what is swift?', five times, each output hashed with shasum. Every hash matched.
  • Model identification. fm respond -v prints the session setup line quoted above and no model build or version.

Where Your Own Content Stands

Nobody will be able to replay what a machine told someone about your business. What survives is what the operator recorded and what you published, so make your half checkable: name the author, date the page, version the content, and declare its purpose in the file itself.
