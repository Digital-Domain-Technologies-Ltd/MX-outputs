The Deploy You Cannot See

2 July 2026 · Tom Cranstoun · 4 min read

We moved a folder. A minute later the whole site was dark. Homepage, blog, llms.txt, sitemap.xml: every URL returned a 404. Here is what happened, why it happened, and the small change we made so it cannot happen the same way twice.

The setup

mx.allabout.network is a static site. Its files used to live inside a git submodule, one repository nested in another. We were part way through a tidy-up: pulling the site's files out of that submodule and into the main repository, so that a fresh checkout could build and serve the site without needing the submodule at all. A good goal, and, we thought, a reversible one. Nothing was being deleted; the files were only moving house.

The mistake

Part way through the move, I pushed the commit that removed the site folder from the submodule's repository. The files were safe in the new location. But within about a minute, the live site started answering every request with 404: Not Found.

Why

The live site is built by Cloudflare Pages, and Cloudflare Pages is connected directly to the submodule's GitHub repository. Every push to that repository triggers a rebuild and a deploy. That connection is a setting in the Cloudflare dashboard. It is nowhere in our code.

That last sentence is the whole story. Earlier, I had looked for a deploy step in the repository's automation, found only read-only checks, and concluded that a push could not reach production. That conclusion was wrong. Cloudflare Pages builds from a repository through its own git integration, which is entirely separate from any GitHub Actions the repository happens to run. Push, rebuild, deploy: all automatic, all triggered by the same commit. Remove the folder the build reads from, and the next build has nothing to serve.

The fix

Fast, once the cause was clear: restore the folder to the source repository, push, and wait about a minute for Cloudflare to rebuild. The site came straight back. No data was lost; the outage was the deploy serving an empty build, not anything gone for good.

The lesson

The coupling you cannot see is the one that bites you. A deploy that lives in a dashboard, not in the repository, is invisible to everyone reading the code, including the person who wrote most of it. So the ordering rule writes itself, and we had it backwards:

When you move what a deploy builds from, repoint the deploy to the new source first, confirm it live, and only then remove the old source.

What we kept

We do not trust ourselves to remember a rule. So we made it mechanical. We wrote a liveness probe, a small script that asks the site's canary pages whether they are serving and reports up or down, and wrapped it in an action that raises an alert when the site is down. The discipline is now a command: run it before a change that touches the deploy, to capture a healthy baseline, and run it again after, to confirm the site still serves. If the second run is red, roll back before doing anything else.

That is the MX argument in miniature. Systems fail at the seams you cannot see: the implicit coupling, the setting in someone else's console, the assumption nobody wrote down. The fix is not to be more careful next time. It is to make the invisible legible and the rule executable, so the knowledge lives in a check a machine runs rather than in a memory a human loses. We turned the deploy coupling into a written note, the liveness check into a command, and the ordering into a rule.

The site was down for a few minutes. What we keep is the check that makes sure the next move is not.
