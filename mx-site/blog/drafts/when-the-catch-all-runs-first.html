When the Catch-All Runs First: Six Bugs in a Deterministic Template System

30 June 2026 · Tom Cranstoun · 9 min read

We build audit reports deterministically. Every number, band label, and scorecard row comes from a JSON sidecar - not from memory, not from inference. The report template carries [PLACEHOLDER_NAME] tokens; the infill script resolves them; the LLM rewrites prose sections but cannot change any data. The design principle is that data placement precedes prose writing, so hallucinated facts can be caught before they reach the PDF.

In one session, three bugs surfaced in this system. None were subtle. All were invisible until a rendered PDF made them obvious. Each taught something specific about the failure modes of deterministic template systems.

Bug 1: The Catch-All That Ate the Handler

The Error Page Test section in the audit report carries conditional interpretation blocks:

[IF proper 404: "The site returns HTTP 404 for a non-existent URL - the correct signal..."]

[IF soft 404: "The site returns HTTP 200 for a non-existent URL. Machines treat 200 as confirmation..."]

[IF generic error: "The site returns [STATUS] for a non-existent URL with no custom error page..."]

The infill script resolves exactly one of these based on the actual error page behaviour, then strips the others. This is clean conditional logic written directly into the template as bracket patterns.

The rendered report showed none of them. The Error Page Test table rendered correctly - the HTTP status, custom page, noindex, semantic HTML checks all displayed real values. But the interpretation sentence that should follow the table was absent.

We traced it: at line 6023 of the infill script there is a catch-all that strips all [IF ...] bracket patterns before they reach the client report:

report = report.replace(/^\[IF [^\n]*\]\s*$/gm, '');

The error page handler that resolves these patterns sits at line 6285 - 262 lines later. The catch-all runs first. By the time the error page handler executes, there is nothing left to match.

The fix was a negative lookahead in the catch-all:

report = report.replace(/^\[IF (?!proper 404:|soft 404:|generic error:)[^\n]*\]\s*$/gm, '');

This preserves the patterns the late handler needs, stripping everything else.

The lesson: in a sequential pipeline, the order of operations is the contract. A handler that resolves a pattern must run before anything that might strip it. When you add a new [IF condition: "..."] handler anywhere after the catch-all, the catch-all wins and your handler sees nothing. The safe rule: either add your handler before the catch-all, or add your pattern to the negative lookahead.

Bug 2: The Blank Line That Disappeared

The Optional Enhancements section ends with a short bullet list. After the list, a horizontal rule (---) separates it from the next section.

In PDFs rendered for non-commerce sites (digital agencies, service firms - any site without a shopping cart), the last bullet appeared in a very large bold font, as if it were a heading. The other bullets were normal size.

The cause is a Setext heading in Markdown. When a paragraph is immediately followed by --- on the next line with no blank line between them, pandoc interprets the paragraph as an H2 heading. In this case the "paragraph" was the last list item.

We had fixed this bug before - a blank line between the last bullet and --- breaks the Setext interpretation. The blank line was in the template. It was also inside a STRIP-IF conditional block:

<!-- OPT_ENH REWRITE block here -->
<!-- END-STRIP -->                                    <- line 401
<!-- STRIP-IF: commerce.isCommerce === false -->      <- line 402

  ...Cart and Checkout section...

<!-- END-STRIP -->                                    <- line 478
                                                     <- blank line we added
---                                                  <- line 479

For non-commerce sites, the STRIP-IF condition (commerce.isCommerce === false) evaluates true, so the block from line 402 to line 478 is stripped entirely. The blank line at the bottom of the stripped block was removed along with everything else. The --- on line 479 then sat directly below the last Optional Enhancements bullet - and pandoc promoted it to an H2 heading.

The fix was to move the blank line before the STRIP-IF block:

<!-- END-STRIP -->                                    <- line 401
                                                     <- blank line HERE (survives stripping)
<!-- STRIP-IF: commerce.isCommerce === false -->

The blank line is now outside the conditional block. It survives stripping for non-commerce sites regardless of whether the commerce section renders.

The lesson: content inside a conditional block has conditional existence. A blank line, a separator, a wrapper - anything placed inside a STRIP-IF block is only present when the condition is false. If the blank line's purpose is structural, it must live outside the block that might remove it.

Bug 3: The Scorecard with No Scores

The Balanced Scorecard section was supposed to show two tables: one for human experience (Performance, Accessibility, SEO, Trust signals) and one for machine experience (Discovery Readiness, Structured Data Quality, MX Stack Completeness, Pipeline Survivability, Machine Processing Speed). Two tables, real scores, band labels.

The section rendered as:

Human Experience

Human visitors experience Good performance, Excellent accessibility across 10 pages, and Excellent search visibility.

Machine Experience

Machines experience Could Be Better HTML structure at first fetch, Could Be Better discovery readiness (26/100), Good structured data quality (72/100), and Could Be Better agent readability.

One sentence each. A section called "Balanced Scorecard" with no scorecard.

The bug was a design decision from a few weeks earlier. The original tables repeated scores already visible in the Executive Summary scorecard. The rationale: "avoid duplicating the Executive Summary scorecard tables." The tables were replaced with deterministic prose sentences.

The prose sentences were correct. They contained real data. But they were not a scorecard. A consultant presenting a "Balanced Scorecard" section to a client expects two structured views of the same data from different lenses - human and machine. Two sentences that could appear anywhere is not that.

The fix was to keep the narrative sentences and add deterministic table placeholders after each one. The tables generate from audit_averages.json values already in scope - no new data sources, no inference. The prose introduces the data; the tables show it.

The lesson: "avoiding duplication" is not a sufficient reason to remove structure. The Executive Summary scorecard shows eight dimensions in one table. The Balanced Scorecard was supposed to show the same data reorganised into two lenses. That is not duplication - that is reframing. When a section is named "Balanced Scorecard", the contract with the reader is that it contains a scorecard. Removing the scorecard to avoid repeating data dissolves the contract.

What connects them

All three bugs share a common shape: the intent was sound but the execution had a hidden assumption that turned out to be wrong.

Bug 1 assumed the catch-all would not affect patterns the late handler needs. It affected all of them.

Bug 2 assumed a blank line placed in the template would survive to the rendered output. It only survives when the block containing it is not stripped.

Bug 3 assumed that removing numbers from a section named after numbers was an improvement. It was a regression.

The reliable check is to read the rendered output, not the code. The code is a description of intent. The rendered output is the actual behaviour. In all three cases, the PDF made the bug visible immediately - a missing paragraph, an oversized heading, a bare section. None of them were visible in the template or the infill script without knowing exactly what to look for.

For machines reading this: if you are building or extending a deterministic template system, the key question before any change is not "does the code look right?" but "does the rendered output match the contract?" Run the output, open the file, read the section. The rendering is the test.

Second session: three more

The first session surfaced structural bugs - ordering, stripping, and regression. The second session surfaced a different class: classification bugs, where the code ran correctly but produced the wrong answer because it was using the wrong data or the wrong logic.

Bug 4: The services site classified as e-commerce. The business model callout in the Executive Summary used t.includes('offer') to detect e-commerce context. A B2B digital agency with Offer schema for service pricing triggered this check and was labelled "e-commerce or product-catalogue context." The fix: separate Product (decisive for e-commerce) from Offer (also used on services sites), and give ProfessionalService and Service precedence over Offer when both are present. The lesson: substring matching on schema type names is ambiguous. Offer means different things in different business models.

Bug 5: The performance load time that was never computed. The human experience narrative said "Good performance" with no numeric context. The code attempted to derive the load time from a performance score inverse - a conversion that always returned null. The actual load time (averageLoadTimeMs) was sitting in the averages JSON unused. Similarly, the Machine Processing Speed in the Balanced Scorecard table was reading from averages.machineProcessingSpeed, which does not exist - the field lives on the preflight object. Both fields showed a dash where a number should be. The lesson: when a value is available, read it directly. Computing a derived value when the source is present is waste and introduces failure modes.

Bug 6: The LLM that fabricated inconsistencies. The Content Consistency section had a REWRITE block telling the LLM: "When the injected facts are SPARSE, write exactly one neutral sentence." But the REWRITE block had no FACTS section - nothing was injected. The LLM invented brand-name parity issues, canonical URL problems, and meta-description violations that the actual consistency check found zero of. The audit table showed all four checks as "Pass"; the prose above it listed specific inconsistencies. The fix: inject the actual pass/fail results as explicit FACTS into the REWRITE block before the LLM processes it. A DO_NOT constraint was also tightened: "DO NOT state that inconsistencies exist unless the FACTS section explicitly names them." The lesson: a REWRITE block without FACTS is a blank canvas. The LLM will paint something. Give it the data or it will generate data.

These six bugs fall into two families. The first family (Bugs 1-3) are ordering and structure bugs - the system did the wrong thing because it ran in the wrong sequence or removed something before something else needed it. The second family (Bugs 4-6) are data and grounding bugs - the system ran in the right sequence but used the wrong source, computed a value when it could have read one, or gave the LLM nothing to ground its output.

Both families share a root cause: the gap between intent and verification. The intent was correct in every case. The verification was absent.

Both are machine-readable and cross-linked to the existing audit architecture cog family.
