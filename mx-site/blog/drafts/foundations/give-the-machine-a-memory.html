Give the Machine a Memory

16 June 2026 · Tom Cranstoun · 5 min read

Every time a machine reads your project, it starts over.

An assistant opens your work and knows nothing about the dead ends you already walked down, the decision you settled last month, or the reason a thing is built the odd way it is. So it infers. It guesses. Sometimes it guesses well, and sometimes it cheerfully repeats a mistake you fixed weeks ago, because nothing in front of it said "we tried that, it broke."

Machine Experience (MX) is the practice of giving machines explicit context instead of making them guess. We usually describe that as metadata on the things you publish: a page, a document, a file that can tell any machine what it is and how to use it. The same idea points inward, at your own work, and it answers a quieter question. What should a machine know before it helps you?

The answer is memory. And memory, written down so a machine can read it, comes in two shapes.

Lessons: What Not to Do Again

The first is a lessons file. A common name for it is LEARNINGS.md.

It holds one kind of entry: a mistake and the rule that prevents it. "We tried X. It broke Y. From now on, do Z." Nothing else. Not a diary, not a feature list, not a record of everything that happened. Only the things that went wrong and what they taught you.

This is the file that stops a machine from walking into the same wall twice. Read it on arrival and the assistant inherits your scar tissue: the workaround that is not obvious, the option that looks right and is not, the order things have to happen in. Skip it and every session pays for the same lesson again.

Understanding: What Things Are, and Why

The second is an understanding log. A fitting name is understand.md.

It holds a different kind of entry: not a rule, but a piece of understanding. What something is. Why it is built the way it is. What you worked out, and when. It is not a changelog. A changelog records what changed in the code, and your version control already does that well. The understanding log records what is now understood about the work, and how that understanding grew.

A machine helping you needs both halves. The lessons file keeps it from making known mistakes. The understanding log gives it the map, so it can answer "why is it like this?" and "what have we figured out?" from the record, instead of reconstructing a guess every session.

Why Two Files, Not One

Because they are different shapes doing different jobs.

A lesson is a rule: do this, never that. It is short, sharp, and timeless, true every time until something teaches you better. An understanding is a model: a description of what is and why. It grows, it gains nuance, and occasionally it turns out to be wrong and is replaced by a better understanding.

Keep them apart and each stays clean. Mix them and you get a document that is neither a reliable rulebook nor a coherent picture.

The Discipline That Makes Them Trustworthy

Both files follow one rule: append only. You add to them. You do not rewrite them.

This sounds small, and it is the whole thing. A record you quietly edit is a record you stop trusting, because you can no longer tell current truth from tidied-up history. So when your understanding changes, you do not go back and correct the old entry. You write a new one, dated, that says what you understand now. The old entry stays as the honest record of what you believed at the time. The trail is the value: not only what you know, but how you came to know it.

Lessons work the same way. A lesson is not deleted when it feels obvious later, because "obvious" is exactly the wall the next person walks into.

Design for Both Readers

Here is the part that makes this MX and not just note-taking.

Both files are plain markdown. A person reads them as prose: clear sentences, in order, that anyone on the team can follow. A machine reads the same files as structure: dated entries it can parse, scan, and act on. One file, two audiences, the same truth. You are not writing twice. You are writing once, in a form that serves the human picking up the project and the machine picking up the project at the same time.

That is the MX move in miniature. Make the implicit explicit, write it where both kinds of reader can find it, and let the machine stop guessing.

What This Buys You

A machine with these two files behaves differently. It opens your project and reads what you already learned, so it does not re-earn the lessons the hard way. It reads what you understand, so it can pick up a thread across days or weeks. When you ask "why is this built this way," it has an answer with a date on it, not a confident reconstruction. And when a new teammate arrives, a person or an assistant, onboarding starts with two files instead of a string of questions you have answered before.

None of this needs a platform or a tool. It needs two plain files, an append-only habit, and the discipline to write down what you learned and what you understood as you go.

Machine Experience is usually pitched as something you do for the machines out in the world that will read what you publish. It is also something you can do for the machine sitting right next to you, the one trying to help. Give it a memory. It will stop guessing, and start helping.
