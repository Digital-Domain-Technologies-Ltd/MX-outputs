Make the Judgement Task Smaller

18 October 2026 · Tom Cranstoun · 4 min read

Andrew Ng opened the 16 October 2026 issue of The Batch with a letter about where AI is getting better, and where it isn't (Ng, 2026). His point is simple and, I think, right. AI gets good quickly at tasks where an answer can be checked automatically, like code that either passes its tests or doesn't. It gets good slowly at tasks that need judgement, like how to answer a customer complaint or which feature to build next. Those have better and worse answers, but no single right one.

The reason is how models are trained. Reinforcement learning needs a reward a machine can calculate. Supervised learning needs labels, and a checkable task hands you clean labels almost for free. Judgement tasks give you neither, so progress there comes from slow, expensive work on one domain at a time. In his words, "Intelligence is jagged".

He adds two more points worth keeping. Benchmarks are easier to build for checkable tasks, so what we measure flatters what we have. And as the checkable work gets automated, people keep an edge on the rest: "I expect people to continue to have a context advantage over LLMs on many tasks for a long time."

The Useful Response Isn't Waiting

If you run a business, you can't do much about how models are trained. You can do a lot about the tasks you hand them.

Very few real tasks are pure judgement. Take "should this support reply go out?" Inside it sit a pile of small questions that do have right answers. Is the product named the current one? Is the policy quoted the version in force? Is the customer's region one we serve? Does the reply link to a page that exists? Only after all that comes the actual judgement: is the tone right for this person, on this day?

A model asked the whole question has to guess at every part. A model handed the checked parts only has to judge the last one. That's the move: make the judgement task smaller.

Declare the Context the Machine Lacks

Ng puts the human advantage in context. It's knowing which few facts, out of a mountain of raw material, actually decide the matter.

A lot of that context isn't hard to know. It's just not written down anywhere a machine can read. Which version of this document is current? Who owns it? What's its purpose? Has something replaced it? A person in the building knows. A model reading the file cold has to infer it, and an inference is a guess with good manners.

MX exists to write it down. It's metadata in the file that says where it came from, what state it's in and how it's meant to be used. When that's declared, "is this the current policy?" stops being a judgement call. It becomes a lookup, and a machine can verify the answer.

Turn Repeatable Judgement into a Check

The second move is internal. Every time a person or an agent makes the same judgement call the same way, it's a candidate for a script.

We run our own repository like this. Rules that started life as "a reviewer should spot this" now run as gates on every push: no typographic dashes in prose, no public page linking into private files, no regulatory date quoted from memory instead of from the one canonical list. A person used to spend attention catching those. The gates spend none and never get tired.

The rule of thumb we use: if an agent does something the same way more than twice, it becomes code. The model's judgement is saved for the places where no check exists yet.

There's a side benefit. A deterministic check doesn't need a model at all, so every judgement you turn into a script is inference you don't have to run. Less inference means less compute and less energy, which I've written about in Reduce Inference, Save Energy.

Keep the Human on What's Left

None of this closes Ng's gap, and I don't want to oversell it. MX doesn't make a model better at judgement. It changes what the model is asked to judge.

What's left after the checks run is the real judgement: the tone, the trade-off, the call no rule could capture. That's where the people with the context advantage belong. Putting a human in command of those decisions isn't caution for its own sake. It's matching the work to whoever is actually good at it.

So when a vendor shows you a benchmark score, ask whether it measures a checkable task or a judgement one. Then look at your own tasks and ask how much of each one you could move across.
