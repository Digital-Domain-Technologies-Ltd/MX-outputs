Why Step 8.5 Comes After Step 8.6

28 June 2026 · Tom Cranstoun · 6 min read

I recently shipped a change where Step 8.5 comes after Step 8.6 in the execution order. The step numbers are real. The ordering is intentional. And it is a symptom of a maintenance problem I'd been ignoring.

This is the story of how a 700-line workflow skill accumulated 22 step identifiers, built three independent sources of truth, and how moving the procedure to a cog fixed all of it in one move.

How It Started

The step-commit skill is a systematic session-close workflow for Claude Code: commit changes, generate a directors report, update documentation, run compliance gates, sync with origin, push. Useful stuff. Grew organically.

It started with simple numbered steps: 1, 2, 3, 4, 5. Then I needed to add a scan before the commit. That became 3a. Then a conventional commits gate. That became 3b. Then cog propagation checks. That became 3c.

The push phase needed sub-steps too. The submodule pointer gate was 9a. The push itself was 9b. The Cloudflare cache purge was 9b-ii. The PR lifecycle was 9c. The final summary was 9d.

Remote sync came in at 8.5. WIP squash landed at 8.6.

By the end, the full step list was: 0, 0a, 1, 2, 3, 3a, 3b, 3c, 4, 5, 6, 6b, 7, 8, 8.5, 8.6, 9, 9a, 9b, 9b-ii, 9c, 9d. Twenty-two identifiers.

Three Sources of Truth

The numbering scheme would have been fine if the step list lived in one place. It lived in three.

The step-order table near the top of the file was supposed to be the canonical list. It was one row per step, with the type (mandatory/advisory) and what to do on failure.

The TodoWrite checklist in Step 0 was the interactive task list Claude called on entry. Each step got a line with a label and an active form.

The section headings scattered through the 700-line body were the actual procedures.

When I added a new step, I had to update all three. When I changed the ordering of steps (8.6 before 8.5 turned out to matter - squash before merge, not after), I had to track down every mention.

I didn't always catch them all. The table had 8.6 listed before 8.5, with a note saying "must complete before Step 9". The ordering in the description was backwards relative to the ordering in the list. The TodoWrite checklist was missing nine steps entirely - 0a, 9a, 9b, 9b-ii, and 9d didn't appear at all.

Gate 40b

Here's something I didn't know when I started: the repo already had a gate for this.

scripts/check-skill-numbered-sections.cjs (Gate 40b) enforces that skill files cannot use ## Step N numbered headings. The rationale in the script is direct: "Numbered step headings create fragile coupling: cross-skill references by step number go stale when any step is renumbered or removed, and no other gate catches the drift."

step-commit and step-document were on an explicit STEP_SOP_ALLOWLIST in that checker, exempting them from the gate. The allowlist comment acknowledged the exception: the numbers were "load-bearing - users follow them in order and reference them by number."

But an allowlist exemption is a code smell. It means the file is doing something the tooling thinks it shouldn't. The right response isn't to keep the exemption indefinitely - it's to understand why the exemption exists and fix the root cause.

Skills Route. Cogs Do

The root cause was that I'd put a 700-line SOP inside a skill file.

Claude Code skills are supposed to be thin. They declare triggers, describe what the skill does when invoked, and point at the code or procedure that does the actual work. The CLAUDE.md rule for this repo is explicit: "Skills route. Cogs do. When a skill and a cog share a name, the cog is authoritative."

step-commit had become a 700-line procedure pretending to be a routing file. The fix was to stop pretending.

I moved the SOP to scripts/cogs/step-commit-sop.cog.md - an action-doc with actionType: sop. The skill became 30 lines:

# step-commit

Session-close workflow. Routes to the SOP cog.

**When:** End of session, user says "step commit" / "close session".

## How it works

On entry, read `scripts/cogs/step-commit-sop.cog.md` in full.
Execute every phase it describes in order.

Named Phases

The cog doesn't use decimal step numbers. It uses named phases.

Eight phases in order: Pre-flight, Submodule sync, Directors report, Main commit, Documentation, Compliance, WIP squash, Remote sync, Push.

The ordering of WIP squash before Remote sync is now visible in the heading list, not buried in a note inside the step prose. The WIP squash phase says in its first sentence: "Runs BEFORE Remote sync - this ordering is mandatory." You don't need to trace through decimal numbers to understand it.

The phase summary table exists once, in the cog. The TodoWrite checklist is in the cog. The procedure sections are in the cog. One source of truth.

Adding a new phase now means adding a section. The name is stable. There's no number to insert between existing numbers. There's no table row to add in the right position. There's no checklist line to sync.

Why This Matters Beyond step-commit

The decimal-numbering trap is easy to fall into with any long procedure. Start with five steps, add substeps when you need more granularity, and within a few iterations you have something like 3a, 3b, 8.5, 8.6, 9b-ii.

The underlying problem isn't the numbers. It's having the same information in multiple places that must stay in sync. Every time you add "and update the table" and "and update the checklist" to your mental model of how to edit the file, you're accumulating maintenance debt.

For Claude Code skills specifically, there's an additional reason to keep them thin: the shorter the skill file, the less the model has to process before it can start doing useful work. A 30-line skill that reads a cog is faster to load than a 700-line skill that contains the cog's content inline.

The Allowlist Is Now Empty

step-commit and step-document came off the STEP_SOP_ALLOWLIST. Gate 40b now passes with no exemptions.

The session-close workflow is the same as it was before. The phases are the same. The rules are the same. The only thing that changed is where the procedure lives and how it's structured.

Step 8.5 still runs after Step 8.6. But now it's called "Remote sync" and it comes after "WIP squash" in a list of named phases. The ordering is obvious from the names. You don't need to know that 8.5 is greater than 8.6 to understand that WIP squash runs first.
