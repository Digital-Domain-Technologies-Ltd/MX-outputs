Every Tool, a Different Format

28 June 2026 · Tom Cranstoun · 7 min read

Yesterday I wrote something I am genuinely pleased with. It is a dream cog - a configuration file that tells a local analysis script what to scan, what to look for, and where to write its findings. This one reads my Claude Code session files, extracts the topics that come up repeatedly across sessions, and surfaces what I keep re-explaining rather than actually solving.

It works. And then I thought: what happens when someone else uses it? What happens when I switch tools?

The answer is: nothing works. Because the script I wrote reaches into a path that only exists if you are using Claude Code on a Mac, with a project at exactly my directory depth. It reads a JSONL format that Claude Code invented. Every line of that script assumes one tool, one vendor, one directory convention.

That is not a bug. That is the state of the industry.

What I Found When I Looked

I wanted to write a cross-tool version. So I looked at where other AI coding assistants store their sessions.

Aider puts them in a markdown file in your project root. One file, all sessions appended, separated by timestamp comments. Readable, human-friendly, but one blob per project. No per-session partitioning.

Cursor puts them in a SQLite database buried in Application Support, behind a workspace hash that changes per folder, with the conversation stored as a JSON blob inside a key-value table. The key name has changed between versions. There is no documented schema.

Continue - which is open source and therefore the most honest about its internals - uses per-session JSON files in ~/.continue/sessions/. That is the closest thing to a sane layout I found.

GitHub Copilot stores nothing locally. Your conversation history, if it exists at all, lives on GitHub's infrastructure. You cannot read it.

Not one of these is the same. Not format. Not location. Not field names. Not even the basic decision of whether to use one file or many.

The Cost

This is not an inconvenience. It is a structural problem.

I want to analyse what questions I ask my AI tools. I want to know what I keep re-explaining, what mistakes keep recurring, what topics I have never thought to document. That is useful. It helps me build better systems and write better rules.

To do that across tools, I have to write four separate readers. When Cursor updates its storage format - which it does, without notice - one of those readers breaks silently. When I add a fifth tool, I write a fifth reader. The infrastructure I care about gets harder to maintain the more tools I use.

There is a word for this: lock-in. Not the aggressive kind where a vendor deliberately makes exit hard. The quiet kind where the cost of using multiple tools is just high enough that staying with one is the path of least resistance. Every tool storing sessions differently is a gentle nudge toward picking one tool and staying there forever.

If you run an organisation that uses AI agents, this scales badly. You want to audit what your agents did. You want provenance - a record of which model, which version, which prompt, which output, in which session, on which project. Right now, that record looks different for every tool your team uses. Consolidating it requires custom code for each one, maintained indefinitely.

The Argument That Is Hard to Make

Here is the bit I struggled with when writing this post.

It is tempting to say: this is a Claude Code problem, or a CogNovaMX problem, or a problem for people who write dream cogs, which is a very small number of people. Most people do not scan their session files. Most people do not care where the files live.

That is true today. It was also true of RSS before people cared about following multiple blogs without visiting each one. It was true of EXIF before people cared about where their photos were taken. It was true of OpenAPI before people cared about generating clients without reading documentation.

Standards get written before the use case is mainstream, or they do not get written at all. By the time everyone needs to read AI session files - for compliance audits, for regulatory evidence trails, for cost analysis, for mistake mining, for cross-tool analytics - the formats will have calcified. The tooling will have shipped. The lock-in will be structural.

The time to agree on a standard is now, when the formats are still plastic and the vendors still have incentive to participate in shaping a shared approach.

What a Standard Would Actually Need

It would not need to be complicated. Four things:

Location convention. A well-known directory, structured by project path, so any tool can find any other tool's sessions for the same project. Claude Code's ~/.claude/projects/<slug>/ is a good shape; the slug derivation from the project path is replicable by anyone.

Format. JSONL. One message per line. A declared schemaVersion field so readers can handle evolution gracefully.

Mandatory fields. role (who spoke), timestamp (when), sessionId (which conversation), content (what was said, as typed content blocks). Enough to reconstruct a conversation without tool-specific knowledge.

Provenance fields. modelId, toolVersion, projectPath. The fields that let you filter and attribute without reading vendor-specific metadata.

That is it. Every vendor adds whatever they want on top. The standard says only what the floor must look like so any reader can stand on it.

The Gathering

This is what The Gathering is for.

The Gathering is a community-led standards body. It fills gaps that existing standards leave open. Dublin Core, Schema.org, DCAT, OpenAPI - they each own their corner. The Gathering works on the corners none of them own.

AI session provenance is one of those corners. It is not a file format problem (no standard covers it), not an API problem (OpenAPI describes requests, not transcripts), not a content problem (Dublin Core describes documents, not conversations). It is a new category of metadata, being invented right now, in incompatible ways, by every tool independently.

The Gathering needs people who care about this. Not just implementers - any community drafting a standard needs people who have the problem, who have tried to solve it tool by tool, and who are tired enough of that to want a shared answer instead.

If you have written a script that reads AI session files, you have the problem. If you have wondered what your team's AI agents were doing last Tuesday and found you could not answer that question cleanly, you have the problem. If you have switched AI tools and lost the ability to analyse your history, you have the problem.

The Gathering is where people with the problem write the standard that solves it. It is open. It is community-led. It is not owned by any vendor. The specifications it produces are free to implement.

Join us at tg.community. Bring the problem you have. Bring the format you invented. Bring the frustration of writing the same reader for the fourth time. That frustration is the raw material a standard is built from.

Every tool, a different format. That is not inevitable. It is just what happens when no one has agreed on anything yet. Let us agree on something.
