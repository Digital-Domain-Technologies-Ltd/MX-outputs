The Guard That Read GitHub as Git

15 October 2026 · Tom Cranstoun · 5 min read

I spent part of an afternoon being told no by a safety check that had misread the word GitHub.

The setup is ordinary. I work with an AI coding agent, and it makes each change in a separate copy of the repository, a git worktree, so it can't trample anything else in flight. That isolation comes with a guard. Before running anything in the shell, the tool checks it can't reach outside that copy. If it can't prove that, it refuses.

That's a good idea. An agent running git in the wrong folder can commit to another branch or wipe someone's uncommitted work. I want that guard.

What It Actually Matched

The refusals kept arriving on commands that had nothing to do with git. Reading a log file. Listing a folder. Fetching a CI result. Each came back with the same message: the session is isolated in the worktree, and this command names git in a form too complex to verify.

It took a while to see the pattern, because nothing in the message pointed at it. The guard looks for the letters g, i, t, anywhere in the text, whether or not they spell a command.

We keep every clone of our repository in a folder called GitHub, so every absolute path I type contains "git". Our organisation's name starts with Digital, which contains it too. Put either one in a command that also does something the guard can't evaluate up front, such as using a variable or running a small script, and it's refused as if it were a git operation. The same thing happened when a sentence in a note I was saving happened to contain the word.

None of those commands ran git. The guard couldn't tell, because it read the words and ignored what they did.

Why a Word-Matching Guard Costs More Than It Looks

A false positive in a safety check sounds harmless. Better safe than sorry. But each one costs something, and the refused command is the least of it.

First, the message tells you nothing you can use. "Too complex to verify" is true from the guard's side and useless from mine. I can't fix a command when I don't know which part of it was the problem, so I rewrite it more or less at random until it passes.

Second, it teaches the wrong lesson. When a guard fires on things that are plainly safe, people and agents learn to route around it instead of listening to it. The workarounds get folded into habit. Then, on the day the guard is right, the reflex is to rephrase and move on.

Third, it blurs the evidence. An agent that hits an unexplained refusal starts guessing. It tries variations, burns time, and sometimes lands on a version that passes for reasons nobody understands. That defeats the purpose of a guard.

The general point isn't about this one tool. A check that matches surface text instead of meaning will always misfire on whatever happens to look like the danger. Keyword filters on email did it. Content filters that block a town because its name contains a rude word do it. A safety guard that reads "GitHub" as "git" is the same mistake in a new place.

What We Could Do About It

The guard belongs to the tool, not to us, so I can't change how it matches. What I could change is when we find out.

So we built a hook that runs before every shell command the agent sends from a worktree. It checks the command against the patterns the guard has refused. The main ones are the letters git together with a value worked out at run time, and git inside free text handed to a script runner. When a command looks likely to trip, the hook tells the agent before the call goes out. It names the words being read as git, such as GitHub and Digital. Then it gives the rewrite that passes: a plain relative path, separate calls instead of a chain, or long text moved into a file.

A second hook does the same job earlier. The moment the agent enters a worktree, it gets a short briefing: this guard reads git as a substring, your own path contains it, and here are the forms that get refused. The first command can then be written the right way, rather than learned by refusal.

The hooks only advise. They never block anything. The guard's real rule isn't published, so our prediction comes from the refusals we actually saw, and it can be wrong in either direction. A warning that turns out to be unnecessary costs a sentence. A block that turns out to be unnecessary would be one more false positive, which is exactly the problem.

Every case the predictor knows about is a command from an actual session, path and all. A test built on tidy invented commands would have missed the point, because the trap is in the folder name everyone already has.

The Part Worth Keeping

Two habits came out of this that I'd apply to any guard, ours or anyone else's.

When you write a guard, match the thing you're afraid of, not something that looks like it. If you can't work out whether a command runs git, say so in the message, and point at the part you couldn't read.

When you depend on a guard you can't change, write down what it refuses as soon as you see a pattern, and make that knowledge run before the call. A refusal that arrives with an explanation is a speed bump. One that arrives without an explanation is a guessing game, and an agent will happily play it all afternoon.
