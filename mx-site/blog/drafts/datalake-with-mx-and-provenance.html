The Datalake Is the Right Architecture. MX and a Provenance Layer Are What Make It Work.

28 June 2026 · Tom Cranstoun · 8 min read

I keep having the same conversation with people building document systems for AI. They've picked a storage model - usually a datalake or a lakehouse of some kind - and they're happy with it. Then I ask what happens when a file from that lake ends up in an agent's context window. What does the agent know about it? Where did it come from? Who decided it was fit for purpose?

Usually the answer is: nothing, nowhere, and nobody.

That's the gap MX fills. Not by replacing the datalake. By giving every file in it a metadata layer that travels with it, and a provenance trail that records what happened to it.

The Datalake Is the Right Choice

Let me be clear about what I'm not arguing. I'm not saying datalakes are wrong. The open-format, schema-on-read, no-vendor-lock-in model is correct. When you store documents in a datalake, you own the data. You can query it, transform it, send it anywhere. You're not tied to a vendor's idea of what a document should look like.

The problem is not the storage layer. The problem is that files in a datalake are often metadata-poor. A filename and a folder path. Maybe a creation date from the filesystem. That's it.

When an AI agent reads that file, it's starting from nearly nothing.

What the Agent Needs to Know

An AI agent that reads a document needs to know at least these things to act responsibly:

  • What is this? (type, purpose)
  • Who is it for? (audience)
  • Is this the current version? (stability, modified date)
  • What does it build on? (relationships, dependencies)
  • Am I allowed to use it for training? (rights, reuse allowances)
  • Who produced it, and when? (provenance)

None of these are in the filename. Most aren't in a typical document header. All of them need to travel with the file if the file is going to be useful outside the environment that produced it.

This is what MX is for.

The Three-Zone MX Envelope

MX uses a three-zone YAML front-matter structure. The zones are a priority ordering that resolves conflicts between standards, not just visual separators.

Zone Fields What it's for
Zone 1a - Identity title, description, author, created, modified, version Document identity, readable by any tool
Zone 1b - OKF reserved type, tags, resource, timestamp Google OKF compatibility, always at top level
Zone 2 - MX operational Everything under mx: Governance, relationships, machine instructions

The priority is: OKF reserved fields win, then ARD, then MX. No field is defined twice. One envelope carries all four formats simultaneously.

Here's what a complete envelope looks like in practice:

title: "Q2 Pricing Analysis"
description: "Internal analysis of pricing options for the enterprise tier."
author: "Tom Cranstoun"
created: 2026-06-28
modified: 2026-06-28
version: "1.0"

type: "analysis"
tags: [pricing, enterprise, internal]
resource: https://example.com/documents/q2-pricing-analysis

mx:
  status: active
  audience: [humans, machines]
  purpose: "Inform the Q3 pricing decision for the enterprise tier."
  canonicalUri: https://raw.githubusercontent.com/example/docs/main/q2-pricing-analysis.md
  stability: stable
  runbook: "Read before the July pricing review. Update if assumptions change."
  buildsOn: [q1-pricing-analysis, enterprise-customer-research]

That file knows what it is. When an agent reads it, the agent knows what it is. When the file travels to a partner's system, the partner's system knows what it is. The metadata didn't stay behind in a catalog.

The Four-Way Interoperability Guarantee

This is the part I find genuinely elegant. An MX COG is not a new format. It's a superset envelope that satisfies four existing formats simultaneously.

Format Compatible? Why
Google OKF Yes OKF reserved fields (type, tags, resource, timestamp) sit at top level exactly where OKF expects them. OKF requires consumers to preserve unknown keys, so the mx: block is preserved and ignored.
YAML Yes The envelope is syntactically valid YAML. Every YAML linter, validator, and pipeline works unchanged.
Markdown front-matter Yes Place the block between --- delimiters and every static site generator, MD-wiki, and knowledge graph extractor treats it as standard front-matter.
MX Yes All MX operational fields live in the mx: namespace with flat camelCase names and the x-mx- extension prefix for vendor fields.

What this means for a datalake: you can start adding MX envelopes to your files without breaking a single existing tool. Your Markdown previewer keeps working. Your YAML linter keeps working. Your OKF catalog keeps working. You've added governance and machine-readability without a migration.

What MX Adds That OKF and YAML Don't

OKF is a good format for tagging and categorising documents. YAML is a good carrier. Neither defines what you need for AI governance.

Capability OKF Plain YAML MX
File type Yes No standard Yes
Tags Yes No standard Yes
Canonical URI Yes (resource) No Yes (mx.canonicalUri)
Status and lifecycle No No Yes (mx.status, mx.stability)
Audience declaration No No Yes (mx.audience)
Semantic purpose No No Yes (mx.purpose)
Relationship graph No No Yes (buildsOn, refersTo, derivedFrom)
Runbook for the machine No No Yes (mx.runbook)
Extension namespace Implicit (any key) None Explicit (x-mx- prefix)
Paired provenance sidecars No No Yes

The last row is the one that matters most for the AI governance conversation.

The Provenance Layer: Two Sidecars, Two Purposes

Every document in a well-designed datalake should ship with a paired set of provenance sidecars. MX defines two, and they serve different audiences.

Sidecar Records Audience Regulatory citation
<file>.provenance.ai.json Non-deterministic steps: LLM calls, multi-agent collectors, human decisions AI governance regimes EU AI Act, UK ICO AI guidance, NIST AI RMF, Colorado AI Act
<file>.provenance.deterministic.json Rule-driven steps: gate verdicts, render steps, validation results Accessibility and technical compliance EAA Directive 2019/882

The two sidecars carry different evidence for different regulators. An EU AI Act auditor walks the AI sidecar to find every model call and human decision. An accessibility auditor walks the deterministic sidecar to find every conformance gate result.

Both cross-reference each other with a companion field, and both carry a responsiblePerson block so a regulator can get from a finding to an accountable human in one step.

This is not a theoretical future state. Every generated artefact under mx-outputs/ in the MX estate already ships with this pair. A pre-commit hook auto-generates a minimal AI sidecar for any staged artefact that arrives without one.

The Architecture Side by Side

Here is the honest comparison between a plain datalake and a datalake with MX and a provenance layer.

Concern Plain datalake Datalake + MX + Provenance
File identity Filename and folder path Embedded title, type, canonicalUri travel with the file
Context when the file travels Lost at copy Travels in the YAML envelope
AI agent usability Agent must guess format and intent Agent reads purpose, audience, stability, runbook
Relationship graph Must be re-derived from content Encoded in buildsOn, refersTo, derivedFrom
Provenance trail External log or nothing .provenance.ai.json + .provenance.deterministic.json adjacent to every artefact
Regulatory evidence Manual reconstruction from logs Queryable, attached, tamper-evident, walks from file to human
OKF compatibility No Yes - OKF reserved fields at top level
YAML tooling compatibility Yes Yes - superset, not a replacement
Extension for vendor fields No standard x-mx- prefix under mx:
Migration cost - None - existing tools keep working

The last row is what I want to emphasise. This is not a rip-and-replace. It's an additive layer. You keep your datalake. You keep your YAML tooling. You keep your OKF catalog. You add MX envelopes to your files, and you add provenance sidecars when artefacts are generated. The files get smarter without a migration project.

Why This Matters Now

The argument for this architecture used to be a nice-to-have. You wanted good metadata hygiene. That's always been true.

The argument now is regulatory and operational. If your organisation is generating content with AI assistance, you are going to be asked to show the evidence chain. Who decided this? What model was involved? What version of the policy was in force when this decision was made? Can you prove the output was generated under the stated rules?

A datalake of files with no provenance layer cannot answer those questions. You'll be reconstructing the chain from logs and memories after the fact, and it will be incomplete.

A datalake with MX envelopes and paired provenance sidecars can answer those questions from the file itself. The evidence is adjacent. It travelled with the artefact. It's queryable. It's tamper-evident (Ed25519 signatures, Merkle log structure).

That's not aspirational. That's what REGINALD, the registry CogNovaMX operates on the MX standard, produces today.

The Architecture Is the Standard

I want to be careful about one thing. MX does not grant compliance with the EU AI Act, the European Accessibility Act, or any other regulation. Compliance is a legal duty of the organisation.

What MX does is make the documentation the organisation must produce structured, machine-readable, tamper-evident, and verifiable on request. That's what auditors, regulators, and AI providers actually need. Sold honestly as queryable, verifiable evidence, it's genuinely useful. Sold as compliance-in-a-box, it collapses on the first inquiry.

The datalake with MX and a provenance layer is the architecture because it's honest about what it provides. Every file knows what it is. Every generated artefact carries its evidence chain. Every relationship between documents is encoded and traversable. The agent that reads your files gets a complete briefing, not a filename and a hope.

That's the architecture I'd build. It's the one we're running.
