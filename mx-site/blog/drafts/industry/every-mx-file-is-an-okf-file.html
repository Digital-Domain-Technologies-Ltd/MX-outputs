Every MX File Is Now an OKF File

21 June 2026 · Tom Cranstoun · 4 min read

Google shipped an open standard for knowledge-as-a-directory-of-files. We adopted it.

Every file in the MX estate - 1,912 of them - now carries a frontmatter block that satisfies both the Open Knowledge Format and the full MX model. One file, one frontmatter block, readable by both.

What OKF Is

The Open Knowledge Format is a lightweight standard from GoogleCloudPlatform. The idea: a directory of markdown files with YAML frontmatter, where each file describes one thing you know - a table, a metric, a policy, a concept. OKF reserves six top-level frontmatter fields: type, title, description, resource, tags, timestamp. Everything else you add is preserved and passed on.

The preservation rule is the key one. OKF says: producers MAY include any additional keys; consumers SHOULD preserve unknown keys and SHOULD NOT reject documents with unrecognized fields. That single rule is what makes dual conformance possible.

What We Did

MX already owned title, description, and the concept behind tags. We adopted the OKF field names directly - no synonyms, no wrappers. type now sits at the top level of every MX file, carrying the same content-type vocabulary that used to live under mx.contentType. tags moved up from under mx: to the top level where OKF expects it. resource is new: an optional field for files that describe a specific external asset, distinct from the citation list under mx.refersToExternal.

The mx: block - with the typed relation graph, the trust layer, the governance fields - stays exactly where it is. An OKF consumer reads the top-level fields and treats mx: as one preserved unknown key. An MX consumer reads everything. No fact is written twice.

The migration ran in one pass across the estate. 1,912 files. Gate 32 now runs strict at push time: any file that puts type or tags under mx:, or that stores a timestamp in source, is rejected before it reaches the remote.

What It Means

For anyone building on OKF: MX files are valid OKF concept documents. You do not need an adapter, a transformer, or a second file format. Drop the markdown into any OKF-compatible tool and it reads cleanly.

For anyone building on MX: nothing changed in the way you author files. type replaces mx.contentType. tags stays at the top. The mx: block is the same. The validator guides you if you put a field in the wrong place.

For the standard itself: The Gathering's draft-core-metadata note has been updated to describe the three-zone model - Zone 1a for identity, Zone 1b for the OKF reserved surface, Zone 2 for the MX operational layer. OKF compatibility is now part of the MX specification, not an afterthought.

What OKF Omits

OKF defines a format for sharing what you know. It says nothing about proving it.

MX adds the layer OKF leaves open: proof of authorship, integrity signature, provenance chain. A resource field tells a reader what a file describes. A proofOfAuthorship field tells a reader who can be held accountable for the claim. A provenancePedigree field tells a reader where the claim came from and when it was checked. REGINALD, our registry, stores attestation records tied to those fields so the claim can be verified independently.

An OKF consumer gets the knowledge. An MX consumer gets the knowledge with the evidence attached.

That distinction is the commercial proposition. We wrote about the untyped-edge problem last week - the fact that OKF has no typed relation graph. This is the same argument from a different angle. OKF solves discovery. MX solves trust. The two standards compose because MX adopts OKF's surface and extends it.
