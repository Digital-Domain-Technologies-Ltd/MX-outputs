OKF's Edges Are Untyped. Here's How You Type Them.

17 June 2026 · Tom Cranstoun · 7 min read

A few days ago I wrote that Google's Open Knowledge Format confirms the argument I have been making for two years, and leaves the hard half open. I pointed at trust and at governance. This week a knowledge-graph consultant, Francois Vanderseypen, pointed at something narrower and sharper, and he is right, so I want to take it seriously rather than wave it away.

His objection, in plain terms: a directory of markdown files linking to other markdown files is a web of documents, not a knowledge graph. A knowledge graph is a graph of entities and typed relations. OKF guarantees one field, type, on each concept. What a link between two concepts actually means, whether it is "depends on", "is part of", or "see also", is left to the producer. So an agent reading an OKF bundle has to infer the meaning of every link from the prose around it, every single time. Calling that a knowledge graph, he says, is misleading.

I am not going to manufacture a disagreement, because there isn't one. He is correct, and the cleanest proof is OKF's own specification. The spec says it directly: "Consumers that build a graph view typically treat all links as directed edges of an untyped relationship." And: "The specific kind of relationship (parent/child, references, joins-with, depends-on, etc.) is conveyed by the surrounding prose, not by the link itself." That is the whole of the criticism, written by the format's authors. A bare markdown link carries a direction and nothing else. The meaning is in the paragraph, and the paragraph is for a person to read.

Why an untyped edge costs the machine

Here is what that costs. An agent that wants to know whether one table depends on another, or whether one document supersedes another, cannot read the answer. It has to reconstruct the answer from the prose near the link, and it has to do that again on the next read, and the read after that. The relationship was never written down in a place the machine could trust. It was implied, and implication is work the machine repeats every time. That is inference dressed as structure. It is exactly the thing a knowledge graph is supposed to remove.

The standard answer to this, the one Francois reaches for, is the Semantic Web: RDF and OWL. Put the relationship in the predicate of a triple, give the predicate a shared meaning, and a reasoner can read the edge, derive new facts from it, and catch the places where the graph contradicts itself. That works. It has worked for twenty-five years. The reason almost nobody ships it is that it asks a producer to model an ontology, serialise to triples, stand up a triplestore, and run a reasoner before any of it is legible. Google did not put the RDF stack in the hands of the people who write internal wikis, and they were right not to. A bare markdown directory is what you get when the formal stack is too heavy to adopt. So the field has been offering people two options: a graph with untyped edges, or a formal stack hardly anyone adopts.

That is a false choice, and it has been a false choice the whole time.

Put the type in the file

The real question is not markdown versus RDF. It is: where does the type of the relationship live? RDF puts it in the predicate. A bare markdown link puts it nowhere. There is a third place, and it is the obvious one. Put it in the file.

That is what MX does, and it is the only part of this I want you to take away. A cog is a markdown file with YAML frontmatter, the same shape as an OKF concept. The relationship is declared as a field in that frontmatter, not left to the prose. buildsOn. refersTo. dependsOn. partOf. derivedFrom. publishedTo. supersedes. Each one has a single fixed meaning, the same meaning in every file, written down where a machine reads it by name instead of guessing it from the sentence next to the link. The edge is typed. The agent does not infer it. It reads buildsOn and it knows.

And because the type is written down, two things follow that an untyped directory cannot give you. A builder can compute the transitive closure over those edges, so "what does this ultimately build on" and "where does this ultimately get published" are answered deterministically, not re-derived by a model. A gate can check the graph for the contradictions you can enumerate: a document that claims to replace another while that other is still live, a cycle in a dependency chain, a supersession that loops. Those are the two practical wins people stand up OWL for, deriving facts and catching contradictions, and you can have both of them without a triplestore, because the edges are typed and the checks are scripts.

I will be honest about the seam, because Francois will spot it anyway. A frontmatter field is a label, not a logic. RDF and OWL give you formal, open-world meaning that composes across datasets you did not author and entails facts nobody wrote down. A named field in a file does not do that. What it does is answer the question the agent in front of the file actually has, which is "what is this relationship", with no stack to stand up and nothing to infer. For a machine holding one document that arrived from somewhere else, typed and validated beats formal and unadopted. Where you genuinely need a description logic, an ontology that federates, open-world reasoning, reach for RDF and OWL. MX defers to them there and says so. For the ordinary case, content that has to stay legible when it travels, the file is the right place to write the edge down.

The edge is not the last thing the machine needs

There is one more thing, and it is the half I wrote about last time. Type every edge perfectly, run the full reasoner, and the machine still cannot tell you whether to believe the document the edge came from. A relationship can be formally immaculate and the node asserting it can be stale, altered, or published by someone other than who it claims. RDF answers what an edge means. It does not answer whether the thing carrying it is genuine, current, or accountable to anyone. That is provenance and lifecycle, and it travels in the file too: who published it, when it stops being authoritative, where its durable home is, and whether a newer version has replaced it, with a signed attestation a machine can check for itself.

So the layers stack cleanly, and they don't compete. RDF and OWL are for meaning, when you need the formal kind. MX is for typed, readable edges that travel, and for the trust the edge says nothing about. OKF gave us the carrier, and a good one. Francois is right that it left the edges untyped. The fix was never to choose between a folder and a triplestore. It was to write the type of the relationship into the file, where the machine can read it, and then sign the file so the machine can believe it.

Type your edges. You do not need anyone's reasoner to do it, and the file carries it wherever it goes.
