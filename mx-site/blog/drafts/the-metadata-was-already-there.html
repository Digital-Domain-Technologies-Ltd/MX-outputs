The Metadata Was Already There

10 June 2026 · Tom Cranstoun · 8 min read
  • Machine Experience
  • Mx
  • Metadata
  • Determinism
  • Intent Cms
  • Content Operations

I've been building a tool that pulls an entire website into a clean content system. Pages, styles, and a great many images. Every one of those images needs metadata if a machine is ever going to do anything sensible with it: a title, a description, what it is, where it lives, how it may be reused. The file has to be able to say all that on its own, because sooner or later it travels away from the page that produced it.

The obvious move, the one everyone reaches for now, is to point a model at the pile. Run each image through a vision model, let it write the description, let it pick the tags, move on. It feels modern. It feels like progress.

I didn't do that. I read what the page already said.

The Reflex Is to Ask the Model

There's a habit forming across the industry, and I want to argue with it before it hardens into common sense. The habit goes like this: content needs to be machine-readable, machines are good at reading, so let a machine read it and write the metadata back.

The trouble is what a model actually does when you ask it to describe something. It guesses. Fluently, confidently, and in its own culture rather than yours. I once handed a phone a bottle of German juice and it told me I was holding "orange with pump." The model got within a single letter of "pulp" and shipped the wrong word without a flicker of doubt, because nothing in its world told it the answer was absurd.

Now picture that same confidence writing the metadata for ten thousand assets you will never check by hand. Some of it will be right. Some of it will be "orange with pump." You won't know which is which, and neither will the agent that reads the file later and takes it as fact.

There's a quieter problem underneath. Inference is private, and it does not repeat. Run the same image through the same model twice and you can get two different descriptions, with no record of how it arrived at either one. For a throwaway caption, fine. For the metadata an auditor, a regulator, or another business is going to rely on, "we asked a model, and that's what it said that time" is not an answer.

Most of It Is Already in the File

Here's the thing the reflex skips over. The metadata is usually already there. A person wrote it, on purpose, when they built the page.

Look at what sits around a single image in real content:

  • The alt text. Someone wrote that so a screen reader could announce the image. It already says what the picture is.
  • The caption. The figure caption is a human description, in the publisher's own words.
  • The nearest heading. The section the image lives under tells you what it's about.
  • The path. The URL and the filename carry the slug, the folder, the date, the context.

None of that is a guess. It's fact, written by the people who made the content, sitting in the file waiting to be read. The job isn't to invent a description. The job is to harvest the one that's already there and write it somewhere a machine looks first.

That's what a decorator does. On the way in, it reads the alt text, the caption, the heading, and the path, and writes a clean MX record into the asset's own carrier: an XMP packet for a JPEG or a PNG, a metadata element inside an SVG, a small sidecar file for the formats that can't hold metadata of their own. The record travels inside the file from then on. Move the image, email it, drop it into a PDF, and the description goes with it.

Same input, same output, every single time. No model in the loop.

What "Deterministic" Actually Buys You

That word, deterministic, does a lot of work, so let me cash it out in plain terms.

It repeats. Run the decorator over the same library tomorrow and you get the same metadata, byte for byte. Run it on a different machine and you get the same again. Nobody has to wonder whether today's batch was tagged differently from last month's.

It's cheap. Reading the alt text costs nothing. There's no per-image model call, no inference bill that grows with the size of your archive. A library of fifty thousand images costs about the same to describe as a library of fifty.

It's auditable. Every field can point back at the signal it came from. This description came from that caption. This title came from that heading. When someone asks how the record was made, you show them the trail. You're not standing behind "the model said so."

It's honest. It never makes anything up. And that matters most at the edge, where the signals run out.

The Honest Gap

Sometimes the signals aren't enough. An image with no alt text, no caption, and a meaningless filename. What then?

You don't guess. That's the whole point. The decorator seeds a skeleton, marks the missing fields with a plain TODO, and flags the asset for a person to finish. The file is never shipped bare, and it's never shipped with an invented description dressed up as a real one. The record says, in effect, here is what I could read, and here is what I couldn't. A human fills the gap where judgment is the thing that's actually missing.

Harvest what's known. Surface what's missing. Invent nothing. That order is the whole difference between metadata you can trust and metadata that merely exists.

Where the Model Earns Its Place

I'm not against models doing this work. I'm against them doing the part that doesn't need them.

There's a genuinely hard part of importing a site: deciding that this chunk of a page is a hero, that one's a card, the other's a pull-quote. That's real interpretation, and a model helps. But even there, the model proposes and determinism disposes. Every mapping it suggests is checked against the page as it actually rendered. A guess it can't ground in the real markup gets dropped, not shipped. The model runs locally, on the operator's own machine, so the content never leaves the building. And whatever the model works out that proves stable across enough sites gets promoted to a fixed rule, so the next import leans on it a little less. The guessing shrinks every time you run it.

Use a model where you must. Harvest where you can. Most asset metadata is the second kind, and the industry is about to pay model prices for it anyway.

This Is What "Manages Itself" Means at the Door

I've written before about content that manages itself: files that carry their own identity, declare their own dependencies, and tell a machine what they are without a human in the loop. The fair question is how a file gets that self-description in the first place.

The answer the market is settling on is "ask a model." The answer I'd defend is "read what the file already tells you, deterministically, on the way in." Self-managing content has to acquire its metadata somehow, and the cheapest, most trustworthy moment to do it is at ingest, from the signals the publisher already wrote. The record goes into the carrier, the carrier travels with the file, and the file stays able to introduce itself anywhere it lands. That's the same instinct behind declaring it once so it works everywhere, and behind keeping the record readable when the file travels away from its source.

So before you budget for a model to read your content library, read it yourself first. Open a handful of files. Look at the alt text, the captions, the headings, the paths. I think you'll find most of the description you were about to pay for is already sitting right there, written by the people who knew the content best.

Start with the alt text.
