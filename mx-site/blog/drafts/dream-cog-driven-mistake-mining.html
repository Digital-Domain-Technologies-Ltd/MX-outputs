Dream: COG-driven mistake mining for Claude Code

14 June 2026 · Tom Cranstoun · 9 min read

I've been watching Claude Code make the same mistakes across sessions, and it bothered me enough to build a fix.

The two patterns I kept seeing: using cd with a relative path in the Bash tool (which fails the moment the shell's working directory drifts), and calling Edit on a file without first calling Read (which the tool rejects outright). Both are documented in LEARNINGS.md. Both appear in memory. And yet - there they are again, session after session.

The problem isn't that Claude ignores the rules. It's that memory is per-session and LEARNINGS.md only helps if someone spots the pattern and writes the rule. The old way put a human in every loop - pattern appears, human notices, human writes rule, future session reads it. Dream changes that loop. The machine does the mining; I read the report and decide what to promote. The human stays in command of what enters the permanent rulebook - just not in every cycle of the extraction.

So I built Dream: a tool that mines the project's Claude Code session transcript files, extracts recurring error patterns, classifies them with a local Ollama model, and commits the findings to a growing catalogue.

What Dream does

Dream reads the JSONL transcript files that Claude Code writes for every session. Each file is a structured log of every tool call, every response, every error. Dream scans those logs looking for two kinds of signal.

The first is hard errors: tool_result entries where is_error: true, and cases where the same tool is called again immediately after an error - a retry with identical arguments, which almost never works.

The second is structural patterns: Bash calls that use a relative cd, and Edit calls that have no preceding Read of the same file. These aren't errors in the strict sense - they succeed or fail depending on context - but they're consistently bad habits.

Everything after extraction is deterministic. I normalise each candidate by stripping volatile tokens (timestamps, UUIDs, absolute paths, hex hashes), then hash the result. If that hash is already in the exclusions list, I skip it. No Ollama call, no duplicate finding. Same logical mistake from ten different sessions produces exactly one classification.

Only when a candidate clears the dedup gate does Ollama see it. Temperature 0.1, JSON output, one call at a time. The model classifies the mistake, names the rule it violates, and that finding goes into findings.jsonl.

The output after a run: a JSONL findings file and a human-readable report, grouped by category. I read the report, promote anything useful into LEARNINGS.md or the relevant gotcha cog, and commit the lot.

Why COG-driven

The original version of Dream had its scan targets and classification lenses hardcoded. Two phases: hard errors, structural patterns. That was fine for two known patterns.

But the moment I wanted to add a third lens - say, one that checks the repo's published blog posts for stale factual claims - I'd need to edit the script. And a fourth. And a fifth.

The fix is obvious once you see it: each dream type is a COG. A .cog.md file in datalake/dream-files/cogs/ that declares what to scan, what to look for, and where to write. Adding a new dream type means writing a COG, not touching the script.

Each dream COG declares three key fields in its frontmatter:

  • x-mx-dreamtype: the composite label. This becomes the output filename prefix and the dream's identity.
  • x-mx-dreamScanTarget: what to scan - session transcripts, scripts in the repo, published blog HTML, the dream COGs themselves.
  • x-mx-dreamLens: what to look for, within that scan target.

The script reads all COGs in the folder, builds the list, and picks one.

A worked example

Take session-structural-patterns, one of the two session-analysis dreams. Its scan target is the Claude Code session JSONL transcripts. Its lens is structural patterns in tool use - the kinds of mistake that do not immediately produce an error but consistently produce bad outcomes.

The COG names two patterns. It describes each one clearly enough that the runner can implement the check without inference. It specifies the dedup rule: every candidate is normalised and hashed before any Ollama call; if that hash is already in the exclusions file, the candidate is skipped. It tells Ollama exactly what JSON schema to return. And it names where findings go: LEARNINGS.md for the rule, and the relevant gotcha cog for the domain.

That is the whole contract. The COG is the specification. The script is the executor. A new contributor who wants to understand what session-structural-patterns does reads the COG - not the script, not the memory, not a conversation. The COG travels with the repo.

Why order does not matter

Dream runs every dream type on each invocation, looping through them until all are done. The order it takes them in does not matter, and that independence is the point: no dream relies on another having run first, so the catalogue is the same however the run sequences them. "Pick one at random" was always shorthand for this - order is not a dependency.

That independence is what lets the deterministic part carry the load. Each dream's extraction is fully determined by its scan target and the input state: which files to scan, which candidates to extract, which hashes to skip, what Ollama receives. The only judgement is the per-candidate classification, and even that is gated by the dedup hash, so the same mistake is never classified twice. Run the dreams in any order, on any day, and the findings converge on the same result.

To focus on a single dream type, pass --dream <dreamtype>.

Processed files go to archive

After a full dream run, the session JSONL files that were processed move to datalake/dream-files/_archive/. The archive folder is gitignored - these are machine-local transcripts, not repo state.

This keeps the working set small. New sessions accumulate in the transcripts folder; old ones, once mined, move aside. A --reset-state flag brings them back into scope when needed.

What this means for LEARNINGS.md

The findings catalogue is not the end state - it's the input to LEARNINGS.md. Dream accelerates the feedback loop: instead of waiting for a human to notice a recurring mistake and write a rule, the catalogue surfaces patterns automatically. A session that spots a new category in the report can draft the rule and promote it in minutes.

The catalogue also makes the rules more honest. A rule in LEARNINGS.md that came from Dream has evidence behind it: a hash, a category, an example, the session file it came from. A rule written from memory has a feeling behind it. Both belong. But the Dream-sourced rules have provenance.

Where Dream sits in the ML landscape

I didn't name it with the ML literature in mind. But after building it, I looked, and the name turns out to fit better than expected.

The dominant technical meaning of "dreaming" in ML is the Dreamer algorithm family - model-based reinforcement learning where an agent trains a world model on past experience, then generates imagined trajectories in latent space. The agent learns from those imagined rollouts without re-running the real environment. Dreamer v3 generalises across a huge range of tasks with one configuration.

The parallel to what I built is real. Dreamer uses stored experience to improve future behaviour without replaying the environment. Dream uses stored session transcripts to improve future behaviour without re-running the sessions. Different domain, same structure.

The closer prior art - the thing actually doing something like what Dream does - is the Reflexion/Reflection agent pattern that emerged around 2025. A Reflexion agent pauses mid-task, writes a verbal self-critique, stores it in episodic memory, and retries. It accumulates critiques and gets better across attempts within a session.

The distinction matters. Reflexion operates in-session: reflect, retry, immediately. Dream operates between sessions: mine completed transcripts after the fact, classify patterns mechanically, commit findings to a permanent catalogue. No retry loop. The output isn't a corrected action - it's a rulebook entry that all future sessions inherit.

That's the REM sleep framing I keep coming back to. Sleep doesn't retry the day's mistakes mid-dream. It processes completed experience into durable memory, ready for tomorrow. That's what Dream does with session transcripts.

There's a governance framing that also holds up. The EU AI HLEG calls the right model "Human-in-Command" - not human-in-the-loop (a human present at every decision) but human in command (a human who holds authority over when and how the system operates). Dream is built on that principle. The output boundary is the enforcement mechanism: Dream writes only inside datalake/dream-files/. It cannot touch LEARNINGS.md, cannot edit a cog, cannot act outside its declared scope. The human reads the report and decides what to promote. That's HIC in practice - the machine mines, the human commands.

Running it

/dream                                    # run every dream COG, in any order, until all are done
node scripts/dream.cjs --dry-run          # extract candidates, no Ollama, no writes
node scripts/dream.cjs --dream session-tool-errors  # fix the COG selection

Ollama needs to be running locally (ollama serve). The default model is gpt-oss:20b. No session content reaches any external service.

After a run, read datalake/dream-files/YYYY-MM-DD/<dreamtype>-report.md - findings and report write to a dated subfolder so the history accumulates without overwriting, while the per-type exclusions.jsonl and resume state persist flat at the root so dedup holds across runs. Promote anything useful to LEARNINGS.md or the relevant gotcha cog. Commit the dated findings.jsonl and report.md together with the updated root exclusions.jsonl.
