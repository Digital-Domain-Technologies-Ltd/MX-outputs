The Machine That Reviewed Itself

22 June 2026 · Tom Cranstoun · 5 min read

This morning I asked Claude to read three days of its own session transcripts and tell me where I was being inefficient. It found inefficiencies in two places: in how I work, and in the system itself. Both surprised me, in different ways.

Here is what that looks like when you build on MX.

The raw material

Claude Code saves every session as a JSONL file -- line-delimited JSON, one object per conversation event. Tool calls, user messages, assistant turns, hook outputs. Every session automatically produces one of these files, and they accumulate under ~/.claude/projects/.

Over three days (19-22 June) the MX-hub sessions generated 83 JSONL files totalling about 137MB. Five of those sessions were large enough to matter: 2-7MB each, covering a range of work from OKF field migrations to gate debugging to building new skills.

I pointed Claude at them with a single question: what could be better?

Two classes of inefficiency

Most AI-productivity writing assumes the human is the variable. Calibrate the prompts, add memory entries, adjust the workflow. The tooling stays as it is.

What came back from the analysis was different. There were two distinct classes of problem.

The first class was mine. I was re-teaching Claude the same rules across sessions. "OKF is primary, MX is secondary" -- Tom's verbatim correction from a 1,932-file codemod -- wasn't in the instructions every session reads. It should be. "After every commit, report the SHA and file count" -- said twice in the same session because the IDE shows stale state -- wasn't there either. Neither is "Node.js, not shell, for new scripts." These are rules that belong in the permanent record, not in the conversation history.

The second class was the system's. This one was more interesting.

Where the system was getting in its own way

One check fires when a blog post source is edited without regenerating its served page. That's correct behaviour. But it was also firing when I updated only the metadata, without touching the body. The rendered page is unchanged. The check was reading when the file changed, not what changed. So it stopped work that didn't need stopping, and I had to step round it twice in one session.

Another check proves that the repository's generated indexes are reproducible by regenerating them and looking for differences. That's correct behaviour too. But when a new cog is committed, the generators legitimately produce new index entries that were never committed, and the check sees the tree as dirty. Not because a generator is unreliable, but because the regeneration step was missed. Each time, the fix was a manual regeneration, a new commit and another attempt. This happened across multiple sessions.

Each of these is the same pattern underneath: a problem a script could catch or prevent was instead left for a person to notice, after the fact.

What we fixed

Three tracks of work came out of the analysis.

The first track was the human rules. Four additions to the instructions every session reads at start: OKF priority, SHA reporting after commits, search before writing new scripts, and a preference for Node.js. Six new memory records took the rest forward. These are rules that should have been permanent. Now they are.

The second track was the deterministic fixes. The freshness check now compares what a change did to the body, so a metadata-only edit no longer asks for a republish. The index check now regenerates first when new cogs arrive, and tells you exactly what to commit rather than failing. The analysis skill reruns itself after a fix rather than waiting to be asked. And a new sweep drains migration debt before the checks surface it one item at a time.

The third track is this post.

Why this is the point

MX OS describes a repository that explains itself, checks itself and repairs itself. Its cog registry does the explaining; its checks and its repair step do the rest.

What happened in June 2026 is that the repository became self-auditing.

The session JSONL files are machine-readable data. They carry timestamps, tool names, user messages, and correction signals. We ran them through the same kind of analysis we run on any other data source. The output was a structured finding set: corrections that should be permanent rules, gates that were firing on false positives, a missing pre-check that every cog-adding session was hitting.

The improvements are now deterministic. The freshness check knows that a metadata-only change needs no republish, and the index step regenerates after a new cog arrives, so nobody has to remember either. The skill instructions tell Claude to re-run after a fix without being asked. Memory files carry the corrections forward into future sessions.

That's the working rule here: anything a script can check is checked automatically. Guidance kept in memory rots; a rule enforced by a check holds.

And the session data that revealed it -- the JSONL transcripts, the tool call sequences, the correction signals -- that's MX in the places you don't normally look. Provenance. Machine-readable context. The metadata that travels with the work.

The machine didn't just help with the work. It helped improve the conditions under which the work happens.

If you're building with Claude Code and want to structure your sessions so the data stays readable and improvable, the MX OS model is a reasonable starting point. The session JSONL format is documented and stable. The analysis in this post took one session and five parallel fork agents to run. The improvements ship in the same session.
