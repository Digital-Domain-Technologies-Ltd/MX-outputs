The Machine That Reviewed Itself

22 June 2026 · Tom Cranstoun · 6 min read

This morning I asked Claude to read three days of its own session transcripts and tell me where I was being inefficient. It found inefficiencies in two places: in how I work, and in the system itself. Both surprised me, in different ways.

Here is what that looks like when you build on MX.

The raw material

Claude Code saves every session as a JSONL file -- line-delimited JSON, one object per conversation event. Tool calls, user messages, assistant turns, hook outputs. Every session automatically produces one of these files, and they accumulate under ~/.claude/projects/.

Over three days (19-22 June) the MX-hub sessions generated 83 JSONL files totalling about 137MB. Five of those sessions were large enough to matter: 2-7MB each, covering a range of work from OKF field migrations to gate debugging to building new skills.

I pointed Claude at them with a single question: what could be better?

Two classes of inefficiency

Most AI-productivity writing assumes the human is the variable. Calibrate the prompts, add memory entries, adjust the workflow. The system is the system.

What came back from the analysis was different. There were two distinct classes of problem.

The first class was mine. I was re-teaching Claude the same rules across sessions. "OKF is primary, MX is secondary" -- Tom's verbatim correction from a 1,932-file codemod -- is not in CLAUDE.md. It should be. "After every commit, state the SHA and file count" -- said twice in the same session because the IDE shows stale state -- is not in CLAUDE.md either. Neither is "Node.js, not shell, for new scripts." These are rules that belong in the permanent record, not in the conversation history.

The second class was the system's. This one was more interesting.

Where the system was getting in its own way

Gate 22 (check-draft-site-fresh.cjs) fires when a blog post source is edited without regenerating its served HTML. That is correct behaviour. But it was also firing when I updated only the frontmatter -- a createdHash field, a modified date -- without touching the body. The rendered HTML is unchanged. The gate was checking file modification time, not content. So it blocked a push that did not need to be blocked, and the escape hatch (MX_SKIP_DRAFT_SITE_FRESH=1) was used twice in one session.

Gate 25 proves index generators are idempotent by running them and checking for drift. That is correct behaviour too. But when a new .cog.md file is committed, the generators legitimately produce new index output -- new registry entries -- that was never committed. Gate 25 then sees the tree as dirty. Not because a generator is non-deterministic, but because the regen step was missed. The fix required manual npm run index:regen, a new commit, and another push attempt. This happened across multiple sessions.

And then there were the API keys sitting in ~/.claude/settings.json. Two Anthropic API keys embedded verbatim in allowlist curl entries from an openclaw debugging session months ago. Not in git, not public, but in a file that should not carry live secrets regardless.

Each of these is the same pattern underneath: something that could be caught or prevented by a script was instead being caught by a person, after the fact.

What we fixed

Three tracks of work came out of the analysis.

The first track was the human rules. Four additions to CLAUDE.md -- the file that every Claude session in this repo reads at start. OKF priority. SHA reporting after commits. Search before writing new scripts. Node.js preference. Six new memory files covering Gate 22 bypass, Gate 25 regen, Appendix M editing, gathering sweep requirements, and the push-before-switching-sessions discipline. These are rules that should have been permanent. Now they are.

The second track was the deterministic fixes. Gate 22 now reads the git diff for a source file and compares body content (everything after the closing frontmatter delimiter) between the base ref and HEAD. If the bodies are identical, the gate skips that file and logs "frontmatter-only change, republish not required." Gate 25 now has a pre-check: if .cog.md files are in the push, it runs npm run index:regen before the idempotency check, and if the regen produces changes, it tells you exactly what to commit rather than failing with a drift error. The dream skill now auto-reruns after a fix rather than stopping and waiting for "run again." And there is a new /pre-push-sweep skill that drains field-migration debt proactively before step-commit gates surface it one-by-one.

The third track is this post.

Why this is the point

MX OS describes a repository that is self-describing, self-checking, and self-healing. The cog registry is its self-description. The pre-push gates are its self-checking. mx:heal is its self-healing.

What happened this week is that the repository became self-auditing.

The session JSONL files are machine-readable data. They carry timestamps, tool names, user messages, and correction signals. We ran them through the same kind of analysis we run on any other data source. The output was a structured finding set: corrections that should be permanent rules, gates that were firing on false positives, a missing pre-check that every cog-adding session was hitting.

The improvements are now deterministic. Gate 22 does not rely on anyone remembering that metadata-only changes do not require republishing. Gate 25 does not rely on anyone remembering to run index:regen after adding a cog. The skill instructions tell Claude to re-run after a fix without being asked. Memory files carry the corrections forward into future sessions.

This is what "a check a script can do, a script does" means in practice. The rule that lives in memory rots. The rule that lives in a gate holds.

And the session data that revealed it -- the JSONL transcripts, the tool call sequences, the correction signals -- that is MX in the places you do not normally look. Provenance. Machine-readable context. The metadata that travels with the work.

The machine did not just help with the work. It helped improve the conditions under which the work happens.

If you are building with Claude Code and want to structure your sessions so the data stays readable and improvable, the MX OS model is a reasonable starting point. The session JSONL format is documented and stable. The analysis in this post took one session and five parallel fork agents to run. The improvements ship in the same session.
