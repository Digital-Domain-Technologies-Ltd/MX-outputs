A Form Is Not a Content Model

13 November 2026 · Tom Cranstoun · 4 min read

A headless CMS vendor added a new tab to its page editor in November 2026. It appears on every page and every list item, and it asks for three things: a schema.org type, an answer-first summary, and a block of JSON-LD, checked for valid syntax as it's typed. The site then renders all of it into the server HTML, so crawlers and AI tools see it without running JavaScript.

I like the instinct. Structured data does belong in the served HTML, and an editor should be able to see it. Most sites I audit have JSON-LD that someone pasted into a header field years ago and nobody has read since.

But I've been building the same outcome a different way since May, and I think the difference matters.

What the Form Asks of an Editor

Look at what that tab hands to a person. They decide what the page is, add a second summary beside the description it already has, and paste or hand-type the JSON-LD.

Every one of those is a fact the content already knows. A blog post already knows what kind of page it is. A page already has a description. The author, the dates and the publisher are already in the CMS. The form asks someone to restate them elsewhere, and a copy drifts. Change the title, forget the summary, and the machine-readable page now disagrees with the human one. Syntax checking catches a missing bracket. It can't catch a summary that stopped being true.

Derive It From the Content

In Intent CMS, each of those values follows from the content instead.

  • The type comes from the page's profile. A table gives each kind of content its schema.org type: blog posts get BlogPosting, reference pages TechArticle, section landers CollectionPage. A page that needs something else names it in one override field, and a name schema.org doesn't define is refused.
  • The summary is the page's own description. The same field fills the meta description, the social cards and the JSON-LD. There's one summary, so there's nothing to keep in step.
  • The JSON-LD is generated. The page's graph is built from its frontmatter and joined to one organisation, one website and one author, defined once for the whole site.
  • What the generator can't write goes in a sidecar. A book, an offer or a speakable section is written in a small JSON-LD file beside the page source. Its nodes extend the generated ones, and where both name the same field, the source keeps the final word. A node without a type stops the build before anything is written.
  • The output is static HTML. There's no script to run, so a crawler sees exactly what a browser sees.
  • Validation happens at publish. Every publish checks schema validity, metadata completeness and accessibility. Nobody has to remember to look.

The editor still controls the content. What the editor doesn't do is type the same facts twice.

Why the Difference Matters

A form is a good answer to "how do we let editors add structured data?" I think the better question is "how do we stop structured data from lying?"

When the type, the summary and the graph come from the content model, they change whenever the page is edited. When an extra node is needed, it lives beside the source, in the standard it's published as, and the build refuses it if it's malformed. The check moves from an editor's attention to the publishing pipeline, which doesn't get tired at five on a Friday.

The vendor's announcement made one more point I agree with: none of this promises AI citations. Nobody can promise that. Structured data makes a page readable to a machine. An answer engine cites a page when it can tell who stands behind it and can corroborate its claims, and a form supplies neither.

If You Run a CMS

Before you add a structured-data tab, list what it would ask an editor to type. For each item, ask whether the CMS already holds the answer. Where it does, generate the value. Where it doesn't, give it a home beside the content, in plain JSON-LD, and refuse it at build time when it's wrong.

That turns structured data from something editors fill in into something the content says about itself.
