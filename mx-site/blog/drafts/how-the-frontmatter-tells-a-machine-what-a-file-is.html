How the Frontmatter Tells a Machine What a File Is

4 July 2026 · Tom Cranstoun · 13 min read

Open any file in this repository and the first thing you meet is not a sentence. It is a block of YAML fenced between two lines of three dashes. A human eye slides past it to get to the words. A machine does the opposite. It reads that block first, and by the time it reaches the prose it already knows what the file is, who wrote it, when it last changed, where the real copy lives, who it is for, and how much to trust it.

That block is the frontmatter, and it is written for the machine. This is what MX means in practice. MX is to machines what UX is to users. UX asks whether a person can understand and navigate a thing. MX asks whether a machine can understand and act on it. The frontmatter is where we answer that question, one file at a time.

Here is how the block is built, which standards sit underneath it, and why we made each choice. I will be honest at the end about how finished any of this is.

The block has three zones

Every fact in the frontmatter lives in exactly one place. We split the block into three zones, and the split is not cosmetic. It is what lets two very different readers both make sense of the same file.

Zone 1a is identity. Title, description, author, created, modified, version. The plain facts about the file as a thing in the world.

Zone 1b is the reserved surface. Type, tags, resource. These sit at the top level too, and they are named to match an open standard rather than our own taste.

Zone 2 is the mx: block. Everything that is specific to how we govern content and nothing an outside standard already covers: where the canonical copy lives, what state the file is in, who its audience is, how stable it is, what it is for, and our own extension fields.

An agent that knows only the open format reads zones 1a and 1b, understands the file, and leaves the mx: block alone. An agent that knows MX reads all three. Same file, two readers, neither one confused.

OKF first: the machine keeps what it does not recognise

The base is the Open Knowledge Format, OKF, published by Google Cloud. OKF reserves six top-level fields: type, title, description, resource, tags, and timestamp. Only type is required. The rest are recommended.

The load-bearing line in the OKF spec is this: producers may add any extra keys, and consumers should preserve keys they do not recognise. That single sentence is why our entire mx: block is legal OKF. To an OKF reader the mx: block is just one unknown top-level key, and the rule says: keep it, do not choke on it. So a plain OKF tool reads our identity fields, derives a timestamp from modified, and passes the mx: block through untouched. Nothing breaks. Nothing is lost. The machine that understands more gets more, and the machine that understands less still gets a working file.

That is the priority in one word: OKF first. Where a name is reserved by OKF, it wins, and it stays at the top level. We never bury type or tags inside mx: to tidy the block. The location carries meaning.

ARD second: the same facts, projected for discovery

The second layer is ARD, Agentic Resource Discovery. When we publish, a generator reads the frontmatter and emits a catalogue that a discovery agent can crawl, served at a well-known path on the site. Where an ARD name overlaps an OKF name, for instance ARD's URL against OKF's resource, the OKF spelling wins in the source file and the generator maps it on export.

One honest note, because it matters for how you read the rest: ARD is our own export layer, not an external standard you can go and cite. It is the shape we project into so that agents can find our files. OKF is the base the file is written in. ARD is where that base is re-expressed for discovery.

MX third: the governance layer nothing else covers

Everything left over lives in the mx: block. These are the fields no open standard defines, because they are about governing content rather than describing a generic resource: canonicalUri, status, stability, audience, purpose, runbook, the provenance fields, and our x-mx- extensions. They survive in an OKF reader as that one preserved unknown key, and they are the reason an MX-aware agent can do more than read the file. It can act on it safely.

One distinction inside this zone is worth pausing on, because merging the two would corrupt meaning. resource is a single URI: the one external asset this file describes. refersToExternal is a list: the external sources this file cites as evidence. One is what the file is about. The other is what the file leans on. A gate errors if they ever share a value, because a machine that confuses "about" with "cites" reaches the wrong conclusion.

Here is the block laid out by zone, with the standard each field answers to.

Field Zone Answers to
title, description 1a identity OKF (recommended)
author, version 1a identity MX
created, modified 1a identity ISO 8601 for the dates
type 1b reserved OKF (IANA media type on ARD export)
tags 1b reserved OKF
resource 1b reserved OKF
canonicalUri 2 (mx:) MX
status, stability, audience 2 (mx:) MX
inLanguage 2 (mx:) BCP 47
purpose, runbook 2 (mx:) MX
x-mx-* 2 (mx:) CogNovaMX vendor extension

One real block, read by zone

Enough tables. Here is a whole block, the kind that sits at the top of an ordinary document in this repository, with the zone each part belongs to marked in the margin.

title: "How MX Defers to Existing Standards"      # Zone 1a: identity
description: "Where MX reuses Dublin Core, Schema.org, and the rest."
author: Tom Cranstoun
created: 2026-07-04
modified: 2026-07-04
version: "1.0"

type: info-doc                                    # Zone 1b: OKF reserved
tags: [mx, standards, metadata]

mx:                                               # Zone 2: the MX block
  status: active
  audience: [humans, machines]
  stability: stable
  canonicalUri: https://raw.githubusercontent.com/.../../standards-deferral.md
  purpose: "Where MX reuses existing standards and where it adds a governance layer."
  runbook: "Read to see which standards MX defers to."

A reader that knows only the open format reads the top two groups, notices mx: is a key it does not recognise, keeps it untouched, and walks away with a complete, working understanding of the file. A reader that knows MX opens the mx: block as well and learns where the authoritative copy lives, who the file is for, how stable it is, and what it is for. Same short block, two depths of understanding, nothing lost to either.

We borrow standards, we do not reinvent them

The strongest rule in the whole design is a rule about restraint. Before we add a field, we ask whether an existing standard already covers the concern. If one does, we use its vocabulary and add nothing. MX contributes only the governance layer those standards leave out.

The reason is the machine. A machine that reads our files already carries libraries for dates, for language tags, for currencies, for structured web data. If we invented our own spelling for a date, the machine would have to learn ours on top of the one it already knows. So we borrow the vocabulary it already speaks. These concerns defer outward.

Concern Defers to
Dataset and catalogue metadata DCAT v3
Tabular and CSV schema, columns, keys CSVW
Generic resource identity: date, format, rights, language Dublin Core
Content language tags BCP 47 / RFC 5646
Currency codes ISO 4217
Dates and times ISO 8601
Web content vocabulary: images, video, people, organisations Schema.org
Embedded media metadata EXIF, IPTC, XMP, ID3
Content credentials for media C2PA
General provenance W3C PROV-O
API surface specification OpenAPI
Standards-document authoring IETF RFC format
Accessibility WCAG 2.1, ARIA
Package manifests package.json, pyproject.toml

An MX-aware file that describes a dataset, an image, an API, or a package uses those vocabularies directly. We add the part they omit, which is the agent policy, the routing, and the provenance attribution, and nothing more.

The field names are camelCase, and there is a reason

Field names in the frontmatter are camelCase. canonicalUri, not canonical_uri or canonical-uri. Single words stay plain: title, author, created.

This is a deliberate decision, recorded and dated in our naming register. The reasoning is short. MX metadata is a vocabulary. It is not markup, not CSS, not HTTP headers. The web vocabularies our metadata sits next to, Schema.org and Dublin Core and the HTML dataset API, all use camelCase. YAML itself has no opinion about casing, so the convention has to come from somewhere. It comes from the ecosystem the metadata is read in, and that ecosystem is Schema.org adjacent. So camelCase. The one exception is our extension fields, which keep their x-mx- and x-mx-p- prefixes as a vendor marker.

The fact does not move when the field does

Occasionally a field changes its home. Two of our fields used to live inside the mx: block and now sit at the top level: what is now type was once mx.contentType, and what is now tags was once mx.tags. When OKF reserved those names at the top level, we promoted them and retired the old synonyms.

The point of telling you this is what did not change. The vocabulary was identical. The value was identical. Only the location moved, so that a plain OKF reader would find the field where the standard says to look. The location changed; the fact did not. That is the whole game with metadata. You are moving facts into the places a machine already knows to check.

canonicalUri: the thread back to the source

One field earns a paragraph of its own. canonicalUri is the permanent address of the authoritative copy of a file. A machine that meets a copy of this post anywhere, scraped, mirrored, pasted into a training set, cached by a service that will later forget it, can read that one field and walk back to where the real thing lives.

It answers a different question from identity. A companion field, the URN, says what the file is, and survives even a change of domain or a CDN reshuffle. canonicalUri says where the file currently lives. Identity and location, kept as two fields, because a machine needs both and they do not always change together.

The rules are checked, not remembered

Everything I have described is a rule, and a rule that lives only in prose quietly rots. So none of this is left to memory. Every placement is checked by a machine before it can go wrong. Write a document with no canonicalUri, or put type down inside the mx: block where it does not belong, or let the address in canonicalUri drift from where the file actually sits, and the write is refused on the spot, with the fix named. On every push, the same checks run again over everything that changed. There is no step where a person is trusted to have remembered the convention.

That is deliberate, and it is the principle that runs through all of MX. A rule you have to remember is a rule that will eventually be forgotten, by a tired author or a new one or an agent that never read the style guide. A rule a script checks is a rule that holds. The frontmatter is not a convention we hope people follow. It is a shape the repository enforces, so that when a machine opens a file and trusts what the block says, the trust was earned by a gate, not extended on goodwill.

These rules are still draft

Here is the honest part. OKF is an early published spec. ARD is our own layer, still moving. The three-zone model, the field names, the exact list of standards we defer to: all of it is under active development. These rules will change. The zone boundaries may shift. Names may be promoted, retired, or renamed. The deferral list will grow.

So read the specifics above as current best, not as final. The shape of the argument is stable. The three zones, borrow before you invent, keep the machine's existing vocabulary, name where the source lives: those hold. The individual field names are the part most likely to move under you. MX asks us to be honest with the machine about what a file is. It would be a poor advertisement for that idea if I were not honest with you about how settled the file you are reading is.

What this post says about itself

Which brings me to the block at the top of this very post, because it practises what the post describes. Its fields tell you how finished it is, and one of them says so twice, on two different axes.

x-mx-contentState: draft says where the post sits in our editorial pipeline. It is a draft. It is served on a page marked noindex, not on the public blog, and it has not been published. When it is, that field flips to published and the page moves. A tool does that, not a hand edit.

stability is the interesting one, and here it is not a single value but a list: [draft, friable]. A file can be more than one thing at once, so the field is an array, and this file is two things. draft, in the stability sense, is about the content rather than the pipeline: the ideas are not settled, because the standards under them are still draft and will move. friable is about the file itself. In our own vocabulary it means the artefact is regenerated from a source and must never be hand-edited. The HTML you are reading was built from this markdown by a generator. Edit the HTML and the next build erases your change. So do not; edit the source. Friable carries its plain-English sense too: crumbly, transient, remade whenever its source changes. Two values, two truths, and the field holds both because I asked it to.

Notice what just happened. The same word, draft, appears in two fields and means two different things: where the post sits in the pipeline, and how settled its content is. A careless reader might call that a contradiction. A machine that knows the vocabulary is never confused, because the field a value sits in tells it which question is being answered. That is the whole reason we name things precisely and let a field carry a list when a file is genuinely more than one thing. This post will be regenerated, and it will change, and its own metadata tells you exactly that before you have finished the first paragraph.

That a file regenerates from a source, and that some things travel with the repository while others are rebuilt wherever they are read, is a larger story than one post. I told it on its own terms in Fat clones, thin clones, and the strawberry problem.

That is the payoff, and it is the reason the block exists. The machine never has to guess. The frontmatter tells it what the file is, who made it, who it is for, where the real copy lives, how settled it is, and how to act. We wrote it down so nothing has to be inferred. That is the whole of MX, in the space between two lines of three dashes.
