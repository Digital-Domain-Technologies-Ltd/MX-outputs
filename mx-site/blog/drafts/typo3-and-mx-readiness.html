TYPO3 and MX: where the CMS already gets it right

18 May 2026 · Tom Cranstoun · 6 min read

Earlier this year my team audited an enterprise TYPO3 site that runs to 14,264 URLs across ten locales. It is the kind of deployment TYPO3 was built for: a multilingual scientific publisher with a long, authoritative article library and a careful editorial workflow. I went into the audit expecting to find a CMS that needed a great deal of work to participate in the Machine Experience layer. I came out with a different impression. The work needed is real, but it is small, and most of it is configuration.

This piece is the short version of what I told the client. It applies to almost any TYPO3 deployment of comparable shape, and I think it is the most useful frame for anyone running TYPO3 today who is wondering where the platform sits in an agent-first web.

A fair test for a serious CMS

A CMS earns its place in the MX layer by answering one question well: when an automated reader fetches one of your pages, can it tell what the page is, who stands behind it, when it was published, and whether it may be cited? Not "can a browser render it nicely". Not "can a search engine index it". The agent test is narrower and harsher. The reader gets one HTTP fetch and the bytes that come back. Everything it needs has to be in those bytes.

The two ways a CMS can fail this test are well known. It can fail by hiding content behind client-side JavaScript that the reader will not execute. It can fail by serving content that is technically present but not machine-readable: no schema type, no author, no date, no structural landmarks. TYPO3 passes the first test cleanly. Where work is needed sits in the second.

What TYPO3 already gets right

The audit looked at ten dimensions across each page. Six of them came back in the Excellent or Good band, and all six map directly to choices the TYPO3 community has made deliberately over many years.

  • Server-side rendering. The served HTML and the rendered HTML differ by a single point in the agent-readability score. An automated reader that fetches the raw page sees what a browser sees. There is no JavaScript wall between the agent and the content.
  • JSON-LD in the document head. Structured data sits where the reader looks first. Every fetched page receives the structured data immediately, without needing to parse the body.
  • Security headers complete. HTTPS, HSTS, Content-Security-Policy, X-Frame-Options, and X-Content-Type-Options were present on every audited page. That is the table stakes layer of trust, and TYPO3 had it right.
  • BreadcrumbList implemented and valid. Navigation context is machine-readable across the article tree. Score: 100 percent on required properties.
  • Hreflang across ten locales. The multilingual architecture maps each localised page to its siblings correctly. A multilingual agent receives the right language variant on the first hop.
  • Heading quality and content ratio. A single H1 per page, no level jumps, and an average body-content ratio of 66 percent. The pages are content-heavy rather than overhead-heavy, which keeps agents inside their fetch window.

That is a strong baseline. It is not the baseline of a system that was retrofitted for machine readers; it is the baseline of a CMS whose default behaviour happens to be agent-friendly because the project values served HTML and editorial discipline.

Where the MX gap sits, and why it is narrow

The gap is not in the content. It is not in the data model. TYPO3 stores rich editorial metadata in its Table Configuration Array, known as TCA: the article title, the author, the editor, the creation date, the content category, the relationships between pages. Editors capture all of that as part of the normal workflow. The gap is that this metadata is not yet surfaced in the markup the agent reads.

Three specific shapes recur on TYPO3 sites of this kind.

  • The page type tells the wrong story. Article pages typically declare "@type": "WebPage" in their JSON-LD, which is Schema.org's most generic content type. An agent reading that string is told it is looking at "a web page on this domain". It is not told it is looking at a technical article written by named authors for a specific audience. The ranking and citation layer treats WebPage and TechArticle very differently. The data to support the better type already exists in TCA; the markup does not yet expose it.
  • Required properties are missing. Even on the generic WebPage type, the required name property is often absent from the JSON-LD block, despite the same string sitting in the <title> element. On article pages, author, datePublished, and about are the three properties an agent needs to cite the content with attribution. None of them require new content; they require a template change.
  • The governance layer is missing. A well-built TYPO3 site usually publishes a complete sitemap.xml from its page tree but stops there. The newer machine-readable governance files, llms.txt and a named-crawler section in robots.txt, are not yet generated. Agents fetch the site under no stated policy.

None of those gaps requires a content migration. None requires a CMS upgrade. All of them sit in the templating and configuration layer that TYPO3 was designed to make changeable.

The configuration changes that close it

The remediation list is short. I have put it in priority order, with the effort each item realistically takes.

  1. Upgrade the JSON-LD @type by page type. In the layout template that emits the JSON-LD block, branch on the page type and output TechArticle (or LearningResource for educational content) on article pages. This is a single Fluid conditional. The data already exists in TCA. Effort: low. Impact: this is the change that lets an AI assistant cite your articles with attribution.
  2. Populate name, author, datePublished, and about. These fields read from existing TCA columns: the page title, the author or editor relation, the creation or publication date, and the content category. Adding them to the JSON-LD template is a markup change, not a content one. Effort: low.
  3. Upgrade og:type on article pages. Change the Open Graph type from the implicit website to article, and add article:author and article:published_time. Open Graph metadata is read by social platforms and by an increasing share of AI systems that ingest page metadata alongside JSON-LD. Effort: low.
  4. Generate llms.txt from the existing page tree. In TYPO3 v12 and later, this is a Site Set configuration comparable in scope to the existing sitemap generator. It reads the same page tree and the same TCA fields. List the article pages with their content type and publisher, serve as text/html with the content in a <pre> block, and register the file in the sitemap so it enters Common Crawl's index. Effort: moderate, but the pattern is the same one the sitemap generator already follows.
  5. Declare AI crawler entries in robots.txt. Even when the policy is Allow: /, naming GPTBot, ClaudeBot, PerplexityBot, and Google-Extended explicitly signals publisher intent. Effort: a direct file edit.
  6. Three accessibility fixes that are also MX fixes. Add a skip link to the main page template; add <title> and <desc> to the inline SVG icon sprite; wrap article body content in an <article> element. Each of those is a single template-layer change that resolves multiple recurring issues across the entire site, and each one closes both a WCAG gap and an agent-readability gap. The same structural elements serve both audiences.

The full list above is, in TYPO3 terms, half a day of careful templating and a clean staging deploy. The data layer does not change. The editorial workflow does not change. The agent-readability profile changes from Basic to Structured: from "agents can discover" to "agents can cite and attribute".

The verdict

TYPO3 is, on the evidence of this audit and others like it, one of the better-suited enterprise CMSes for the MX layer. The reason is structural. The platform values served HTML over client-side rendering. It captures rich editorial metadata in a data model designed for reuse. It exposes a configuration layer (Site Sets, Fluid templates, TypoScript) that is built to be changed without touching content. None of that was done because the project was thinking about AI agents. It was done because the project takes publishing seriously. The two values turn out to be the same value, just looked at from different sides.

The platforms that struggle in agent audits tend to be the ones that delegated structure to the client side, treated editorial metadata as an SEO afterthought, or made the templating layer hard to reach. TYPO3 has done the opposite on all three fronts. That is why the remediation list is short.

The MX framing of this is straightforward. A CMS earns its place in the agent web by serving documents that machines can read, with the data they need to cite, under a governance policy the publisher has declared. TYPO3 is most of the way there by default. The changes that complete the picture are configuration changes, not architectural ones.

What to do next

If you run a TYPO3 site and the agent question is on your roadmap, the cheapest first step is to look at the JSON-LD on one article page and ask what @type it carries. If the answer is WebPage, you have the same opportunity I have described above sitting one template change away. The data is already in TCA. The configuration layer is already there. The work is to surface what your editors have already captured, in the place where the machine reader looks.

I am happy to talk through the specifics for any team that is making this move. The patterns recur, the remediation list is short, and TYPO3 deserves more credit than it usually gets for the foundation it provides.
