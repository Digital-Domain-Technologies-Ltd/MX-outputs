What a Worktree Does Not Carry

2 October 2026 · Tom Cranstoun · 5 min read

For a few days, every time I published a change to this site, the last line of the run said the same thing: Cloudflare purge skipped, credentials missing. The pages went live, the cache kept serving the old copies for a while, and I did what any tidy person does. I wrote a note asking for the credentials to be added to the settings file.

They were already there. They'd been there for months.

Where the Publishes Actually Ran

I run my AI coding assistant inside git worktrees. A worktree is a second working copy of the same repository, checked out into its own folder on its own branch. It's a lovely arrangement when several sessions are busy at once, because each one edits its own files and nobody treads on anybody else's half-finished work.

What I'd forgotten is how a worktree gets its files. It gets everything git tracks, and nothing git ignores. My .env file, the one holding the Cloudflare zone and token, is ignored on purpose, so secrets never end up in the history. So the worktree simply didn't have one. The purge script looked for .env in the folder it was running in, found nothing, and reported the credentials missing. Every word of that message was true about the folder, and wrong about my setup.

The Error Was About the Search

That's the bit I keep turning over. "Missing" sounds like a statement about the world. It's really a statement about where one program looked. The script never claimed to have checked my main checkout; I filled that part in myself, and then wrote it down as a task for someone else.

I've a rule for this in my own work, and I broke it: a proxy for a thing isn't proof of it. An error message is a proxy. So is a directory listing, an exit code from a pipeline, or a page that returns 404 when you didn't send your login. They all tell you something real, and they're all easy to read as something bigger. The fix is one cheap check before you write the conclusion. Here, opening the actual file would have taken seconds and saved a wrong note, plus the time to find and correct every place that repeated it.

The Other Things a Worktree Leaves Behind

Once I started looking, that session was full of the same kind of surprise.

  • Files that arrive later. My assistant writes a small session record when it enters a worktree. One day it wrote that record after the first commit instead of before, so the push ran the full suite of checks and then failed on an untracked file at the very end.
  • A branch older than main. A worktree starts from whatever the repository looked like when it was cut. Publish from it later, and you copy that older tree to the live site, quietly undoing whatever landed since.
  • Submodules. Content held in a git submodule isn't checked out in a fresh worktree unless you ask for it, so any tool that expects it either skips or reports it absent.
  • Guards that can't see out. My safety hooks refuse git commands they can't prove stay inside the worktree, which is right, and which surprises you the first time a perfectly harmless compound command is turned away.

None of these are bugs in git. They're the design. A worktree shares history and keeps its own working files, and that's exactly why it's useful. The trouble starts when a tool assumes it's running in the main checkout.

A Resolver, With a Test

The fix I wanted was one place that answers "where's the settings file?" properly, so I'd never have to remember the answer. Now there's a single function that reads the worktree's own .env if it has one, and otherwise asks git where the main checkout lives and reads that one. Every script that needs a setting goes through it, and the cache-purge hook falls back the same way.

It comes with a test that builds a throwaway repository, adds a worktree, and checks the cases that matter: a copy with no settings of its own reads the main checkout's, one with its own .env keeps it, and a folder outside git gets no surprises. The first purge run from a worktree after the change came back clean.

I could have written "remember that worktrees have no .env" in a checklist instead. That would have lasted until the next busy afternoon. A test doesn't get busy.

What I'd Pass On

If you run an AI agent in worktrees, and more teams do every month, it's worth listing what yours leaves behind: ignored files, submodules, anything newer than the branch. Then route the tools that need those things through something that knows where to look.

And when a tool tells you something is missing, take it as a report on where it looked. Go and check the place yourself before you ask anyone to fix it.
