Your Repo Is a Publishing Point Too

13 June 2026 · Tom Cranstoun · 6 min read
  • Practitioner
  • Machine Experience
  • MX foundations
  • Repositories
  • Governance

We talk about MX as something you do to web pages. Make the page state what it is so an agent reading it doesn't have to guess. That's the pitch, and it's a good one. But it undersells where the idea actually goes.

Your repository is a publishing point too.

Think about who reads a codebase. Not just you. The agent you've handed a task to, working on a branch. The build that runs on every push. The new hire on their first morning. Another project that pulls yours in as a dependency. Every one of those is a machine, or a person acting like one, meeting your files away from the moment and the mind that made them. That's the exact situation MX exists for. The only thing different about a repo is that we've never thought to treat it that way.

So I tried it. I pointed the same discipline at my own repository instead of at the pages it ships. Here's what happens when you do.

The repo starts to describe itself

Drop an agent into an unfamiliar codebase and watch what it does first. It tries to work out what the place is. Which folders are the source of truth and which are scratch. Which docs are current and which got abandoned two years ago. What's safe to edit, and what's generated and must never be touched by hand. With nothing to go on, it guesses all of that from file names and the shape of the directories, and every guess is a chance to be wrong in a way that costs you real money in tokens and, worse, in confident wrong edits.

Now give every file its own metadata, and keep a machine-readable map of the repo itself. The agent stops guessing and starts reading. It asks the repository what it is, and the repository answers. That's it. That's the whole trick, and it's the same trick we've been selling for web pages, just turned to face inward.

The funny part is that this helps the humans just as much. The questions an agent asks on its way in, where do I start, what's authoritative, what's safe to change, are the exact questions a new colleague asks. A repo that can't answer the machine can't answer the newcomer either. The two-week onboarding and the thousand wasted tokens are the same problem wearing different clothes.

Then it starts to check itself

Once the repo describes itself, it's making claims. And a claim is only worth as much as the thing that checks it. So you let the rules be checks instead of habits. If a rule can be enforced by a script, a script enforces it, and it runs every time, not when someone remembers.

This is the part people skip, and it's the part that matters. A rule that lives in your head, or in a line in the contributing guide, rots the first time everyone's busy. A rule that lives in a check that runs on every change can't rot quietly. Either it passes or it shouts. The repo stops asserting that it's correct and starts proving it.

And then it starts to heal itself

Here's where it gets fun, and where it gets dangerous.

A repo that knows its rules and checks them can also fix the places where things have drifted. Stale derived files get rebuilt. The boring, well-defined breakages get repaired without you. The really nice version even remembers a fix it's seen a few times and turns it into a rule, so it stops happening at all.

But, and this is the whole point of the post, a repo that fixes itself can also break itself, and it won't look like breaking. It'll look like tidying.

Say the repo rebuilds a map of itself while half of it isn't actually present. It doesn't crash. It cheerfully produces a perfect, clean map of the half it can see, and quietly drops everything else. Commit that and you've overwritten the truth with a smaller, plausible lie. Same with repairs: a link into a part of the codebase that happens to be missing right now looks identical to a link that points at nothing. "Fix" it and you've cut a real connection.

That's the trap. The failure isn't loud. It's confident, plausible, and wrong, and it passes review.

So the rule I'd put above every other one here: a repository should only heal itself when it can see its whole self. It has to know whether it's complete before it acts, and it has to refuse, loudly, when it isn't, rather than smooth over the gap. The skill that makes self-healing safe isn't the fixing. It's the judgement about when not to. A repo that fixes itself indiscriminately is worse than one that never tried, because it's wrong in a way you'll trust.

Competence and the judgement of when to use it are two different things, and the second is the one that keeps the first from hurting you.

Why bother

Because it's the same maths as the rest of MX, just paid down where the work actually happens. An agent that reads facts instead of guessing them makes the wrong edit that never has to be undone, which is the cheapest edit there is. The orientation it would have spent a fortune assembling, it reads in a glance.

And if you're in a regulated corner of the world, there's the part your auditor cares about: a repository that records what it is, checks its own rules, and can show its derived state was built from its sources in a way anyone can reproduce is a repository that can answer "how do you know this is what you say it is" with a record instead of a shrug.

The web spent thirty years being a passive thing machines had to decode, and it's paying for that now in every wrong answer an agent gives about a page. There's no law saying your repository has to make the same mistake. Make it explicit, make it checkable, let it mend itself within the limits of what it can actually see, and the next thing that opens it, human or agent, walks into a place that already knows what it is.

That's MX. It was never only about the pages.
