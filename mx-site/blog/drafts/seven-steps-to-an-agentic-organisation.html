Seven Steps to an Agentic Organisation, and Where Context Lives

25 October 2026 · Tom Cranstoun · 6 min read

Most organisations are still at the first rung of the move to agents while they shop for technology built for the last. What they need first is the discipline of the middle steps.

The seven steps are tool adoption, context on the file, harness first, going headless, governance, agent to agent, and orchestrated work. Two of them differ from the way this ladder is usually drawn, and both differences have one cause. A machine has no stake in its own errors, so whatever it relies on has to be checkable by whoever reads its work next.

At each step I set out what MaXinE, our engine, does as of October 2026, and what it doesn't do yet.

Step One: Tool Adoption

AI tools exist across the organisation and people run each one by hand. When someone closes their laptop, the automation stops. When they go on holiday, the workflow goes with them.

There's a second loss at this step that's easy to miss. When a file leaves the tool that made it, its context stays behind. The next reader, person or machine, gets the content without knowing what it is, where it came from, or what its purpose is.

Step Two: Context on the File

The usual answer is a knowledge graph in each department, each behind its own API gateway, so that sales queries engineering through an interface and agents don't cross departmental boundaries.

That works while the file stays inside the building. It fails the moment a file is emailed, published, attached to a contract or picked up by a supplier's agent. The context lived behind the gateway, and it stayed there when the file left.

MX puts the context on the file itself: what it is, who made it, when, from what, and how it may be used. An agent reads that from the file, inside the organisation or outside it, with no API call. Departments can still keep their boundaries; the boundary is declared on the file, so an agent can see it rather than guess it.

MaXinE already reads context this way. Asked about a web page, it answers from what the site declares: its MX head, the cog it links with <link rel="cog">, and the metadata on its images. That content is fetched through an egress guard and treated as untrusted data.

Step Three: Harness First

Build the evaluation criteria, routing rules and quality gates before choosing a model. The harness is the asset; the model underneath is replaceable. If swapping the model breaks the system, what was built is a dependency, not a platform.

Our own repository works to that rule: a check a script can do, a script does. The model gets only the decisions software can't make.

MaXinE is built the same way. Its AI router puts every provider behind one interface, a model registry holds more than one model, and a routing policy picks a model per task with a fallback order. Some decisions never reach a model at all: when someone asks how the product works internally, a deterministic rule answers before the decider runs.

Step Four: Headless

Every automation runs as a service, on a schedule or on a condition, without anyone logging in at nine in the morning. Organisations stall here, because nobody forces the move from a script on someone's desktop to a service that runs on its own.

MaXinE works as a hosted instance without the desktop app, and answers questions through one endpoint. It's designed to go where the organisation already operates: on one machine, on an internal network, or with external inference switched on deliberately. Not every deployment mode in that design is built yet.

Step Five: Governance

Every knowledge structure has access control from the start. Every agent has an owner, a declared boundary and an expiry date. An agent nobody has run for months, or whose evaluation scores have fallen below the line, is retired. A dead agent with live API keys is a liability.

Governance describes how you run, not a certificate that you comply. Machine-readable records make an audit possible; they don't pass it for you.

Agent expiry dates aren't a MaXinE product feature yet. We apply the practice in our own working repository: a person stays in command of each system, every AI call is logged centrally, and items that sit undecided are surfaced until someone decides them.

Step Six: Agent to Agent, Checked Before It Is Judged

Agent A finishes and hands off to agent B. The usual design puts a language model between them as a quality gate, judging every handoff.

That brings inference back at exactly the point step three removed it. A model judging a model's output is a second opinion with the same blind spots. Instead, a script checks everything that can be checked, such as the schema and the required fields. A model judges only what remains. And every handoff carries its provenance, so B, or a person reviewing later, can see what A read and what it produced.

Handoff checking between MaXinE agents isn't built yet. It's the next step on our ladder.

Step Seven: Orchestrated Work

Workflows run semi or fully automated. Agents take the volume and people deal with the exceptions. The organisation runs on agent output.

Authority stays with people. Agents act within a boundary a person has declared, and that same human decides when each system is used. Exceptions reach a human because the records at each step show where something didn't check out.

Where to Start

Most organisations reading this are at the first rung. Going headless is where the discipline shows, and I would put context on the file alongside it: an automation that runs on its own still needs to know what it's reading. Do that first, and everything that follows has something to check.
