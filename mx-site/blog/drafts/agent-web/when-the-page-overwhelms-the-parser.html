When the Page Overwhelms the Parser

24 June 2026 · Tom Cranstoun · 9 min read

There is a category of machine-readability failure that does not appear on the standard checklist.

You check for structured data: present. Semantic HTML: reasonable. llms.txt: declared. The JSON-LD validates. The heading hierarchy is correct. By every conventional measure the page is machine-ready. And yet a machine reading it in a constrained environment returns nothing — not incomplete data, nothing. The processing context ran out of budget before it finished.

This is the DOM complexity problem. It is not about any individual element being wrong. It is about aggregate structural weight.

The thing parsers do not do

When a human browser encounters a heavy page it slows down. It renders the above-fold content first, progressively builds the rest, and eventually finishes. The user might notice a delay. The page eventually loads.

A machine parser in a constrained environment does not do this. It does not progressively render. It does not defer non-critical work. It takes the whole document, allocates the memory it needs to hold that document, traverses it, and either finishes or stops. There is no graceful degradation into partial results. There is a budget, and when the budget is exhausted the work stops.

This matters because most machines reading your content are not operating with generous resources. Lightweight agents, local models, automated tools running within shared compute allocations — these are the machines that serve most users in most moments. The machines with abundant resources are the exception, not the norm. Designing for the exception is not designing for the audience.

Five things that add up

Individually, each of these is manageable. Together, they determine whether a constrained machine can process your page.

Element count. Every element in the DOM — every div, section, button, span — must be parsed and held in memory. A page with thousands of elements requires proportionally more memory than one with hundreds. This is not usually a problem. It becomes one when the other signals are also elevated.

Nesting depth. A deeply nested tree requires the parser to maintain a stack of parent contexts as it descends. Template-driven layouts that wrap content in layer after layer — a wrapper inside a container inside a section inside a row — accumulate this cost invisibly. The content at the bottom of the tree costs more to reach than the content at the top.

Inline data. JSON embedded directly in <script> blocks is efficient for client-side rendering: no extra network round-trip, data available immediately. For large datasets — maps with hundreds of markers, product catalogues, configuration objects — the effect is that the machine must parse and hold a large data structure as part of reading the HTML. That data is not content the machine needs. It is a client-side application concern that the machine cannot skip.

Here is where structured data becomes part of the same problem. A single <script type="application/ld+json"> block with a well-chosen schema type is exactly right. The trap is over-decoration: a Product graph with nested Offer and ShippingDetails and AggregateRating, a FAQPage alongside it, a BreadcrumbList, a WebPage wrapper — each individually defensible, collectively a substantial inline payload that the machine must parse before it reaches the content the schema was meant to describe. The very markup added to help machines read the page makes the page harder for constrained machines to process. I think of this as the over-decoration trap: the act of speaking more clearly to machines creates conditions that make the message harder to receive. The judgment call is which schema types genuinely serve a reader arriving without context, and which ones are on the page because someone ran a structured-data checklist. That judgment is a machine-readability decision, not just an SEO one.

Shadow DOM and Web Components. A custom element hides its internal markup behind a boundary that a document-level parser does not cross. The machine sees the tag; it does not see the contents, because those contents only exist after the browser instantiates the component. For a machine reading the served HTML without executing scripts, content inside shadow roots is invisible. The more of a page's content lives behind that boundary, the less a non-browser machine can read — and the more memory the browser-attached machine uses to instantiate components before it can read the page.

Concurrent third-party initialisation. Loading multiple external scripts — analytics, consent management, mapping libraries, A/B testing — starts concurrent activity from the moment parsing begins. Each competes for processing time and memory with the page's content. In a capable browser on good hardware, invisible. In a constrained processing context, collectively destabilising.

The tool that makes it worse

There is a category of product built specifically to address the problem of machine discoverability: automated GEO and LLM optimisation tools. They crawl your site, identify content, and inject structured data — JSON-LD, schema markup, entity annotations — on the theory that more machine-readable signals means better AI citation. The category includes tools like Enhancely, Adobe LLM Optimizer, SiteUp, and AthenaHQ, among others. They are marketed as the machine-readability answer.

Here is the problem. Each JSON-LD block these tools inject is inline data — exactly the signal we just discussed. A tool that adds structured data to help machines read the page is adding to the inline data weight the same machines must parse before they reach the content the schema was meant to describe. The over-decoration trap applies to automated injection just as it applies to hand-crafted schema.

The tools vary in how responsibly they operate. Adobe LLM Optimizer requires explicit human approval before any change reaches production and deploys at the CDN edge, so it leaves no injected script tags in the source HTML. Enhancely runs a factuality-validation pipeline before injecting — checking that extracted values actually match the page content — but injects automatically without per-page approval. Others operate at higher volume with less documented oversight, generating schema across hundreds of pages without a human in the loop.

The provenance gap is the deeper problem. Most of these tools produce no record of what was injected, when, by which version, or who reviewed the output. An AI agent reading the page sees structured data but has no way to know whether it was written by the publisher, validated by a tool, or generated from a template and never reviewed. That ambiguity is exactly what MX was built to address — metadata that travels with the content and records who produced it, when, and under what authority. A tool that injects schema without a provenance record bypasses the practice MX is trying to establish.

Knowing which tools are running on a site, what they inject, and whether their output has been validated is itself a machine-readability discipline. It is not an SEO configuration question.

Why it is additive but the risk is multiplicative

A page with one of these signals elevated is unlikely to cause failures. A page with all five elevated at once can push a constrained parser past its threshold before it has finished reading the content you actually want machines to find.

The problem is invisible in a browser, which is why it escapes standard audits. Open the page in Chrome: it loads, perhaps slowly, but it loads. Check the structured data: it is there. The machine-readability checklist passes. The constrained parser, operating without a full browser context, running within a shared memory budget, hits the threshold and stops.

The checklist was not wrong. It just was not checking for this.

What to do about it

None of this requires abandoning modern web patterns. It requires being deliberate about where weight accumulates.

Move large datasets out of the page. Data that drives a client-side interface belongs at an API endpoint, not embedded in the HTML. The page declares that data exists and provides the fetch path; the application retrieves it on demand. This reduces the served document size and means machines reading the HTML see content rather than an application state object.

Render machine-critical content in the served HTML. A custom element that contains a product description, a price, or a contact address should render that content in the document rather than only inside the shadow root. The component can use the shadow DOM for styling and interaction; the machine-facing information should exist in the base layer. The same principle applies to dynamically loaded content: if a machine needs it, it should survive a plain HTTP fetch.

Audit third-party script loading. Each external script domain adds initialisation load. The question is not whether analytics and consent management are necessary — they usually are — but whether they are being loaded as efficiently as possible. A single tag manager loading multiple scripts sequentially is lighter than multiple scripts loading independently in parallel. Scripts that are not needed for initial rendering should be deferred until the content is available.

Test without a browser. Fetch the page with curl. Parse it with a plain HTML parser. Check whether the content you expect machines to find is present in the result. If it is, the page is structurally accessible to constrained parsers. If it is not, the content depends on script execution that non-browser machines cannot perform — and the question is whether that dependency is intentional.

The machines this reaches

There is a useful framing here that I keep coming back to. The machines that serve most users at most moments are not the most capable ones. They are the ones running under constraints: limited memory allocations, shared compute budgets, processing windows that close when a deadline is reached.

Reducing structural complexity does not make a page worse for capable machines. It makes it better for constrained ones. And reaching constrained machines means reaching the widest possible audience — the same principle that underlies accessibility, and for the same structural reasons.

A page that serves its content to a lightweight agent with a modest memory budget serves it to every machine. That is the goal MX has always pointed at: content that reaches every reader, human or machine, capable or constrained, without the reader needing to know anything special about the page to get what they came for.

Structural complexity is one more thing a page can silently get wrong. Now you know what to look for.
