One Context, Many Harnesses

14 October 2026 · Tom Cranstoun · 7 min read

A friend who runs an agency asked me a question I hear more and more. They run several AI harnesses now: one for coding, one from Anthropic, one from OpenAI, an open-source agent, a hosted platform for the marketing team. Over time they've each built up a private memory of how the business works. And the memories don't agree any more.

That's the problem in one line. Every harness wants to be where your context lives, and once you run more than one, you've got several private copies of the truth drifting apart.

We hit this early, because our own repository is worked on by several harnesses every day. Here's what we settled on, what it does well, and where it still falls short.

Where the Context Should Live

The fix starts with a decision: treat each harness as a reader of your context rather than its home.

We keep ours in a git repository, as plain markdown files. Every one opens with a short metadata block giving its purpose, its audience, how a machine should use it, and its links to other files. We call these files cogs, and the cog format is public, but the idea works with any convention your team will keep. The point is that the file explains itself to whichever machine opens it, so nothing depends on one tool remembering what it meant.

Git does the rest. You get a history of every change and the ability to roll one back, and you can see who changed a rule and why. A vendor's memory feature gives you none of that.

A Pointer for Every Harness

Every harness already looks somewhere for project instructions at start-up. So we put a pointer in exactly that place, and it says one thing: read the rules file, and if we ever disagree, the rules win. A pointer carries no rules of its own. If one starts accumulating instructions, it's drifting.

Harness Where it reads project instructions
Claude Code CLAUDE.md
OpenAI Codex AGENTS.md
Hermes Agent AGENTS.md, unless a .hermes.md or AGENTS.override.md is present
Gemini CLI GEMINI.md
Cursor .mdc files in .cursor/rules/, and AGENTS.md
GitHub Copilot .github/copilot-instructions.md, and AGENTS.md
Windsurf .windsurf/rules/ (or the older single .windsurfrules), and AGENTS.md
Continue .continue/rules/

Look at how often AGENTS.md turns up. Codex reads it before it does any work (OpenAI, n.d.), Cursor, Copilot and Windsurf read it beside their own files (Cursor, n.d.; GitHub, n.d.; Windsurf, n.d.), and Hermes loads the first it finds of .hermes.md, AGENTS.override.md, AGENTS.md, CLAUDE.md and .cursorrules (Nous Research, n.d.). A well-kept AGENTS.md reaches most of the list on its own. A stray .hermes.md would quietly take Hermes somewhere else.

The overlap is also the best argument for keeping rules out of the pointers. Several tools read more than one file, so a rule written into two of them is two rules, and the day they disagree you've no control over which one the agent follows. GitHub's own advice is to avoid conflicting sets of instructions, because Copilot is given all of them at once (GitHub, n.d.).

I'll admit ours isn't perfect on this. Our CLAUDE.md carries rules of its own, because Claude Code is the harness we lean on hardest, and it's the file most likely to drift from the rest. The other pointers are a few lines each.

The rules file also asks each agent to identify itself before it applies anything, by checking a short list of signals such as an environment variable its harness sets. An agent that can't place itself says so in its first reply instead of guessing, so it never applies rules meant for a different tool.

Hosted Tools That Can't Read Your Repository

Some platforms never see your files. They're hosted, and all they give you is an instructions box. For those, paste or sync the canonical file into the box, and treat what you pasted as generated output: you regenerate it from the source, and nobody edits it in place. It's the copy most likely to drift, because it's the only one you can't check from the repository.

I'll be straight: we haven't tested this against a hosted marketing platform. It's the right shape, but I can't tell you yet how well any particular platform holds a long instruction file.

Write What the Agent Learns Back to the Repository

Reading one context is half the job. The other half is what happens when an agent learns something worth keeping: a correction, a client's naming rule, a mistake it shouldn't make twice.

That learning goes into a file alongside the rest of your context, not into the tool's private memory. Once it's there, every harness on every machine picks it up on the next pull. A new colleague's assistant gets the team's accumulated practice on the first clone.

Here's the gap. In our setup, the write-back is automatic for Claude Code only. The other harnesses read the same files, but they don't yet write their learnings back without a person moving them. If you run several harnesses as heavily as we run one, that's the piece to design first.

If a Script Can Check It, a Script Does

An agent will eventually forget any instruction that exists only in prose. Whatever can be checked mechanically gets a script that runs before anything is pushed. That holds no matter which harness is driving, because the gate doesn't care who wrote the change.

Pointers need this too. When I audited ours against each vendor's documentation, two sat in places their tools never read, one sent its reader to a path outside the repository, and two harnesses had no signal that would let them identify themselves. Nobody had noticed, because each pointer looked fine on its own. So we check them before every push: each pointer has to exist where its harness reads, and has to resolve to the rules file. It's a short script, and it would have caught every one of those on the day it broke.

There's a quieter win as well. An agent that boots from a clear, current file spends less effort working out what you meant. That means less spent on tokens and fewer wrong guesses, and over a team running several harnesses all day, it adds up.

What's Still Open

The pattern holds, and it's where I'd start. These parts aren't solved, at least by us:

  • Write-back from every harness. Only Claude Code does it on its own; for the rest, a person moves the learning across.
  • Hosted platforms. The generated-copy approach is sound on paper and untested in practice.
  • Conflicting learnings. When two harnesses learn opposite things on the same day, git shows you the conflict. It doesn't resolve it for you, and it shouldn't.

If you want to try it, start small: one rules file, and one pointer for the harness you use most. Add another pointer each time a new harness arrives. The smallest working version, with the pointer check, is a free starter kit under the MIT licence: one-context-kit on GitHub. For the wider argument about why every agent platform keeps rebuilding this layer, see Many Agents, One Metadata Layer.
