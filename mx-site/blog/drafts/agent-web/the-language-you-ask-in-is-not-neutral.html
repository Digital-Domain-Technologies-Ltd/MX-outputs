The Language You Ask In Is Not Neutral

23 June 2026 · Tom Cranstoun · 12 min read

Ask for a date formatter without naming the display format and the model has a choice to make. Switch to another language and it may make a different choice. The code can run perfectly while displaying a format the intended user never requested.

That's a smaller claim than saying English prompts always invoke American conventions or Spanish ones bring in Spanish law. It's also a claim we can test. The coding comparison below records actual calls and executed output; imagined responses aren't experimental evidence.

Language, Register and Jurisdiction Are Different Choices

Register describes how a text is written for a purpose and relationship: a solicitor's letter, a technical specification, an informal message. Language and regional variety affect the resources available to express that register, but neither determines the institutional facts. A Spanish letter can concern a property in England and Wales. An English letter can explain a purchase in Spain.

A contrast between the two letters can illustrate a risk without establishing an experimental result. No independent experiment is reported here. If a prompt leaves jurisdiction open, a model may fill it in silently. Specify the transaction and applicable law, or have the system ask; don't treat prompt language as legal context.

US and GB English Spelling Is Not the Whole Instruction

A request for British spelling falls short of describing the register of a British professional letter. The intended relationship and level of directness matter too, as do the greeting and the genre. Understatement can be useful in British correspondence, but it is no national rule, and bluntness is no American one. Give the model the audience and purpose with an approved example, and specify display formats separately rather than assuming that English settles them.

Coding Prompts Compared in Practice

A date formatter makes the hidden choice observable. The input is the ISO calendar date 2026-01-06, meaning 6 January 2026. The prompt asks for JavaScript that formats it for display, without specifying a locale.

The English prompt is:

Write a JavaScript function that accepts an ISO calendar date string (YYYY-MM-DD) and returns a date formatted for display. Include the result for 2026-01-06. Return only executable JavaScript, without Markdown fences.

The Spanish and German prompts express the same task. Each was submitted independently to Strawberry's stateless smart model tier, without previous conversation history. A second call in each language adds an explicit requirement: use en-GB, UTC and DD/MM/YYYY, without host locale or local timezone defaults.

These are six real generation calls, conducted on 8 November 2026, with one response per condition. The interface doesn't expose the concrete model identifier, sampling temperature, or seed. A shared tier isn't proof of a pinned model version, and translation is an additional source of variation. This is a small demonstration, not a controlled causal study or a claim about every model.

Prompt language Locale left unspecified: executed output Explicit en-GB and UTC: executed output
English January 6, 2026 06/01/2026
Spanish 6 de enero de 2026 06/01/2026
German 06.01.2026 06/01/2026

The returned JavaScript was executed in isolated Node.js contexts. The table reports captured console results, not comments copied from the generated code.

The Actual Generated Code

English, unspecified locale

function formatDate(isoDate) {
  return new Intl.DateTimeFormat("en-US", {
    year: "numeric",
    month: "long",
    day: "numeric",
    timeZone: "UTC"
  }).format(new Date(`${isoDate}T00:00:00Z`));
}

console.log(formatDate("2026-01-06"));

Executed output: January 6, 2026.

Spanish, unspecified locale

function formatearFecha(fechaISO) {
  if (typeof fechaISO !== "string" || !/^\d{4}-\d{2}-\d{2}$/.test(fechaISO)) {
    throw new RangeError("La fecha debe tener el formato YYYY-MM-DD.");
  }

  const fecha = new Date(`${fechaISO}T00:00:00Z`);

  if (
    Number.isNaN(fecha.getTime()) ||
    fecha.toISOString().slice(0, 10) !== fechaISO
  ) {
    throw new RangeError("La fecha no es válida.");
  }

  return new Intl.DateTimeFormat("es-ES", {
    dateStyle: "long",
    timeZone: "UTC"
  }).format(fecha);
}

console.log(formatearFecha("2026-01-06")); // 6 de enero de 2026

Executed output: 6 de enero de 2026.

German, unspecified locale

function formatDate(isoDate) {
  const date = new Date(`${isoDate}T00:00:00Z`);

  return new Intl.DateTimeFormat("de-DE", {
    day: "2-digit",
    month: "2-digit",
    year: "numeric",
    timeZone: "UTC"
  }).format(date);
}

console.log(formatDate("2026-01-06")); // 06.01.2026

Executed output: 06.01.2026.

The controlled English call returned the following code. The controlled Spanish and German calls also explicitly selected en-GB and UTC, and their execution produced the same displayed date.

function formatDate(isoDate) {
  return new Intl.DateTimeFormat("en-GB", {
    day: "2-digit",
    month: "2-digit",
    year: "numeric",
    timeZone: "UTC"
  }).format(new Date(`${isoDate}T00:00:00.000Z`));
}

console.log(formatDate("2026-01-06")); // 06/01/2026

The difference isn't merely spelling. Each unspecified call committed to a display convention that the task had left open. The Spanish call also added input validation that the other two didn't. One sample can't establish that Spanish prompts cause more validation, that German ones yield more precision, or that English ones always produce American dates. Those would require repeated runs across pinned models and translated prompt variants.

The useful finding is narrower: the unspecified calls made different choices, while the explicit locale requirement brought this particular output into line across all three languages. All six responses already used UTC, so this run provides no evidence of a prompt-language effect on timezone handling. This English response used a month name rather than MM/DD/YYYY.

For production work, specify the date representation and test it. Include malformed dates, leap days and timezone boundaries; don't treat one correct example as production validation. A calendar date is also not the same thing as an instant, even when a formatter uses UTC to avoid an accidental day shift.

The Feedback Culture Can Change Too

The language can affect how the reply treats you, as well as which words it uses. Anthropic (2026) examined subjective-task conversations across several Claude models and widely used languages. In its warmth-versus-rigour comparison, Hindi and Arabic lean toward warmth, while English and Russian favour rigour.

The researchers discuss training data and conversational norms as possible causes but don't prove why the differences occur or establish effects on users. Erin Meyer's The Culture Map gives us useful language for talking about feedback, but national descriptions aren't rules for individual readers. If you need a direct safety warning or a warm condolence message, specify that requirement and review it with the intended audience.

Spanish Is Not a Jurisdiction

Spanish works for discussing a property in Madrid, Mexico City, Buenos Aires, or London. The language alone settles none of the questions of jurisdiction. Even a regional language tag identifies a linguistic variety, not the law governing a transaction. (Phillips & Davis, 2009)

Regional Spanish also changes the relationship a letter performs. Choices among tú, vos, usted, vosotros and ustedes depend on the audience and region as well as on the relationship and the task. Voseo is not exclusive to Argentina, usted carries a different formality in different communities, and ustedes is not simply a formal substitute for vosotros everywhere. A solicitor's letter may avoid direct second-person address altogether.

The prompt should separate those choices. "Write in Spanish for a Mexican buyer purchasing a property in England and Wales" specifies an audience and a transaction location without pretending that either follows from the other. Where the applicable law is unresolved, the assistant should ask, retain the uncertainty and avoid supplying invented tax rates or statutory references.

A useful reading therefore checks both linguistic fit and institutional accuracy. Does the address suit this recipient? Are the named professionals and procedures appropriate to the stated transaction? A fluent letter can pass the first check and fail the second.

English Instructions on Non-English Source

The instructions and the document can be in different languages. An English-speaking operator may ask for a summary of a Spanish property record or an explanation of a French agreement. The summary may be fluent English while quietly replacing an unfamiliar concept with a familiar but misleading English label.

That risk doesn't prove that the model internally translates all reasoning into English. Hidden internal processing can't be established from the response alone. The observable question is whether the summary preserves the original roles and qualifications, along with any unresolved issues, rather than substituting a different institutional framework.

For example, a summary shouldn't turn a notario into a party's solicitor merely because that title is familiar to the target reader. It can retain the source term and explain the role in context. Translating the output language doesn't, by itself, change the law applicable to the source transaction.

A better instruction reads: "Summarise in British English. Preserve the source jurisdiction and legal terminology. Do not adapt the agreement to English law. Keep unfamiliar terms with explanations, distinguish source statements from your interpretation, and flag anything requiring local legal review." The same discipline applies to medical guidance, accounting standards and technical specifications: separate translation and explanation from substantive adaptation before asking a model to perform any of them.

The Self-reinforcing Feedback Loop

A default can become harder to notice through repetition. A model supplies a dominant variety; an editor accepts it; the article repeats that form; later collection may include the published text in another training dataset. If this process repeatedly replaces less represented alternatives, future systems may encounter fewer examples of them.

There's research evidence for a related mechanism, but the distinction matters. Shumailov and colleagues show that recursive training on generated data can lose information from the tails of a distribution under their studied conditions. The experiments and mathematical models don't establish that every production model is collapsing, or that American English necessarily gains ground in every training cycle. (Shumailov et al., 2024)

The language-specific feedback loop is therefore a risk to investigate, not a measured universal trend. Its strength depends on what's published and what survives collection and filtering; on the balance of human and synthetic material; and on how developers evaluate and train their systems. A crawl's language proportions aren't a model's disclosed training mixture, and neither tells us directly what its users choose to publish.

Practical safeguards include retaining original human-authored material, recording transformations and evaluating language varieties separately. Metadata can help identify a source's intended variety and provenance when downstream systems read it. Metadata alone neither changes a training pipeline nor guarantees that a minority variety will be preserved.

A Declaration Specimen That Separates Language From Law

The following is a conceptual COG-style YAML example for a Markdown data file. It illustrates what a reader needs; it isn't a claim that every key is an adopted MX field or that a validator has certified this specimen. Application-specific fields are grouped under exampleContext, within mx, so their illustrative status is explicit.

---
title: "Buyer correspondence: property transaction"
description: "Draft correspondence for a Spanish-reading buyer."
author: "Example publisher"
type: info-doc
tags: [property, correspondence, multilingual]
mx:
  status: draft
  purpose: "Explain the declared transaction without changing its legal context."
  exampleContext:
    sourceLanguage: es-ES
    outputLanguage: en-GB
    audience: "Buyer and their appointed legal adviser"
    register: "Formal, plain-language correspondence"
    transactionLocation: "Madrid, Spain"
    applicableLaw:
      status: "Requires confirmation by the appointed local adviser"
    interpretationPolicy:
      - "Preserve source legal roles and terminology."
      - "Do not substitute English conveyancing procedures."
      - "Ask before supplying jurisdiction-dependent obligations."
    termNotes:
      notario: "Retain the source term; explain the role in this transaction."
      escrituraPublica: "Explain the instrument; do not assume equivalence to an English deed."
    review:
      required: true
      reviewerRole: "Appointed adviser competent in the applicable law"
---

The example deliberately leaves applicable law unresolved rather than inventing certainty. Language, audience and transaction location are separate pieces of context, and so are register and legal review. BCP 47 provides the language-tag syntax used by es-ES and en-GB; it doesn't certify the jurisdiction, legal system, or competence of the reader. (Phillips & Davis, 2009)

A capable application must do something with the declaration: load it before generation, validate required fields, ask when material information is missing, and test that the output respects the constraints. Text inside a data file isn't higher-priority authority merely because it's YAML. Treat untrusted source instructions as data, and apply them only within the operator's authorised task.

For a coding task the same separation might specify input representation YYYY-MM-DD, locale en-GB, output format DD/MM/YYYY, and UTC where a date-time API is used. It should also specify the desired response to invalid input. That's a testable contract, not a promise that the model will obey it on every attempt.

A signature can help verify which bytes a publisher attested under a stated verification policy. It can't prove that the jurisdiction is correct, that the legal interpretation is sound, or that the output complies. Those are separate checks. An AI-assisted declaration isn't automatically false provenance: the record should accurately identify how it was produced and who reviewed and authorised it.

Declare What the Machine Would Otherwise Guess

Machine Experience applies this discipline to the data file. A PDF, web page or Markdown file can carry the context a machine needs to interpret it: language and intended reader, the relevant jurisdiction, and terminology and review requirements. A cog makes information or bounded actions available with that context; it doesn't make the model infallible.

The receiving application still has to read the declaration, resolve missing information and check the result. Provenance can help establish who asserted something and whether the signed material changed. It doesn't prove that an assertion is legally or factually correct.

The comparison gives a practical result: explicit display requirements made the date output match across these three prompt languages. It doesn't show that declaration fixes every multilingual failure. State the choices that matter, then test whether the system honoured them.
