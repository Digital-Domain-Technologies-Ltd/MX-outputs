Your Site Generator Should Emit llms.txt Automatically

30 June 2026 · Tom Cranstoun · 6 min read

Every modern site generator does the same three things automatically: it emits sitemap.xml, it emits robots.txt, and it emits feed.xml if you publish anything subscribable. These are standard. You do not hand-author them. The generator reads your site structure and produces them.

llms.txt should be on that same list. But it is not. Most teams either skip it or hand-author it once and then abandon it when the next product launch or service change lands.

Hand-authored llms.txt is an anti-pattern. It goes stale. It becomes a liability. And the fix is the same one that solved this problem for sitemaps: automate it.

The Hand-Authored Problem

A team creates an llms.txt by hand. They describe their services. They list their key pages. They commit it. It sits on the server.

Three months later, a service changes. A new offering launches. The team updates the homepage, the services page, the pricing page. Nobody remembers to update llms.txt. It now describes an old version of the company. An LLM querying the site reads the outdated index and serves incorrect information.

Six months later, the team discovers the gap. They update llms.txt again. But because it is manual, it is not part of the deployment pipeline. It is easy to skip when things are busy. It gets lost in the backlog.

This is the same problem that plagued hand-authored sitemaps before generators took over. Humans forget. Generators do not.

Why This Matters Now

The previous post in this series established that llms.txt is no longer optional:

  • It saves 97% of inference tokens when an AI agent researches your site internally or externally.
  • It is tested by Google's own auditing tools, whether Google's guidance admits it or not.
  • It is the fastest, cheapest way to give an LLM a current, authoritative description of your site.

(Read Google Says Ignore llms.txt, Then Tests for It for the full case.)

But this value only materialises if the file is current. Stale llms.txt is worse than no llms.txt at all, because it is authoritative-looking while being wrong. An LLM will trust a structured description from your own domain more than it trusts general knowledge. If that description is outdated, you have poisoned the well.

The only way to keep llms.txt current is to stop thinking of it as a manual document and start treating it as a generated artefact, the way you treat sitemaps and robots.txt.

What the Generator Should Do

A site generator that emits llms.txt should:

  1. Read your actual site structure. Parse the navigation, the page hierarchy, the published content, the metadata tags. This is the ground truth. The generator already does this to build the site.

  2. Extract structured information. From page titles, descriptions, categories, and tags, derive: what does this site do? What are the main sections? What actions can a visitor take? What is the business model?

  3. Emit a current llms.txt at the root, describing the site in clear, structured terms. Include: the site's purpose, the key offerings or sections, links to the major entry points, contact information, and a note of when the file was generated (so an LLM can assess freshness).

  4. Wrap it as HTML (this is the technical requirement from the previous post). The generator emits both the plain-text version and an HTML wrapper served with Content-Type: text/html, so crawlers can index it.

  5. List it in sitemap.xml. The generator adds the /llms.txt URL to the sitemap with a priority marker (high, because this is important discovery information) and a lastmod timestamp matching the build date.

  6. Add a link tag to every page. In the <head> template that runs on every page, add <link rel="llms-txt" href="/llms.txt"> so any LLM that lands on any page knows to read the index first.

All of this runs during the build. Every time you deploy, llms.txt is regenerated from your site's current state. It never drifts. It is always authoritative.

Why Generators Do Not Do This Yet

Three reasons:

  1. llms.txt is recent. Most site generators were built before Jeremy Howard proposed it in September 2024. Migration takes time.

  2. The value was unclear. Earlier guidance focused on training data (long-term, uncertain). Now that the query-time value is obvious (immediate, measurable, energy-saving), the case for automation is much stronger.

  3. It requires metadata discipline. The generator needs well-formed frontmatter or metadata on pages (title, description, category, purpose) to derive a meaningful index. Many sites do not have that. But many do, or should. And if a site wants an LLM to understand it, metadata discipline is non-negotiable anyway.

The Transition Path

If you maintain a site generator:

  1. Add automatic llms.txt generation to your build pipeline. Read the site structure, extract metadata, emit a plain-text index describing what the site does.

  2. Wrap it as HTML at serve time or build time (your choice; a build-time wrapper is cheaper).

  3. Add it to the sitemap during generation.

  4. Inject the link tag into your page templates.

  5. Document the feature and mark it no longer optional. Every site should have this on.

If you maintain a website:

  1. Audit your generator. Does it emit llms.txt? If not, ask the maintainers to add it or switch to one that does.

  2. Ensure metadata is complete. Every page should have a clear title, description, and category tag. This is what feeds the generator.

  3. Test it. Ask an LLM to research your site, give it your llms.txt first, and confirm it works.

  4. Stop hand-editing it. If the generator owns it, do not fork and hand-maintain. Any manual edit will be overwritten at the next build anyway.

The Standard

This is becoming a content-operations baseline. Just as you expect any CMS to generate robots.txt, sitemap.xml, and feed.xml without asking, you will soon expect it to generate and maintain llms.txt as a standard part of the deployment.

The sites that have already done this will be the ones that serve LLMs accurately and efficiently. The ones that have not will be the ones that confuse or misdirect them.

Automate it. It is too important to hand-maintain.
