Can an Agent Actually Use Your Site?

24 June 2026 · Tom Cranstoun · 4 min read

There is a question I have been asking sites for a while now: what does an agent see when it reads you? It is a good question, and the answer surprises most owners. But lately I have been asking the harder one. Reading is the easy half. The agents turning up now do not just read. They act. They are sent to find a price, fill a form, pick a plan, get to the thing you actually want a visitor to do. And reading the page tells you almost nothing about whether they can.

So I stopped guessing and started watching. I drive a real browser the way an agent drives one, and I follow it through a simple task on the page. Not "did it load". Did it get there.

An agent does not see the page you designed

When you look at your site, you see the design. The agent does not get the design. It gets the accessibility tree, the same underlying structure a screen reader works from: a list of things with names and roles. A button called "Buy now". A link called "Pricing". A field labelled "Email". That tree is the page, as far as the machine is concerned. Anything that is only in the picture, only in the colour, only in the position, is not in the tree, and so it is not there.

This is why an agent can fetch your page, report that it loaded fine, and still be completely stuck. It read something. It just could not find the part it needed in a form it could act on.

Where it gets stuck is invisible to you

The frustrating thing is that the blockers are exactly the ones you never notice, because for you, with a mouse and a pair of eyes, they are not blockers at all.

A button covered by a cookie banner. You dismiss the banner without thinking; the agent reaches for the button and gets told it is hidden behind an overlay. A control that is really a styled box with no name, so the tree shows "clickable thing" where it should show "Add to basket". A menu that only opens on hover and never announces itself, so the agent simply cannot see that the rest of your site exists. A checkout step gated behind something that needs a real pointer. Each one is fine for a human and a dead end for the machine.

You will not find these by looking at your site, because you do not experience them. You find them by sending something that does.

So I send something that does

The test is plain. Open the page the way an agent would. Take the accessibility tree, the machine's-eye view, and look at it honestly: how many things on this page can a machine actually name and reach? Then try the task. Find the navigation. Find the primary action. Get to it. And when it cannot, write down why, in the agent's own words: covered by this, named nothing, never reached the tree.

The result is a verdict you can act on. Not a score for its own sake, but a short answer to a question you cannot answer from the design view: could an agent navigate this page and do the thing, or not, and where exactly did it fall over.

It is the same fix that helps people

Here is the part I like. None of this is a special agent project bolted on beside your accessibility work. It is the same work. The button with no name fails the agent and the screen-reader user in the same breath. The menu that never reaches the tree is lost to both. Fix it once and you serve the machine and the person at the same time, which is the quiet through-line of all of this: the page that is good for the machine was already the page that was good for the human you were leaving out.

The agents are not waiting for permission. They are already turning up with a task and trying to complete it on your pages, and most of the time nobody on your side ever learns that they failed. The point of watching one do it is simple. You get to see the wall before your customer's agent does, while there is still time to take it down.
