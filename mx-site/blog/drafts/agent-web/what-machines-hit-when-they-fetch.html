What a Machine Hits When It Fetches Your Page

7 June 2026 · Tom Cranstoun · 7 min read

I sent an agent to read an essay. It came back with three words: Host not in allowlist.

That particular wall was mine. My own network policy had blocked the fetch before it left the building. But the three words sent me somewhere useful, because they are the machine's whole experience of the web in miniature. An agent asks for a page. Something between the request and the meaning gets in the way. The agent does not knock twice. It records the dead end and moves on.

So I spent an afternoon cataloguing the dead ends. What surprised me is how few of them are deliberate. A handful of sites genuinely slam the door. The rest are own goals: the content is sitting right there, and the page hides it from the machine by accident.

The walls, sorted by who built them

The first group is the painful one, because the work is already done and thrown away.

A page rendered in the browser sends a machine almost nothing. Most agents fetch the raw HTML, read what is in it, and leave. They do not run JavaScript, they do not wait, they do not retry. A single-page app answers that request with an empty shell: a root element, a spinner, and a pile of script tags. The article exists. The agent captured a loading state.

The same trap swallows structured data. A page that injects its JSON-LD after load has injected it into a room the machine already left. If the schema is not in the first response, it was never said. Lazy-loading and infinite scroll lose everything below the fold. Tabs and accordions lose everything behind a click. Text baked into an image, or a PDF with no tags, is text the machine cannot read at all. And underneath all of it, a page built from anonymous containers, with no headings and no landmarks, gives the machine no way to tell a title from a footer. The same missing structure that fails a screen reader fails an agent, for the same reason.

The second group is the half-open door. A consent banner that gates the body behind a button the agent will not press. A paywall that returns nothing rather than a useful preview. A "not found" page that reports success, so the agent files an error message as fact. None of these is malice. Each is a default nobody revisited.

The third group is the only one built on purpose: the bot blocks, the rate limits, the fingerprinting that flags a visitor for clicking too precisely. These are a choice, and a defensible one. But they are also the smallest group, and the least of the problem. Most pages are not refusing the machine. They are failing to speak to it.

How agents cope, and what coping costs

Faced with a page that returns a spinner, an agent does not give up. It climbs.

The cheapest move is the one most agents make most of the time: a plain request for the raw HTML, read and done. This is what my own tooling does, and it is what the large crawlers do. It costs almost nothing, which is exactly why it is the default.

When that returns an empty shell, the agent reaches for something heavier. A reading service that renders the page on its behalf and hands back clean text. A pre-built index where the hard rendering happened once, offline. Heavier still, a real browser driven under automation that can click, scroll, and wait. At the top sit the new agentic browsers that run a full browser per visit and look, in the logs, exactly like a person.

Every step up that ladder works. And every step up that ladder costs more: more time, more memory, more money, more energy. The page that renders in the browser does not just lose the cheap reader. It taxes the capable ones, on every visit, forever. A page that answers the first plain request never forces anyone to climb. It is read once, cheaply, and understood.

This is the part worth sitting with. Machine-readability is not a favour you do for one well-behaved crawler. It is the difference between a web that can be read for the price of a request and a web that has to be rendered, again and again, at the cost of a small data centre running quietly in the background.

The agent can throw it away too

The page is not the only one that can lose the structure. The agent can discard it on purpose. A growing number of tools do not ask for the page at all; they ask for a Markdown rendering of it, or run the HTML through a converter before reading, because Markdown is cheaper to tokenise. The conversion keeps the prose and drops everything around it: the JSON-LD, the meta tags, the microdata, the machine-legible source the page carried in its head. An agent that reduces a page to Markdown has thrown away the machine-readable layer as completely as the raw fetch that never ran the JavaScript, only this time it did the stripping itself. Fetching and format are two faces of one obligation. A page has to put the meaning in the raw HTML; an agent has to read it in a form that keeps it.

The point of the metadata

This is the work I spend my days on, so let me be plain about where it lands. The fixes for the first two groups are not exotic. Render the meaning into the HTML the server sends. Put the structured data in that first response. Use real headings and real landmarks. Load the meaning near the top, before the cut, because the machine often only sees the first slice. Let the page carry a machine-legible account of what it is, in its own markup, so an agent learns what it is reading in the same fetch that delivers it.

None of that touches the surface a person sees. The reader gets the page they always got. The machine gets a page it can read without spinning up a browser to do it. The visible thing is for eyes; the structure behind it is for the agent; both say the same thing.

Jono Alderson has been writing a sharp series on what survives when machines mediate the web, and one piece lands on staying weirdly human: the distinctive, idiosyncratic voice that does not flatten into the average. I think he is right, and I think it is only half the instruction. Stay weirdly human on the surface, by all means. Be plainly legible underneath. The voice is for the person who reads it. The structure is for the machine that has to understand it before anyone is recommended anything. A page can be both, and the good ones are.

My fetch came back with three words because of a wall I had built myself. Most pages come back with a spinner because of a wall nobody meant to build. The first I can fix by editing a policy. The second the whole web could fix by serving the machine the meaning it already wrote down for the human. The agent is already at the door. The only question is whether the page bothers to answer.
