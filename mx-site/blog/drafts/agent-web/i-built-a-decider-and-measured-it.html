I Built a Decider and Measured It

22 September 2026 · Tom Cranstoun · 18 min read

Last week I wrote about TypeSafe's Jev, a model that never writes a word and answers typed questions with a probability instead. That description is the company's own, not mine: the launch post says Jev "gives up string generation", and the primitives documentation says the model "returns a probability distribution over your options or levels, never a value outside them". Then Avi Chawla published a walkthrough for building the same interface on an open model, and I couldn't leave it alone. So I built one on the Ollama that already runs on this machine, wrote five evals, and ran them through three lanes: the decider, the same model asked to write an answer, and a Claude call. Every number below comes out of one run file, rendered by a script. I didn't type any of them.

What I Built

The mechanism fits in a paragraph. A language model reading a prompt produces one vector for the next position, with a logit for every token in its vocabulary. Normal generation samples from that vector and goes round again. A decision only needs the first vector. Label each permitted answer with a single letter and put its meaning in the prompt. Ask Ollama for the top twenty logprobs of the first token, keep the ones that are your labels, throw the rest of the vocabulary away, and softmax across what's left. One forward pass, num_predict of one, temperature zero, fixed seed.

That's about sixty lines added to the local LLM client this repository already had, plus a unit test for the arithmetic. It copies the inference path. It doesn't copy the calibration training, and you'll see what that costs.

The Five Evals

I wrote twenty cases for each, with gold labels by hand, so treat the accuracies as indicative rather than as a benchmark. Support ticket routing, with a "none of the above" option. Documentation change-impact triage, with "needs review". Internal link relevance, yes or no. Documentation content type, four kinds. And one from the paper I'd just written: is this document current, asked about ten documents twice: as bare prose with no date, then with frontmatter declaring status and validity.

Three lanes saw exactly the same prompt. The decider ran on three local models with three passes per case. The generation lane ran the same 3B model at temperature zero and parsed the letter out of its answer. The Claude lane ran claude -p on haiku from an empty directory with the default system prompt replaced, no tools, no settings, no MCP servers, so the request held the decision and nothing else.

A 3B decider answers in 102 ms at the median. The same 3B model writing a letter and a sentence takes 441 ms. Claude takes five seconds and $0.0027 a decision, and it's the only lane that gets the answers right. That last column is worth a note of its own: my first Claude call from inside the repository cost $0.17 for a single letter, because the CLI loaded 83,179 tokens of project context before it read my prompt. Any race against "the claude CLI" that doesn't strip that context is timing the tooling, not the model.

The reasoning model is the odd row. gpt-oss:20b came back empty on 98 of 100 calls. Its first token opens a thinking channel, so no label ever appears in the top twenty, and the decider has nothing to score. The technique needs a model whose first token is the answer.

Is It Deterministic? I Measured Instead of Assuming

I'd written "deterministic by construction" in a code comment. Then the first run reported that not one of the 3B decider's hundred distributions matched itself at the sixth decimal. So I recorded the repeats properly and ran it again.

Decider lane Runs per case Same decision every run Same distribution (6 d.p.) every run Largest probability shift seen
Decider (llama3.2:latest) 3 100/100 0/100 0.008493
Decider (llama3:latest) 3 100/100 31/100 0.000996
Decider (gpt-oss:20b) 3 100/100 100/100 0

The decision never moved. The vector moved by under a hundredth. The smoke runs showed why: the first pass scored with a partial prompt-cache hit, the repeats hit the cache for all but one token, and the repeats agreed with each other exactly. So it's reproducible given the cache state and not bit-identical across it. That's a fine property to have. It isn't the one I'd claimed, and I only found out because the run measured it.

The Escape Option Nobody Takes

Chawla's walkthrough makes a point of adding an "other" or "escalate" label, because a restricted softmax over three choices always sums to one and can't say "none of these". I declared one wherever the cases could fall outside the list. Here's how often each lane used it.

Three support tickets were meant to escape: someone's customer list leaked from the platform, a legal team demanding everything held on them under data protection law, a user receiving threats. Both deciders routed all three to "account access". The 8B model did it at 0.82, 0.97 and 0.95. Three PR summaries said nothing ("Misc fixes", "Adjust the thing Sam asked about in the standup", "Tweak the limits") and both deciders judged them anyway; the 8B model decided "Misc fixes" needs no documentation update at 0.997 confidence.

Declaring the escape label is necessary, and it isn't sufficient. A small decider with the option in front of it put almost no mass there, and what it returned instead looked exactly like what it returns when it's right.

The Declaration Delta

This is the one I actually wanted. Same ten documents and the same question, with the frontmatter and then without it.

Local generation (llama3.2:latest) 90% n/a 40% n/a
Claude (haiku) 100% n/a 100% n/a

Read the 8B decider's row. Handed a refund policy, a security overview, an SLA with no date on any of them, it said "current" at 0.71 to 0.81 on half of them, when the honest answer was "cannot be determined". Handed the same documents with status, validFrom, signatureExpires and supersededBy declared, it went ten for ten at a mean confidence of 0.983. Fifty points of accuracy and 0.19 of confidence, from adding the metadata.

Now read the 3B rows, because they complicate it in a useful way. The 3B decider got worse with the frontmatter: it read status: active and answered "not current" four times. The 3B generator went to "cannot tell" on the declared documents, which means it ignored the frontmatter altogether. Declared state helps a model that can read it. The smallest models here mostly couldn't, and the one that could went from a coin flip to perfect.

Then I Put It on a Real Carrier

Frontmatter pasted into a prompt is a fair test of whether a model reads a declaration. It isn't a fair test of MX, because MX says the metadata travels with the file. So I made the same ten documents into PDFs, twice each.

The bare PDF is the rendered page text and nothing else. The MX PDF is the identical file with an XMP packet written into it by the same exiftool config the estate's PDF pipeline uses. The packet holds status, dates, an expiry or review date, what supersedes it, and who owns it. It also holds two plain-language fields: a summary saying what the document is and what state it's in, and agent instructions saying what to do about it. The bodies carry no date, no status and no owner on purpose, so every such fact is in the packet or nowhere.

Then the script does its one job. It peels each PDF the same way regardless of variant: read the XMP packet, extract the page text with pdftotext, and hand the model whatever it found, declared fields first. On the bare file the packet is empty, so the model gets the text. On the MX file it gets the declaration and the same text. Nobody types anything; the carrier decides what the model sees.

Two questions, forty decisions per lane: is this document current, and does this file say who's accountable for it.

The metadata wins on every lane, and it wins in the way that matters. Every decider and every generator scored 100% on the declared PDFs for currency. On the bare PDFs the 3B decider guessed one way or the other for eight of ten documents that say neither, and the 3B generator did the same. Asked whether a bare file names an owner, the 3B decider said yes nine times out of ten, at up to 0.86, for files that name nobody. That's a small model inventing accountability out of a refund policy. Hand it the packet and it's ten for ten at 0.889.

The difference from the pasted-frontmatter eval deserves a pause. There, the 3B models got worse when the declaration arrived. Here they went to perfect. Two things changed at once: the metadata is peeled into labelled lines under a heading that names the packet as its source, and it holds a summary and agent instructions written for a reader, not just a status code. My guess was that the explanation was doing the work. So I ablated it, two more arms on the small models, one with the structured fields and no prose, one with the sentences and no fields.

My guess was wrong. Strip the prose and the 3B decider still scores 100% on both questions; it just gets less sure. The labelled fields are what it reads. What the prose does is arithmetic the 8B model won't do on its own: without the sentence saying "in force", it looked at status: active and a future expires and called two documents not current. And prose on its own is the worst arm on nearly every row. "Reviewed by finance operations" isn't read as an owner the way author: finance-ops is, so the 3B generator's accountability score fell to 30%. The refund policy's summary says "valid until the expiry date declared here", and with the expires field stripped the 8B decider called it not current at 0.965. A sentence that points at a field fails when its target isn't there.

So the full packet wins, and the two halves need each other: the fields are the facts, the prose is the reading of them, and a small model uses whichever one it can parse.

Claude, for the record, got all eighty right on both variants, because on a bare file it says "cannot be determined" and means it. Everyone else needed to be told.

The Confidence Layer

The decider's confidence number has an ancestor on this site. In 2025 I wrote up a framework for evaluating AI confidence. Ask the model for logprobs on every token it generates and throw away the stop words and punctuation. Flag the content words it was less than 60% sure of, list the alternatives it weighed at each one, and roll that up into a level for the whole answer. The demo fed a chat model a false premise, water boiling at a lower temperature when heated harder, and watched it explain the physics fluently. The prose was confident. The probabilities under absorbs, energy, kinetic and reach were all under 0.6, with the words it nearly chose sitting right there. I called it the certainty illusion.

So I built that layer into the generation lane and reran everything. Ollama returns per-token logprobs on a normal chat call, and the library is about a hundred lines of pure functions with a test. For every generated reply the runner now records the label token's probability and how sure the explanation sentence was. The label itself is read by a small grammar rather than a guess: the first non-empty line, with emphasis and any Label: prefix stripped, has to start with a declared letter at a word boundary; failing that, a Label: marker anywhere counts; nothing is ever taken out of prose. Every reply in this run parsed from its first line, and re-parsing the 420 replies from the earlier runs changed no decision. The Claude lane can't carry the layer, because neither the CLI nor the API gives you logprobs. There, the only way to know how sure the model was is to ask it, which is the number TypeSafe's launch post calls overconfident and inconsistent.

Two things came out of it, and the second one I didn't expect.

The label token's probability behaves like the decider's confidence, and now it's the same quantity. The runner takes the first generated token, keeps the ten alternatives Ollama offers at that position, and runs the decider's own restricted softmax over the declared labels. Every label was present in that top ten on all 140 replies, and the arg-max agreed with the parsed letter every time. On every eval the figure is higher when the label was right than when it was wrong, by ten to twenty-seven points. On the PDF currency question it's 72.5% when right and 45.9% when wrong; the decider on the same cases is 77.6% against 49.5%. Same signal, same direction. What's left between the two columns is the prompt, not the arithmetic: asked for only the letter, the 3B model is more decisive on five evals, and asked to add a sentence it's surer on two.

The whole-reply level doesn't track the decision at all. Look at the level column. Most replies come out "low" because the explanation sentence is hedging numerically everywhere, four to six flagged words per reply, whether the label was right or not, and accuracy at "low" is often as good as at "medium". That isn't the framework failing. It measures what it was built to measure, which is how sure a model is of the claims in its prose. A bounded decision is a different object. Its confidence is one token's probability, and the rest of the reply is the model talking. A first-token decider throws the talking away and keeps the token, which is why it's faster and why its number means something.

And the layer gave the carrier result a second witness. On the PDF currency question the generator's label mass went from 0.456 on the bare files to 0.781 on the declared ones, alongside its accuracy going from 20% to 100%. On the pasted-frontmatter eval it sat at 0.606 bare and 0.607 declared while accuracy fell. A declaration the model reads shows up in the number. One it ignores doesn't.

What I Take From It

The decision-model pitch is right about the thing it pitches. Splitting the decision from the generation makes it fast enough to put inside a loop and too cheap to bother counting. I got that on a laptop with sixty lines.

What the pitch leaves out is that a decider is two declarations and a model, and the last is the smallest part. The first declaration is the answer set, and a model can be handed an escape option and still refuse to use it. The second is the state, and a model can be perfectly consistent about a page that never says when it was published. Neither failure shows up in the confidence, because that figure is probability mass over the choices you declared, about the state you supplied. It can't be about anything else.

So if you build one of these, and you should, declare the escape option and then measure whether it gets used, because "declared" and "used" came apart in every eval I ran. And put the declared fields into the state before you ask, because on the one model here that could read them, that was the difference between guessing and knowing. That second part is MX's whole job. Every field a document declares is a question the decider never has to answer. Now I have numbers for what that's worth: fifty points on an 8B model when the frontmatter is pasted in, and eighty points on a 3B one when the packet travels with the PDF and a script peels it out.

The evals, the runner, the run file and the script that rendered these tables are all in the repository. Run them on your own models and tell me what moved.
