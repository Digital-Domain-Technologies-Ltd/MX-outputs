When a Repository Should Refuse to Heal Itself

23 June 2026 · Tom Cranstoun · 7 min read

We like the idea of a repository that fixes itself. You change a source file, and the indexes that summarise it update on their own. A path moves, and the link checker repoints it. Drift creeps in, and a repair pass quietly sweeps it out. It feels like the codebase is looking after itself, and most of the time it is.

The trouble starts the moment you ask where "itself" actually is. Because the same repository is met by very different environments, and a repair that is right in one is quiet, confident damage in another. The hard part is not the healing but knowing when to refuse it.

The same files, two very different homes

A repository turns up in two shapes.

The first is the fat clone: a full local checkout on a developer's machine. Every linked component is pulled down, every dependency is installed, the whole estate is present. On a fat clone an agent can see everything and run every tool it carries. It is the complete picture.

The second is the thin clone: a stripped-down, often cloud-hosted checkout, spun up to do one job and then thrown away. It deliberately leaves most of the estate on the shelf, and it frequently arrives before its tools are even installed. It is a partial picture, and crucially it knows almost nothing about the parts it never fetched.

A third descriptor sits alongside these two: the egress clone, the one allowed to reach the internet. Fat and thin say what a checkout can see; egress says what it can reach, and the repository this post describes runs on egress-less clones by default - anything needing the outside world is written down and routed to the clone that can cross. The healing story below is about seeing, so fat and thin carry the weight here.

Both are legitimate. The thin clone is supposed to be light; that is the whole point of it. You do not fix the difference by making every environment heavy. You fix it by making the repository honest about which one it is standing in.

Why "just regenerate it" is the dangerous instinct

Picture the friendliest possible self-healing task: regenerate a whole-estate index, a file whose job is to list every part of the repository in one place.

On a fat clone this is exactly right. The generator reads the whole tree, emits the full list, and because it is deterministic, running it twice produces byte-identical output. A change in the index means a source genuinely changed. Lovely.

Run that same generator on a thin clone and the failure is not a crash. The generator reads the slice it can see, silently drops every entry the missing parts would have contributed, and writes a file that looks freshly generated and is quietly gutted. No error. No red mark. Just a plausible, authoritative artefact that the next reader, human or machine, inherits as truth.

That is the case worth fearing. A crash tells you something is wrong. A confidently wrong file tells you nothing at all.

Self-awareness is what guards self-healing

The repair is only safe if the thing doing it first works out whether it can see its whole self. So the healing logic asks three plain questions before it writes a single byte.

Am I in the right place? Estate indexes are rebuilt where everyone's work merges together, not on a feature branch where files are still in flux. Regenerating them off to one side just manufactures churn and merge conflicts, so the generators stand down there.

Is the tree complete? If a linked component the index needs to read is absent, the generator cannot represent it, so it must not pretend to. A missing piece of the estate is an immediate "not here".

Are the tools installed? A generator that parses structured metadata needs its toolchain present. In a fresh checkout before the install step has run, parsing fails silently and the generator drops everything it could not read. So an absent toolchain is also a "not here".

When all three answers are yes, the environment is a fat clone in the right place, and a regenerated file is a real update worth keeping. When any answer is no, the same file would be corrupt, and the only correct move is to not produce it.

Refuse loudly, or skip quietly, but never fake it

Knowing it should not run is half the design. What it does about that is the other half, and there are two right behaviours depending on who is asking.

When a generator is told to write, and it cannot do so without lying about what it sees, it refuses loudly. It stops, names the gap in plain language, points at the fix, and writes nothing. A loud refusal is a gift: it converts that silent gutting into an obvious, addressable message.

When a verification gate is checking the work, and the environment cannot run the generator faithfully, it skips that check rather than failing it. Failing a contributor for an environment they did not choose and cannot control just trains people to ignore the gate. Skipping what cannot be verified here, and verifying it where it can be, keeps the gate trustworthy.

Same knowledge, two behaviours. The generator protects the artefact. The gate protects the contributor. Neither one fakes a result.

A check a script can do, a script does

There is a deeper principle underneath all of this, and it is what makes the whole thing hold together. We do not keep these guards in anyone's head, in a memory, or in a sentence of advice that says "remember not to regenerate on a thin clone". A rule written only in prose rots: it gets skipped, it goes stale, and what it claimed to hold quietly becomes a suggestion.

So the environment check is a script. The branch rule is a script. The is-the-tree-complete question is a script. They are wired into the test suite and into the checks that run before code is pushed, and they read the same to every agent that opens the repository, whichever model happens to be reading today. You can ask the repository for its verdict directly and get a straight answer: may these repairs run here, or not, and if not, exactly why.

That is what turns "self-healing" from a hopeful phrase into something you can rely on. The repository regenerates and repairs only where it can see its whole self, and it refuses everywhere else, because healing from a partial view heals wrong. The machine is as much the audience for that verdict as any person is; an agent reads the same refusal a developer does, and stops for the same reason.

The cleverness was never in the healing. Plenty of systems can rewrite a file. The cleverness is in a system that knows the difference between repairing itself and damaging itself, and has the discipline to stop at the line.
