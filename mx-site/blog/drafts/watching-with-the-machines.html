Watching with the machines

31 May 2026 · Tom Cranstoun · 7 min read

The Silent Install series argued one thing across all of it. Trust has to run in both directions. If the web is going to make content legible to machines, the machines have to be legible back: who deployed them, what they may do, what they actually did. The exhibit was Chrome quietly writing a four-gigabyte AI model to people's disks. The fix the series pointed at was attestation and a record.

This is the same model, used for the thing it should have been used for.

What it does

Click an icon in the browser toolbar on any web page. A small panel opens. It reads the page's HTML for the signals MX cares about, asks the page's own origin whether it serves the discovery files machines look for, and asks the on-device language model to write a brief summary of how MX-ready the page is.

No part of the inspection sends the page anywhere. The model that writes the summary is whichever the browser brought along. Chrome ships Gemini Nano, Edge ships Phi-Silica on Copilot+ PCs, and the panel uses whichever one is enabled. On any browser without an in-built model, the panel reaches a local Ollama server if Ollama is installed, and uses whichever model the operator has pulled.

The data does not leave the device. Not by accident, by design.

What MX-ready looks like, in a panel

The panel splits its findings into sections the same way the audit pipeline does, at a level a popup can run in under a second:

  • MX. The magic-header meta tag that says "this page is MX-aware," the governance triplet of status, content-type, and audience, and the AI policy hints (welcome, editable, content-policy).
  • AI. The WICG ai-disclosure meta tag (with the right value for how the page was authored), and the matching IPTC digitalSourceType IRI inside the page's structured data.
  • Links. The discovery links in the page head: llms-txt, ai-usage, the canonical, the sitemap pointer.
  • Origin. The files the origin serves at the root: /llms.txt, /AI-USAGE.json, /robots.txt (with a check for whether it blocks AI agents), /agent-card.json for sites operating agents, /sitemap.xml.
  • Data. Schema.org JSON-LD presence and type coverage.
  • OG. Open Graph fields and Twitter Card fields.
  • A11y. The accessibility quick wins: the document's declared language, a skip-to-main link, image alt coverage, form-control labelling.
  • Prov. The provenance markers: the embedded source-YAML frontmatter in the page head, references to a provenance payload.

Each item lands as a pass, a warn, a fail, or an info. The score is the equal-weight average across them. A page above 70 is doing the work. A page below 50 has the standard in front of it untouched, which is the more useful diagnosis because it names the gap.

Three places the summary can come from

The summary panel writes the verdict. Where that prose comes from depends on what the browser exposes:

Chrome with the Prompt API flag. The on-device Gemini Nano model answers. Chrome installed the weights through its component-update system, which is also the subject of the series. On a machine where Nano has been installed, this is the lightest and fastest path because the model is already in memory.

Edge on a Copilot+ PC. Microsoft's Phi-Silica answers, also locally. The Edge surface (self.ai.assistant) has the same shape as Chrome's, so the panel does not care which one fires.

Local Ollama, anywhere. When neither browser exposes an in-built model, the panel reaches http://localhost:11434 and asks whichever model the operator has pulled to write the summary. This is the same default the full MX audit pipeline uses in regulated-industry mode, where the policy is "no client data crosses the browser sandbox into a vendor's cloud" and the operator wants a model under their own administrative control answering the prompt instead of one shipped by the browser vendor.

A single button in the panel forces the Ollama path even when the browser has its own model. Useful for comparing a small Nano against a larger Ollama model on the same page, or for committing to the regulated-industry path when an organisation's policy requires it.

A second button copies the score, the summary, and every finding to the clipboard. Useful for pasting into a bug report, an outreach note, or a row in a CSV when sweeping across a sample of pages.

Local by design, not by marketing

The inspection stays on the machine for reasons of consent, correctness, and regulation.

Consent: the page being inspected may not have given permission for its content to reach a remote endpoint. Sending the page somewhere for the inspection would put the inspector in the position of the very actors MX exists to hold to account.

Correctness: the signals the panel reports are facts about the bytes the browser already loaded. They do not need a remote model to confirm. The model writes prose, not findings.

Regulation: the MX audit pipeline already runs in a local-LLM-first configuration because regulated industries (financial, healthcare, public sector) cannot ship client data across vendor sandboxes for inference. The extension follows the same rule. The Ollama fallback is the same lever the audit pipeline pulls.

Where this fits

The MX audit pipeline is the full system: dozens of inputs, weighted scoring, written reports, accessibility conformance, provenance sidecars, gates against drift. The panel is its lightweight cousin. The audit is for client engagements where you want the report. The panel is for ten seconds on the page in front of you when someone asks "is this MX-ready?"

The signals the panel grades are the signals the series argued for. The magic-header meta tag and the governance triplet are the page's way of telling a machine what it is. The AI disclosure is the page's account of how it was authored. The discovery files at the origin are the publisher's offer to be machine-legible at the site level. The provenance markers are the chain a regulator or an inspector can walk back to the source. None of these are theoretical. They are the things a machine reading the web on someone's behalf either finds or has to guess about. Guessing, in MX terms, is the part the standard exists to remove.

The Silent Install series pointed at a browser writing a model to a user's disk without asking. The lesson was not that on-device inference is wrong. The lesson was that the relationship between the person and the software acting on their behalf has to run in both directions. This extension is one small step at the page level: a local read of how legible a single page is, run on the same kind of on-device model that started the conversation. Installed carefully, with a button that names the boundary it runs inside, used to make a thing more legible rather than less.

Where to find it

The extension lives in the MX-Hub repository alongside the audit pipeline it cousins. It loads as an unpacked browser extension via the standard developer-mode flow in Chrome or Edge. The README walks through the install steps, the on-device model setup for Chrome and Edge, the Ollama fallback (including the one configuration step that catches everyone the first time around CORS), and how to read the panel.

The extension is a sideloaded developer tool, not a public store listing. The intent is the same as the audit pipeline: an instrument for MX practitioners, demonstrably correct, with the source open to inspection. The first reader is an MX practitioner; the second reader is a regulator who wants to see how the inspection was conducted.
