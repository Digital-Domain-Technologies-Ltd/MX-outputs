An MX Audit, Read by an Engineer

28 May 2026 · Tom Cranstoun · 3 min read

An MX audit arrives as a small set of files, and each one is built to be checked by the person who receives it. Here is that set from an engineer's side: what each file is for, what the PDF says about itself, and how to confirm it with tools you already have.

What arrives

A free audit delivers two documents, each as a tagged PDF with an HTML edition beside it. The Main report holds the verdict, the top findings, the action plan, the scope and its limits, the findings in detail and the change since the last audit. The Appendices hold the supporting evidence. A machine-readable JSON export of the results comes with both. A contract, or the evidence add-on, adds the findings export and the provenance pair.

One scale, and findings you can verify

The report uses one scale throughout: Good, Fair or Poor, with a grade alongside, from each row up to the overall figure. A row and its comparison can't speak different languages, and a machine reading the export gets one enum.

Each finding has five parts: what was observed, the evidence, why it matters, what to change, and how to verify it. You'll use the last part most. It names a check you can run yourself, so a fix is confirmed the day you ship it rather than at the next audit.

The report is checked before it ships

Before release, every fact the report states is checked against the results the audit recorded, and a disagreement stops the PDF. So the figure quoted in a paragraph matches the one in the table beside it.

The PDF declares what it is

The PDF conforms to PDF/A-3a for archiving and PDF/UA-1 (ISO 14289-1) for accessibility. It carries each identification only after the finished file has passed validation. Its XMP packet records the title in dc:title, and its Producer field names who issued the report. On a contract or with the add-on, the same packet embeds the full evidence chain under XMP-mx:ProvenanceAiPayload, and the two provenance files ride inside the PDF as associated files.

Checking it yourself

  • Any PDF/UA validator, or a screen reader, tells you whether the tagging holds.
  • exiftool -XMP:all <file>.pdf lists the packet. On a delivery with provenance, exiftool -b -XMP-mx:ProvenanceAiPayload <file>.pdf | jq . returns the chain. The -b flag matters: without it exiftool prepends a label and the JSON doesn't parse.
  • The interactive inspector at /tools/pdf-inspector.html accepts any MX PDF and walks the chain in the browser. The explainer at /learn/mx-for-pdfs.html maps each signal to the standard it cites.
  • The JSON export parses with any JSON tool, so you can compare its figures with the report's tables line for line.

How the pieces fit

The report makes the argument. The export gives a machine the figures. The PDF's metadata says what the document is, and with a contract or the add-on it also holds the evidence chain behind it.

Each part does one job, and you can check every one of them without asking us.
