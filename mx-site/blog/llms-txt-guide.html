Why llms.txt Isn't Working, and How to Fix It

9 April 2026 · Tom Cranstoun · 9 min read

There is a reasonable idea behind llms.txt. Proposed by Jeremy Howard in September 2024, it follows the same logic as robots.txt: place a structured file at your root, and AI systems can find a curated, structured description of your site, without needing to crawl every page to piece together what you do.

The proposal is sensible. The execution, for most sites, is broken in two specific ways that are easy to miss and easy to fix.

The Two Problems Nobody Mentions

A common assumption is that agents fetch llms.txt on their own whenever they answer a query about your site. Most do not. Agents operating at inference time follow their own retrieval logic; they are not scanning your root directory for an llms.txt file on each request.

Where llms.txt does have value is as a query-time index: a short, curated map, kept current, from your site to the pages you stand behind. A tool or agent that chooses to read it gets there faster, and so does anyone who hands it to an assistant first when researching the site, your own team included. It is not a ranking signal, and there is no evidence that publishing one shapes what a model learns. That value only materialises if the file can be reached and read, and this is where most implementations fail.

Problem one, it does not answer as Markdown

The llms.txt proposal defines the file as Markdown: an H1 with the site's name, a short summary, then sections of Markdown links to the pages that matter. A reader that asks for /llms.txt expects exactly that, as plain text, with a 200 status.

Plenty of sites send something else. A catch-all rewrite returns the home page, or an HTML "not found" page, with a 200. A bot wall answers with a challenge page or a 429. A redirect sends the request somewhere that is not the file. Each looks like success in a browser tab and fails for a machine that wanted Markdown.

Google's Lighthouse now checks this. Its Agentic Browsing category includes an llms-txt audit that fetches /llms.txt from the site root. A missing file (any 4xx) is marked not applicable, because publishing one is optional; a server error or a 429 fails. When a file comes back, the audit reads it as Markdown and expects at least one H1 line, at least one Markdown link in [text](url) form, and at least 50 characters (Lighthouse llms.txt audit source; Chrome for Developers). Bare URLs written as plain text do not count as links.

The fix is to serve the file as it is, with Content-Type: text/plain; charset=utf-8 or text/markdown; charset=utf-8, and a 200. Do not wrap it in an HTML document, and do not let a rewrite rule, a firewall or a single-page app router answer for it. Most web servers already send text/plain for a .txt file; the work is making sure nothing in front of the server changes that.

Here is a real llms.txt, the one we use for allabout.network, as it is served:

# allabout.network, CogNovaMX

> Making the web, and everything you publish beyond it, work for everyone and everything that uses it.
> MX (Machine Experience) is structured metadata that makes your content
> readable by every AI agent on earth, without making it less readable by humans.

This is what an agent or assistant needs to understand who we are, what we do, and where to find more. It describes services in plain terms, links to substantive content, and gives enough context that an AI system reading it can form an accurate picture of the organisation, without needing to crawl dozens of pages. That is the point of the format: curated signal, not bulk content. Notice that the links an agent should follow are written as Markdown links; the plain URLs in the "About" section are fine for a person, but a checker that looks for links will not count them.

Problem two, nothing points to it

A file at the root is only found by a reader that already knows to look there. Most do not, so the second fix is to point to it from the pages themselves.

The proposal gives a way to do that with an HTTP Link header on each page: rel="describedby" points to the llms.txt file that covers the page, and rel="alternate" type="text/markdown" points to a Markdown version of the page if you publish one (llms.txt proposal):

Link: </llms.txt>; rel="describedby", </about.md>; rel="alternate"; type="text/markdown"

The same relationships can go in the <head> of every page as link elements, which matters on sites where the body is empty until JavaScript runs:

<link rel="describedby" href="/llms.txt">
<link rel="alternate" type="text/markdown" href="/about.md">

Leave llms.txt out of sitemap.xml. A sitemap lists the pages you want indexed for people; llms.txt is described as a curated overview for language models, not one of those pages (llms.txt proposal). Listing it there, or dressing it up as an HTML page so a crawler indexes it, turns a reading guide into a search result that competes with the pages it links.

These are not technical challenges. They are configuration decisions that most teams simply do not make, because the guidance around llms.txt rarely addresses how a machine reaches the file and reads it.

What MX Practice Says About This

MX, Machine Experience, is a discipline concerned with how digital content is read, interpreted, and used by machines: AI agents, search indexers, voice assistants, training pipelines, and browser automation. Where web accessibility asks how we make content usable for people with disabilities, MX asks the same question about non-human readers. The two turn out to share most of the same answers. You can read more in the MX book series.

From an MX perspective, the llms.txt situation is a familiar pattern. The principle that guides MX work is straightforward: if you want machines to read your content reliably, you cannot depend on them inferring what you intended. You have to make the structure explicit, using mechanisms that machine readers already understand.

llms.txt in its common form asks AI systems to discover and interpret a relatively new convention, and most agents do not go looking for it unprompted. An unfetched file informs no one, and a file that answers with the wrong thing misinforms whoever does fetch it.

This is not an argument against llms.txt. It is an argument for implementing it in a way that works with existing infrastructure rather than waiting for new infrastructure to catch up. That is one of the core principles of MX: do not reinvent, reuse existing patterns. HTTP already has content types and status codes. HTML and HTTP already have link relations. Use what is already there.

A Note on Headless and JavaScript-Rendered Sites

If the above matters for conventional sites, it matters more for headless and JavaScript-rendered ones.

Headless CMSs, Contentful, Sanity, Hygraph, and similar, deliver content through APIs to a frontend that renders it in JavaScript. When an AI agent visits the resulting site, it often sees something like this:

<body>
  <noscript>You need to enable JavaScript to run this app.</noscript>
  <div id="root"></div>
</body>

No content. Just a shell. Two things help here. The link elements live in the <head>, which is served before JavaScript runs, so the pointer to llms.txt is already in the response. And the single-page app router is the usual reason /llms.txt answers with the app shell, so check that the path is served statically before the router sees it.

The Checklist

If you are implementing llms.txt, for any kind of site:

  1. Write it as Markdown. One H1 naming the site, a short summary, and sections of Markdown links to the pages you stand behind.
  2. Serve it as text. text/plain or text/markdown, with a 200, from the file itself. No HTML wrapper, no catch-all rewrite, no challenge page.
  3. Point to it. A Link header or <link rel="describedby" href="/llms.txt"> in the <head> of every page.
  4. Keep it current. Generate it from the same source as the pages and the sitemap, so it cannot list a page that has gone.

Each check is quick. Run curl -sI https://example.com/llms.txt and confirm the status is 200 and the Content-Type is text/plain or text/markdown. Run curl -s https://example.com/llms.txt | head and confirm the first line is a Markdown H1, not <!DOCTYPE html>. Then run Lighthouse's Agentic Browsing category and look at the llms-txt audit.

Readable by Both Means Readable by Both

MX does not treat machine readability as a separate track from human readability. The same content, properly structured, should work for both. llms.txt is consistent with that principle, but only when it is implemented in a way that a machine can reach and read.

Most llms.txt files are well-intentioned but structurally invisible. Nothing links to them, and too many answer with something other than the file. An agent that does not already know to look will not find them, and one that does may receive an HTML page it never requested.

Reachable is not the same as influential, and this post claims only the first. The fix is straightforward. But it does require understanding what llms.txt is for: a query-time index of the pages you stand behind, worth keeping current, because a stale one points machines at pages you no longer stand behind.
