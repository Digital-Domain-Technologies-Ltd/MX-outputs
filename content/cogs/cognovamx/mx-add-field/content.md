# mx-add-field

One command for adding a new MX field. Replaces the manual five-touch-point dance.

## Overview

Adding a single MX field today means editing `mx-canon/ssot/fields-data.yaml`, editing the relevant Appendix M section, bumping the dictionary version, optionally updating a gathering draft, running `fields:gate`, regenerating the definitions index. Five touch points minimum, easy to forget one. The runbook at [`datalake/knowledge/system/adding-an-mx-field.cog.md`](../../datalake/knowledge/system/adding-an-mx-field.cog.md) is the manual procedure; this cog automates the choreography.

## When to use this cog

- A new field needs to enter the MX canon.
- A field's definition needs to be renamed or retyped (use `add` with the new name; the old entry is left as-is unless the author explicitly removes it).
- The author wants to preview a proposed addition before committing (use `propose`).

## When NOT to use this cog

- A field is being **deprecated**. Tom's standing rule is that the canon's `deprecations:` block stays empty; old field names are not migrated through the dictionary. Remove the field directly and address any references to it in a separate clean-up pass.
- A vendor-only `x-mx-` extension is being added. Those live in [`mx-canon/ssot/cognovamx-fields.yaml`](../../mx-canon/ssot/cognovamx-fields.yaml), not the open standard. The cog edits `fields-data.yaml`; vendor extensions get their own pass.
- The field belongs to an external standard (Schema.org, Dublin Core, BCP 47, SPDX). Pass-through fields go in §7 of the relevant gathering draft, not in the canon.

## The lockstep

Every `add` action touches all of these or none:

| Surface | What changes |
|---------|--------------|
| `mx-canon/ssot/fields-data.yaml` | New entry inserted in topical grouping; version bumped; modified-date updated |
| `datalake/manuscripts/mx-books/mx-appendices/appendix-m-index-of-metadata.md` | Prose mirror added in the target §22+ section, with at least one YAML-fence example |
| `mx-shared-gathering/draft-<note>.md` | If named, the field is added to the relevant table or property block, kramdown-rfc style |
| `mx-canon/ssot/definitions-index.md` | Regenerated by `npm run definitions:index` |
| Verification gates | `fields:gate` clean; `check-mx-compliance` totals all zero |

If any step fails, the cog stops and surfaces the error. There is no half-applied state.

## Walkthrough

### Step 1 — Gather field properties

The author is prompted for: `fieldName`, `type`, `definition` (one sentence, full stop), `example`, `profile`, optional `validValues` / `default` / `required`, the target Appendix M section, and (optionally) a gathering draft to update. The schema is exactly the one in [`datalake/knowledge/system/adding-an-mx-field.cog.md`](../../datalake/knowledge/system/adding-an-mx-field.cog.md) §1.

### Step 2 — Determine the Appendix M target

| Profile / intent | Section |
|-----------------|---------|
| General frontmatter (status, contentType, etc.) | §22 |
| Folder metadata / `.mx.yaml.md` | §23 |
| Book or manuscript frontmatter | §24 |
| Non-markdown carriers (shell, JS, CSS) | §25 |
| HTML `<head>` metadata | §26 |

### Step 3 — Identify the gathering draft (optional)

If the field is part of a topic the open standard already covers, the author names the relevant `mx-shared-gathering/draft-*.md`. The cog will add the field's prose to the right section of that note. If no draft applies, this step is skipped.

### Step 4 — Edit `fields-data.yaml`

Insert the new entry in the topical grouping with adjacent fields (e.g. lifecycle fields together, identity fields together). Schema:

```yaml
- name: <fieldName>
  type: <type>
  definition: <definition>
  example: <example>
  profile: <profile>
  status: canonical
  required: <true|false>
  validValues: [<...>]    # only for enums
  default: <value>        # only when there's a safe default
  notes: <notes>          # optional
```

### Step 5 — Edit Appendix M

Add a prose definition in the target section. Timeless wording, no "new in this version", no dates referencing when the field was added. Include at least one realistic YAML-fence example showing the field in context — the drift checker reads these to confirm the field is documented.

### Step 6 — Edit gathering draft (if named)

Mirror the existing IETF-style structure of the note. Add the field to the relevant section table; if it's a Zone-2 field add it under the §6 "Zone 2 core operational fields" section; if it's a discovery / lifecycle field add it under §7a; if it's a pass-through alignment add it to §7.1's inventory. Never add an `mx:` block to a gathering draft — the validator's `GATHERING_FORBIDDEN_KEYS` blocks it, and the drafts can't use MX to describe themselves.

### Step 7 — Bump the dictionary version

Edit the `version:` field at the top of `fields-data.yaml`. Patch bump (1.66 → 1.67) for adding a field. Minor (1.66 → 1.7) for renaming or retyping. Major (1.66 → 2.0) for a breaking change. Update the `modified:` field to today's ISO date.

### Step 8 — Regenerate the definitions index

Run `npm run definitions:index`. The new field should appear in the resulting `mx-canon/ssot/definitions-index.md` row count and in the canon column of its row.

### Step 9 — Run `fields:gate`

Must report clean: `cog:validate` 0 errors, `fields:check` clean (drift OK, stubs OK), `fields:conformance` Level 1 progress not regressed. If anything fails, stop and surface the error.

### Step 10 — Run `check-mx-compliance.js`

Totals must be all zero (`unknown`, `deprecated`, `naming`, `invalid-enum`, `frontmatter-parse-error`). The new field should not introduce any unknowns because it's now in the canon.

### Step 11 — Print the diff

Unified diff of every changed file. Author reviews; if anything looks wrong, rerun the cog with corrected inputs.

### Step 12 — Offer the commit

Default message:

```
Add `<fieldName>` field to MX canon

<one-paragraph context — what the field is for, why now>
```

Do not commit until the author confirms. After commit, suggest pushing per the standard workflow.

## What this cog does NOT do

- Submit the change to The Gathering for ratification. That's the next sister cog (`mx-gathering-submit`, the round-trip flow).
- Mark the field as ratified. `consensus: false` stays on every gathering-draft change until The Gathering's review concludes.
- Backfill existing files with the new field's value. If the field is widely needed, that's a separate sweep (compare the canonicalUri backfill from earlier this week).
- Add a vendor extension (`x-mx-...`). Those live in `cognovamx-fields.yaml`; this cog only touches the open-standard `fields-data.yaml`.

## Verification

After running the cog, confirm:

1. `mx-canon/ssot/fields-data.yaml` carries the new entry, version bumped.
2. Appendix M § carries the prose mirror with an example.
3. The named gathering draft (if any) carries the new field reference.
4. `mx-canon/ssot/definitions-index.md` lists the new field with `canon` column populated.
5. `npm run fields:gate` reports clean.
6. `node scripts/check-mx-compliance.js` reports all zeros.
7. The pre-commit hook accepts the diff (markdown lint, frontmatter validator pass).
