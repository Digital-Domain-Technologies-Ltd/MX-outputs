# Mount Table Architecture: Git Repos as Trackable Filesystems

**Afternoon session — 1 March 2026**

## Summary

This afternoon we established the architectural model for how MX-hub works as a deployable template. The hub's `.gitmodules` file is a mount table — each submodule is a categorised mount (personal, team, product, standard). When a new business deploys MX, they clone the hub and swap the personal mounts while keeping the shared product mounts. Git repositories become trackable filesystems, navigable by AI agents through `.mx.yaml` metadata.

The work also stress-tested the namespace policy for the first time. Adding mount metadata required vendor extension fields — Cog-Nova-MX's first use of the `x-mx-` prefix. It took three naming iterations to get right, which validated the policy's importance and earned a LEARNINGS.md entry.

## What Was Built

### BDR-003: Hub as Mount Table

Established through structured interview. Four mount types:

| Type | Swappable | Examples |
| ---- | --------- | -------- |
| **Personal** | Yes — each person/business mounts their own | mx-crm, mx-outputs, allaboutv2 |
| **Team** | Yes — each team creates their own | mx-collaboration |
| **Product** | No — same repo, mounted by all customers | mx-audit, mx-reginald, mx-maxine-app |
| **Standard** | Fork — upstream standard + local cogs | mx-canon |

The insight: any git repository on any host (GitHub, GitLab, Bitbucket, self-hosted) with `.mx.yaml` metadata becomes a trackable filesystem. The hub's mount table is one instance of a broader pattern.

### First Vendor Extension Fields

Added `x-mx-mount-type`, `x-mx-mount-swappable`, and `x-mx-mount-upstream` to all submodule `.mx.yaml.md` files. These are Cog-Nova-MX's first public vendor extensions, following the established namespace policy:

- Standard fields (no prefix) — The Gathering
- `mx:` object — The Gathering standard extensions
- `x-mx-` prefix — Cog-Nova-MX public extensions
- `x-mx-p-` prefix — Cog-Nova-MX private extensions

Registered all three fields in the field dictionary with a new `x-mx-public` profile.

### Namespace Policy Validated

The naming went through three iterations:

1. `mount: { type, swappable }` — wrong (nested objects)
2. `mountType`, `mountSwappable` — wrong (bare camelCase looks like standard fields)
3. `x-mx-mount-type`, `x-mx-mount-swappable` — correct (vendor extension prefix)

Tom caught both mistakes. The correction led us to the existing namespace policy ADRs — documents we'd written weeks ago but hadn't yet exercised. First real use of the policy proved it works.

### Info Cogs

Two new reference cogs in `mx-canon/mx-the-gathering/`:

- **namespace-extensions.cog.md** — Explains how extensions work: standard vs vendor, prefix conventions, how to create new extensions
- **field-dictionary-guide.cog.md** — Companion guide to the field dictionary spec: profiles, overlap resolution, how to add fields

## Revenue Implications

The mount table architecture is the deployment model. Every customer gets a hub. Every hub mounts Cog-Nova-MX products. The mount table is the billing surface. Product mounts (mx-audit, mx-reginald, mx-maxine-app) are licensed. Personal mounts are the customer's own. This makes the business model concrete and auditable.

## What This Means

The hub is no longer "Tom's workspace." It is a template that any MX-powered business can clone. The mount types make onboarding explicit: "clone the hub, fork Canon, create your personal repos, mount them." The namespace policy ensures that Cog-Nova-MX extensions are clearly separated from The Gathering's open standard — other implementations can ignore them or adopt them.
