# Co-Directors Report — Magic-header carrier convention + PRD humanisation + repo-wide byte-zero scrub

**Date:** 18 May 2026 — Morning
**Segment:** morning (since midnight 2026-05-18, after yesterday evening's report)

---

## Summary

The morning ratified a single carrier convention for the cog magic-header — a YAML comment line inside the frontmatter, an `mx:cog` HTML meta tag in `<head>`, and an XMP packet in PDFs — and applied it across the whole repo: 244 markdown files, 302 HTML files, every PDF generated by the unified orchestrator. The REGINALD v-next PRD was humanised, structurally aligned with the canonical MX two-zone frontmatter, and reorganised so its YAML examples, field tables, and worked end-to-end example all use the same field names (`cogUrn` and `schemaVersion` replaced `cogId` and `cogVersion` to avoid colliding with reserved names in the existing Gathering draft). Two new gathering drafts (MX Decision Records and MX Policy Records) joined the public draft set, and the suite now passes its conformance gate at 0 errors / 0 warnings across all seventeen sister drafts. A new PostToolUse hook gates the rule going forward; a pre-write check now requires the magic-header on every `.cog.md` file.

The headline consequence: the wire schema now travels with the content through every step of the publishing pipeline. A registry, validator, or search indexer can read the same MX metadata from a Markdown source, the HTML rendering, or the PDF, without round-tripping through the originating file. The byte-zero HTML form that was tried earlier and rejected has been scrubbed entirely from the prose — no backward-compatibility shim, no legacy mentions, no documentation drift.

## What Was Done

### 1. REGINALD v-next PRD — humanisation, structural alignment, carrier-envelope section

The PRD at `mx-canon/ssot/papers/reginald-vnext-prd.md` received four substantial passes this morning. The first stripped 120 em-dashes from the body, fixed three heading violations, and removed banned vocabulary and inline-bold-paragraph repetition that read as AI-tells. The second swept the PRD's body YAML examples so each one was MX-compliant (Zone 1 doc identity at the top level; every decision/policy/attestation field under `mx:`); the same pass renamed `cogId` → `cogUrn` (URN form, distinct from the filename-derived `cogId` reserved in the existing Gathering draft) and `cogVersion` → `schemaVersion` (per-`contentType` semver, distinct from the existing `cogHeader.version`). The third added §1.3.1 Carrier envelopes, the explicit per-carrier envelope table (YAML/Markdown, JSON, HTML, PDF/XMP, HTTP headers, database column), and the CogNovaMX pipeline rule paragraph. The fourth pass added a design-rationale paragraph and a paired clean-up where the prose YAML examples in the body were updated to match the field-definition tables (six mismatches fixed: §4.2 missing `cogId`, §4.3 example using short-form `policyRef.cogId`, §5.2 attestation table missing `cogId`, §6.3 policy table missing `cogId`, §6.4 example missing `cogId`, supersedes referencing `policyId` instead of `cogId`). The PDF regenerated cleanly four times across the morning, each time tagged at ISO 14289-1 Level 2 with `MX XMP metadata injected (20 field(s))`.

### 2. Two new gathering drafts: MX Decision Records and MX Policy Records

The cogUrn/schemaVersion rename and the per-`contentType` field families introduced by the PRD have no canonical home in `mx-shared-gathering/` until those drafts exist. Two new IETF-style notes landed this morning, both authored from the canonical template, both passing conformance: `draft-decision-records.md` enumerates the decision-record schema (twelve required fields plus optional `sequence`), the relationship to attestation, completeness signalling, and selective disclosure; `draft-policy-records.md` enumerates the policy-record schema (nine required fields plus optional `supersedes`), the `cogUrn`-vs-`policyId` distinction, clause addressability, versioning, third-party publication, and the conformance hierarchy. Both notes carry the §4.4 design-rationale form pioneered in `draft-cogs.md` and the new §6.5.3 / §6.5.4 universal-field anchors (`cogUrn`, `schemaVersion`) added to the cogs draft itself.

### 3. The magic-header carrier convention, in four forms

Per the discussion in the morning the magic-header now has three canonical carrier forms and one optional metadata-preservation form. Form one — a YAML comment line `# cog v1 spec=... runtime=...` inside the frontmatter, placed on the line immediately after the opening `---` — applies to every markdown carrier. Form two — `<meta name="mx:cog" content="v1 spec=... runtime=...">` in `<head>` — applies to every HTML carrier. Form three — `cogHeader` frontmatter object — applies to consumers that work on parsed YAML rather than raw text. Form four — the preserved source YAML inside an HTML comment in `<head>` — is the optional metadata-preservation aid for HTML generated from a markdown source. All four were applied across the repo: 244 markdown files received the YAML comment line; 302 HTML files received the `mx:cog` meta tag; the unified PDF orchestrator already emitted the XMP form. The byte-zero HTML form that earlier sessions had tried was reverted entirely, the references in spec sources and learnings were scrubbed, and the `cog.v1.cog.md` snapshot of the cog v1 spec on mx-site was rewritten so its §3 describes the YAML-comment-in-frontmatter form as the canonical magic-header line.

### 4. Canon and infrastructure

Two MX-canon fields were broadened in `cognovamx-fields.yaml` (now v6.9): `mx.generate` was expanded to cover both build-pipeline orchestration (`script`/`format`/`output`/`description`) and content regeneration (`prompt`/`source`), since the unified PDF orchestrator and the html-writer skill both depend on the build-pipeline form; `mx.refersToExternal` got a substantive definition replacing the auto-generated stub. The new `cogUrn` and `schemaVersion` universal fields landed in `mx-shared-gathering/draft-cogs.md` §6.5.3 / §6.5.4 (open-standard layer) rather than the dictionary YAML; per the PRD's path-C decision they stay in the gathering draft for ratification and do not pre-empt the standards body.

Two hooks landed. The new `post-write-metadata-transfer.sh` (PostToolUse on Write and Edit) calls `scripts/check-metadata-transfer.js` to verify that any HTML or PDF written into MX content paths carries the appropriate MX metadata form — `<meta name="mx:...">` tags or an embedded YAML comment for HTML, an `XMP-mx:` namespace for PDF. The existing `pre-write-cog-opening.sh` (PreToolUse on Write) gained a second check: every `.cog.md` write must carry the magic-header YAML comment line in addition to the standard 5-line briefing. Both hooks are tested across the obvious failure modes and against the entire `.cog.md` corpus (227 files, all conformant).

### 5. Repo-wide byte-zero scrub

The earlier session had tried a byte-zero HTML magic-header form (`<!-- cog v1 spec=... -->` before the YAML frontmatter); it was rejected because it shifts the frontmatter past byte zero and breaks every YAML parser the ecosystem depends on. This morning the prose mentioning that form was removed from every active authored file: `LEARNINGS.md`, the gathering drafts, the appendix-u and chapter-21 manuscript pages, the cog spec snapshots on mx-site, the canonical `fields-data-cogs.yaml` description for `cogHeader`. Generated outputs were either regenerated from the cleaned sources (`llms-understanding.txt`, `llms-full.txt`, `mx-reginald/index.json`) or patched directly (book HTML outputs that wait on the next book-build run). The historical changelog archive entry was preserved as audit trail. Zero references to the byte-zero form remain in active content.

## Why It Matters

The carrier convention is the operational property the REGINALD v-next architecture depends on. The PRD's §1.3 promises that the wire schema is identical across carriers — that a registry serving a decision COG can hand the same record back as Markdown, JSON, HTML, or PDF without ever round-tripping through the originating file. Until this morning that was a position statement; with the magic-header convention applied across the repo and the PostToolUse hook enforcing it, the property is now real and self-policing. A future audit asking "does the content the registry serves match the content the publisher submitted" can be answered by reading any of the three carriers, not just the original. The CogNovaMX implementation of REGINALD inherits this property from the toolchain at zero additional cost.

The two new gathering drafts close the per-`contentType` schema gap that v-next opened. Decision records and policy records are the artefact classes the AI-governance evidence vehicle depends on; without published drafts naming the fields, regulators or operators trying to implement the PRD have nothing to point at. The drafts pass the field-pattern conformance script and are ready to submit through `/mx-gathering-submit` whenever The Gathering's review window opens.

## The Insight

A magic-header earns its keep through what it survives, not through where it lives. The byte-zero HTML form looked elegant because every reader sees byte zero first — but that very property pushed the YAML frontmatter past byte zero and broke pandoc, gray-matter, and kramdown-rfc. Putting the marker as a YAML comment inside the frontmatter trades the dramatic byte-zero appearance for survival across every parser the ecosystem actually uses, plus the same raw-text visibility (the line sits at byte ~5 of the file, well within any raw-byte scanner's first read). The aesthetic cost was a paragraph of rationale prose; the engineering benefit was the entire toolchain working without workaround.

---

## Decisions Made

- **Magic-header lives inside the frontmatter, never at byte zero.** No backward-compatibility shim. The byte-zero HTML form is removed from every active authored file. Compatibility is not an issue because no production files ever shipped with the byte-zero form.
- **PRD field renames committed.** `cogId` → `cogUrn`, `cogVersion` → `schemaVersion`. The names are CogNovaMX-house terms used inside the REGINALD v-next implementation; The Gathering's existing reserved `cogId` (filename-derived) is left untouched, and the existing `cogHeader.version` is left untouched. No collision with the open standard.
- **Two new gathering drafts join the public set.** decision-records and policy-records will be submitted through `/mx-gathering-submit` when the next review window opens; until then they are draft-status and labelled `consensus: false` per the existing convention.
- **The PostToolUse hook is presence-only, not byte-by-byte equivalence.** It verifies that the destination carrier holds MX metadata in some recognised form, not that the destination's metadata exactly mirrors the source. Equivalence is the publisher's responsibility; the hook is a safety net against fully-stripped destinations.
