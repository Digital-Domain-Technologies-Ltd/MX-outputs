We fetch every page twice: as a server-side agent sees it (raw served HTML, no JavaScript) and after full browser rendering. The gap between those two results is the served-versus-rendered gap: the share of content invisible to agents that do not execute JavaScript. ### A note on llms.txt

The [llms.txt](https://mx.allabout.network/blog/llms-txt-guide.html) convention places a structured description file at a site's root for AI systems to read, following the same pattern as robots.txt. Where a site publishes it, this report records its presence, transport type, and whether it is included in the sitemap.

Two structural problems currently limit its practical reach. The first is content type: the llmstxt.org specification defines `text/plain` as the content type for llms.txt files. We recommend serving llms.txt as `text/html` instead, because Common Crawl (the archive underpinning most major LLM training datasets) prioritises HTML for its LLM-training subsets, so a plain-text llms.txt is unlikely to enter training corpora at the same rate as the rest of the site. The fix is to wrap the raw text in a minimal HTML document with the content inside a `<pre>` block and return `Content-Type: text/html` from the server or CDN edge. The second problem is discovery: without a sitemap entry, crawlers have no reliable signal that the file exists.

The Discovery Files section records llms.txt presence, transport type, and sitemap registration. Where it is absent, we note the gap and the effort required to address it.

**Priority 1: Contrast Ratio 3.09:1 on Usercentrics Consent Banner, WCAG 1.4.3 (7 pages)**

**Bucket:** Compliance Risk

**Finding:** Across the audited set, the accept button rendered by the Usercentrics consent SDK (`#uc-btn-accept-banner`) presents a contrast ratio of 3.09:1 against its background, below the 4.5:1 threshold required by WCAG 1.4.3. The finding appears on every one of the 7 audited pages because Usercentrics injects this element at runtime; it is not part of the typo3.org template. Because consent acceptance is a legally consequential interaction under data-protection frameworks, low-vision users who cannot perceive the button are effectively excluded from exercising an informed choice.

**What to change and why:**
- Engage Usercentrics to adjust the consent banner's button background to meet a minimum contrast ratio of 4.5:1, as the consent SDK controls the rendered colour values and a theme edit to typo3.org's own template will not reach this element. Resolving this through the vendor moves all 7 instances simultaneously and addresses WCAG 1.4.3 across the audited set.
- If an SDK update from Usercentrics is not available within the required remediation window, a DOM-observer patch that modifies the button's background after the SDK injects the element is a viable interim measure; document this patch in the site's accessibility audit trail as a temporary compensating control, not a permanent fix.
- Record the vendor's response and any interim patch in your accessibility conformance record so that an audit trail demonstrating due diligence exists should a regulatory review arise.

**Effort:** Medium

---

**Priority 2: Contrast Ratio 3.09:1 on Page Body Text, WCAG 1.4.3 (1 page)**

**Bucket:** Compliance Risk

**Finding:** On one audited page, body-copy text and in-text link elements within `#c1012` present a contrast ratio of 3.09:1, below the WCAG 1.4.3 minimum of 4.5:1. Three selectors on that page share the same contrast shortfall, suggesting a single styling rule governs both the paragraph text and the anchor elements within it. Low-vision users reading that page risk missing substantive content and any calls to action embedded in the affected text.

**What to change and why:**
- Adjust the background colour applied to the `#c1012` content block so that text and link elements within it achieve at least 4.5:1 contrast. Because three selectors share the same contrast shortfall, a single change to the parent block's background is likely to resolve all three instances together, addressing WCAG 1.4.3 for that page.
- Verify that the corrected contrast value holds across all interactive states of the in-text links (default, visited, hover, focus), as each state may inherit or override the parent background independently.
- Once corrected, add this selector to your regression test suite so that future template or content changes do not reintroduce the contrast gap.

**Effort:** Low

**Priority 3: Iframe Missing Title Attribute, WCAG 2.4.1, Usercentrics Cross-Domain Consent iframe (7 pages)**

**Bucket:** Compliance Risk

**Finding:** Across the audited set, an iframe element with the selector `#cross-domain-consent-sharing-iframe` carries no title attribute. WCAG 2.4.1 requires that frames be given a descriptive title so that keyboard and assistive-technology users can identify the frame's purpose and choose whether to enter it. This element is injected at runtime by the Usercentrics consent-management SDK (hosted at `app.usercentrics.eu`) and is absent from the typo3.org template; sighted keyboard users on all 7 audited pages are therefore unable to determine the frame's purpose from keyboard navigation alone.

**What to change and why:**
- Engage Usercentrics to ship a fix in their consent SDK that adds a descriptive, non-empty title attribute to `#cross-domain-consent-sharing-iframe` at the point of injection. Because this element originates in the vendor's SDK and not in typo3.org's own template, a theme or partial edit on the typo3.org side will not reach it; the remediation must come from the vendor.
- If the vendor fix is delayed, a DOM-observer patch that detects the injected iframe and programmatically sets a descriptive title attribute after injection is a viable interim measure. Document this patch as a temporary compensating control in your accessibility audit trail.
- Confirm with Usercentrics that the title value they add accurately describes the frame's function (cross-domain consent sharing) so that the attribute satisfies WCAG 2.4.1's requirement for meaningful identification, not merely a non-empty string.

**Effort:** Low

**Priority 4: Semantic Structure 21/100, https://typo3.org/association (228 of 310 bare divs)**

**Bucket:** Compliance Risk

**Finding:** We score Semantic Structure at 21/100 across the audited set. The figures that drive this band come specifically from https://typo3.org/association, where 228 of 310 total elements are bare, non-semantic divs. If the remaining audited pages share the same template structure, the band is likely representative of the template's default output rather than content specific to that page. A DOM built predominantly from unsemantic containers gives screen-reader users fewer structural landmarks to navigate by, and reduces the confidence machines can assign when parsing content hierarchy for indexing or summarisation purposes.

**What to change and why:**
- Review the template responsible for https://typo3.org/association and identify layout containers that wrap distinct content regions (navigation, main content, sidebars, footers, complementary sections) with the intent of replacing them with the appropriate sectioning elements. - Prioritise landmark regions first, as assistive technologies expose these to users as navigation shortcuts. Even a partial conversion of top-level containers on the shared template would propagate across every page that uses it, reducing the bare-div ratio beyond the single worst-case page.
- After the initial conversion, rerun the Semantic Structure check against https://typo3.org/association to verify the score moves out of the high-concern band; use the resulting score as the baseline for ongoing template review.

## Server Response Stability

Single load-time measurements can mislead. A page that returns in a few hundred milliseconds on the crawler's second visit may be served from a warm CDN edge; the same page on a genuine cold visit could spend several seconds at the origin before the first byte arrives. To separate the two experiences, this section probes the slowest page from the crawl and a median-load control with three cache-busted GETs each, then compares those measurements against the crawler's original cold-cache baseline. The result is two distinct verdicts per page: a first-visit cost (what a brand-new visitor actually pays) and a returning-visitor cost (what someone with a warm cache experiences). The overall verdict for each page is the worse of the two, so a fast warmed median cannot paper over a slow cold-cache response.

**Method:** Each URL fetched three times with a `?_mx_cb={stamp}` cache-busting query parameter and `Cache-Control: no-cache`. For each page we compare both the crawler's cold-cache baseline and the median of three cache-busted GETs: a response is treated as healthy at or below 1500ms, acceptable up to 3000ms, and slow above 3000ms. The overall verdict reflects the worse of the two views.

**Slowest.** The slowest page is `https://typo3.org/association/membership`. A first-time visitor sees the cold-cache cost: the crawler recorded 1596 ms on its initial fetch. **First-visit verdict: Acceptable but elevated**. Three cache-busted re-probes that followed returned 353ms (HTTP 404), 257ms (HTTP 404), 159ms (HTTP 404); no median is reported because no sample returned a usable timing. **Returning-visitor verdict: Indeterminate**.

**Median-load control.** The median-load control page is `https://typo3.org/`. A first-time visitor sees the cold-cache cost: the crawler recorded 846 ms on its initial fetch. **First-visit verdict: Healthy**. Three cache-busted re-probes that followed returned 80ms (HTTP 404), 164ms (HTTP 404), 234ms (HTTP 404); no median is reported because no sample returned a usable timing. **Returning-visitor verdict: Indeterminate**.

**Verdict:** First-visit response time is within healthy bounds. The returning-visitor view is Indeterminate for both pages because cache-busted re-probes were rate-limited (HTTP 429) or otherwise unsuccessful, so we cannot characterise the warmed-cache experience from this audit.

## Provenance Gap

**What we mean by provenance gap.** A provenance gap is the structural distance between a page that *describes* a claim and a page that *evidences* it. Schema markup tells a machine what an entity is: a Product, an Article, an Organisation: but it cannot tell a machine who made the assertion, when, or whether the claim is supported by anything outside any single page. AI systems that cite content increasingly need both halves: the typed assertion and a verifiable trail behind it. A page with rich JSON-LD but no third-party links, no `dateModified`, no `author`, and a year-swapped title is structurally indistinguishable from a page that was generated to fill an index slot. The Provenance Gap concept and its full taxonomy are documented at <https://mx.allabout.network/blog/the-provenance-gap.html>.

**What this section checks.** Each signal below is derived deterministically from served HTML and JSON-LD on disk: no inference, no model judgement. Five structural signals fire per page: (i) self-promotional listicle (a ranked list is advertised whose first entry resolves to the publisher's own host), (ii) year-swap refresh (the title year is two or more years ahead of `dateModified`), (iii) first-party superlative (claims like "best", "leading", "world-class" without an external reference), (iv) third-party citation count (outbound links to hosts other than the audited site), and (v) provenance metadata presence (`author`, `dateModified`, `publisher`). Pages whose body content runs over 400 words while emitting zero third-party citations carry no verifiable references and contribute to the blocker list. When the audited set is clean we omit the per-page table altogether and let the verdict line below carry the result.

## Schema Maturity Level

Schema.org implementations fall into five maturity tiers. The transitions are not continuous. Each level requires structurally different work. Maturity is a structural classification: it depends on what the markup carries (typed blocks, required properties, cross-references, external identifiers), not on the SDQ score the markup happens to earn. A page can sit at Level 1 with a high SDQ score and at Level 3 with a moderate one. Score and level are reported separately.

|  | Level | Name | What it looks like |  |
|---|-------|------|---------------------|---|
| **→** | 0 | Clean slate | No Schema.org markup present. The full maturity curve is open: every property added at this stage is net new capability. | **←** |
|  | 1 | Decoration | Typed blocks present, with sparse properties and no nesting or cross-references. The structural primitives are in place; the next opportunity is to fill the required and recommended fields. |  |
|  | 2 | Good schema | Full required and recommended properties, nested types where appropriate, valid vocabulary. The next opportunity is to wire entities together with @id cross-references. |  |
|  | 3 | Real graph | Level 2 plus @id cross-references between entities and linked-data signals (sameAs, mainEntityOfPage, isPartOf). The next opportunity is to anchor entities to external identifiers. |  |
|  | 4 | Verified linked data | Level 3 plus external identifiers (Wikidata QIDs, ISNIs, ORCIDs) and provenance metadata. Entities are anchored in the linked-data web. |  |

**Current level:** 0: Clean Slate\
**To reach the next level:** Add at least one Schema.org JSON-LD block (e.g. Organisation, WebSite, or Article); every property added is net new capability for AI agents.

The Structured Data Quality (SDQ) score and the Schema Maturity Level measure two different things. SDQ counts the properties present and validates them against Schema.org expectations; the level captures whether those properties are connected (cross-entity wiring, linked-data signals, external authority identifiers). Both numbers above are reported as-is from the audit data.

## Div Soup: naked containers without semantic mapping

When every container is a `<div>` with no role, no ARIA landmark, and no class name that describes what it is, machines lose structural context and fall back on positional inference ("the third div from the top is probably navigation") to determine meaning. The visual layout still works for sighted users; the structural information that machines need to index, cite, and represent each page is gone.

We run the Div Soup check on both served and rendered HTML so we can tell whether the soup is in the source the publisher controls or something the JavaScript framework introduces at render time. Score 100 is a page with no naked divs; score 0 is the worst case (every container is a bare nested div).

| Source | Score (band) | Bare div stats | Top bare selectors |
|--------|--------------|----------------|--------------------|
| Rendered HTML | 21/100 (high) | 228 bare divs · 74% ratio · depth 7 | `div.frame-group-container` (136), `div.frame-group-inner` (132), `div.frame-container.frame-container-default` (132), `div.frame-inner` (132), `div.contentcontainer-column` (77) |

On the worst page we sampled, https://typo3.org/association, 228 of 310 elements on the rendered surface are bare divs (74%), meaning machines lose structural context and must rely on positional inference to determine meaning. The pattern is simultaneously deep and surface-wide: a deepest bare chain of 7 combined with a high bare-div ratio points to an untyped component framework where layout wrappers such as `div.frame-group-container`, `div.frame-group-inner`, `div.frame-container.frame-container-default`, and `div.frame-inner` are stacked concentrically, each adding nesting without contributing semantic signal. The most direct first move is to replace the outermost wrappers with appropriate landmark elements (header, nav, main, footer) and assign meaningful class names to the remaining containers, which would reduce the bare-div ratio without requiring any restructuring of the visual layout.

## Appendix C: Image Optimisation

Across the audited set, we catalogued 71 images in total. SVG is the dominant format at 52 images, followed by 14 PNG, 3 WebP, and 2 JPEG. Alt-text coverage stands at 51 images (71.8%), leaving 20 without descriptive text. Those 20 gaps are worth resolving: screen readers and machines alike rely on alt text to understand non-decorative images, and missing attributes reduce both accessibility scores and the quality of structured content signals.

On loading strategy, 22 images carry the explicit `loading="lazy"` attribute, and none are marked `loading="eager"`. The remaining 49 images have no loading attribute at all. That third state is worth noting separately: a missing attribute does not behave identically to eager loading. The browser applies its own heuristic, factoring in the image's position in the document and viewport size, and the result can vary across browsers and devices. For images below the fold, adding `loading="lazy"` gives the browser an unambiguous instruction; for images in the initial viewport, an explicit `loading="eager"` makes the intent equally clear. Working through those 49 un-attributed images and tagging each one deliberately would tighten control over page load sequencing across the audited set.

> **Double-lazy loading pattern not detected** - no image in the audited set carries both native `loading="lazy"` and a JavaScript lazyload placeholder at the same time.
